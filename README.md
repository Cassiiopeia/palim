# Palim (팔림)

> 여러 판매채널에서 물건이 팔리는 순간을 놓치지 않는 재고 알림 시스템

쿠팡·네이버 스마트스토어·롯데온 등 여러 채널에 흩어진 주문을 자동으로 모아 하나의 재고로 관리하고, 판매가 발생하면 텔레그램으로 즉시 알려줍니다.

---

## 왜 만들었나

여러 채널에서 물건을 파는 소규모 판매자는 대개 이런 상황에 놓입니다.

- 채널마다 따로 로그인해야 주문을 확인할 수 있다
- 채널별 재고를 엑셀로 각각 관리하다 보니 숫자가 실제와 어긋난다
- 같은 물건을 여러 채널에 걸어두면 동시에 팔려 **초과판매(오버셀링)** 가 발생한다
- ERP를 도입해도 판매 데이터를 결국 사람이 옮겨 담아야 한다

기존 통합관리 솔루션(사방넷, 플레이오토 등)은 이 문제의 상당 부분을 해결하지만, **판매자에게 능동적으로 알려주지는 않습니다.** 웹에 접속해서 직접 확인해야 하고, 알림톡 기능은 구매 고객을 위한 것입니다.

Palim은 그 빈자리를 채웁니다.

| | 기존 통합관리 솔루션 | Palim |
|---|---|---|
| 성격 | **관리 도구** — 접속해서 확인 | **감시 도구** — 접속하지 않아도 통보 |
| 알림 대상 | 구매 고객 | **판매자 본인** |
| 알림 수단 | 이메일, 웹 화면 | **텔레그램 실시간 푸시** |
| 알림 규칙 | 고정 | 사용자가 직접 설정 |

## 주요 기능

### 주문 수집과 알림
- 여러 채널의 주문을 공식 API로 자동 수집
- 신규 주문 발생 시 텔레그램 즉시 알림
- 채널별 API 호출 한도를 준수하는 큐 기반 스케줄러

### 재고 관리
- SKU 단위 통합 재고 — 어느 채널에서 팔려도 하나의 재고에서 차감
- 채널 상품코드 ↔ 자사 SKU 매핑 관리
- 안전재고 미달 시 경고 알림
- 재고 변동 시 각 채널 판매 가능 수량 자동 동기화

### 리포트
- 일일 판매·재고 요약을 텔레그램으로 발송
- ERP 업로드용 판매내역 엑셀 내보내기

### AI 보조
- 일일 리포트를 자연어 문장으로 재작성
- 텔레그램에서 자연어로 재고·매출 조회

```
발주자: 지금 재고 얼마나 남았어?
Palim : 전체 21개 SKU 중 재고 부족이 3건입니다.
        SKU-003 (4개), SKU-007 (2개), SKU-015 (1개)
```

> **AI는 수치를 계산하지 않습니다.** 모든 수치는 데이터베이스 조회와 코드 연산으로 산출하며,
> 언어 모델은 그 결과를 문장으로 표현하는 역할만 수행합니다.

## 지원 채널

| 채널 | 주문 수집 | 재고 동기화 | 연동 방식 |
|---|---|---|---|
| 쿠팡 | ✅ | ✅ | 공식 API (HMAC-SHA256) |
| 네이버 스마트스토어 | ✅ | ✅ | 공식 API (OAuth2 + 전자서명) |
| 롯데온 | ✅ | ✅ | 공식 API |
| 11번가 | ✅ | ✅ | 공식 API |
| G마켓 / 옥션 (ESM) | ✅ | ✅ | 공식 API (JWT) |
| SSG닷컴 | 🔜 | 🔜 | 공식 API (입점 승인 선행) |
| 롯데백화점 | 📄 | ❌ | 공식 API 없음 → 엑셀 업로드 |

채널 어댑터는 각각 독립적으로 구성되어, 새 채널을 추가해도 기존 코드에 영향을 주지 않습니다.

## 설계 원칙

### 정확성이 필요한 곳과 표현이 필요한 곳을 나눈다

```
        [ 정확성 영역 — 코드가 처리 ]
주문 수집 → 중복 제거 → 재고 계산 → 채널 동기화
                          │
                          ▼ 수치는 여기서 확정
        [ 표현 영역 — 언어 모델이 처리 ]
        ├─ 리포트 문장 생성
        └─ 자연어 질의 응답
```

재고 계산, 중복 주문 판정, 채널 전송 판단에는 언어 모델을 사용하지 않습니다.
오류가 발생하면 곧 매출 손실로 이어지는 영역이기 때문입니다.

### 부가 구성 요소의 장애가 핵심 기능을 멈추지 않는다

- 알림 대상은 주문 저장과 **같은 트랜잭션에서 Outbox에 기록**합니다. 발송이 실패해도 유실되지 않습니다.
- 애플리케이션이 재기동되면 미발송 알림을 이어서 발송합니다.
- 언어 모델 장애 시 리포트는 기본 형식으로 발송됩니다.

### 재고를 밀어 넣는 기능에는 안전장치를 둔다

채널에 재고를 잘못 전송하면 상품이 품절 처리되어 매출 손실이 발생합니다.

- **시뮬레이션 모드** — 실제 전송 없이 전송 예정 내용만 알림
- **변동량 상한** — 1회 변경량이 임계치를 넘으면 중단하고 경고
- **전체 중단 스위치** — 재고 전송을 즉시 비활성화
- **전송 이력** — 변경 전후 값을 모두 기록

## 기술 구성

| 영역 | 사용 기술 |
|---|---|
| 언어 · 프레임워크 | Java 25 · Spring Boot 4.1 |
| 빌드 | Gradle (Kotlin DSL), 도메인 축 멀티모듈 10개 |
| 데이터베이스 | PostgreSQL — 주문·재고·매핑·설정의 단일 기준 |
| 알림 전달 | PostgreSQL Outbox — 재시도·유실 방지의 단일 근거 |
| 알림 | Telegram Bot API |
| 화면 | Thymeleaf · Tailwind CSS 4 · daisyUI 5 |
| 배포 | GitHub Actions → GHCR → Docker Compose |
| 외부 노출 | Cloudflare Tunnel |

### 확장을 고려한 구조

현재 데이터 규모에서는 PostgreSQL만으로 충분하여 검색 엔진을 도입하지 않았습니다.
다만 규모 확대에 대비해 다음을 설계에 반영했습니다.

- 조회 로직을 별도 계층으로 분리 → 검색 엔진 도입 시 해당 계층만 교체
- 모든 레코드에 변경 시각 기록 → 증분 색인 가능
