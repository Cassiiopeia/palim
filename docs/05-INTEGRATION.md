# 05. 외부 연동

## 채널 어댑터

### 계약

```java
public interface ChannelOrderCollector {
    ChannelCode channelCode();
    List<ChannelOrder> collect(Instant from, Instant to, Map<String, String> credentials);
}
```

어댑터는 채널 API 를 호출해 공통 `record` 를 반환할 뿐이다. **도메인 엔티티를 알지 못하고 데이터베이스에 접근하지 않는다.** 엔티티 변환은 `palim-collector` 의 몫이다.

그래서 신규 채널 추가가 기존 코드에 영향을 주지 않는다 — 어댑터에서 `Sku` 를 참조하면 컴파일이 실패한다.

### 구현 시 지킬 것

| 항목 | 이유 |
|---|---|
| 주문 시각을 `Instant` 로 정규화한다 | 채널이 KST 로 주면 변환해야 한다. 타임존 모호성은 재고 이중 차감으로 이어진다 |
| 페이징이 있으면 전체를 순회한다 | 부분만 반환하면 주문이 누락된다 |
| **실패는 예외로 던진다** | 빈 목록을 반환하면 조율 계층이 "주문 없음"으로 오판해 커서를 전진시키고, **그 구간 주문이 영구 유실된다** |
| 호출 제한을 준수한다 | 쿠팡은 지속 초과 시 **영구 차단**된다 |

### 채널별 호출 제한

| 채널 | 제한 | 기본 수집 주기 |
|---|---|---|
| 쿠팡 | 초당 10회, 지속 초과 시 **영구 차단** | 5분 |
| 네이버 | 초당 2회 | 5분 |
| G마켓/옥션 | 주문조회 5초당 1회 | 10분 |
| 11번가 | 미공개 | 10분 |
| 롯데온 | 미공개 | 10분 |
| SSG닷컴 | 미공개 | 10분 |
| 롯데백화점 | 공식 API 없음 → 엑셀 업로드 | 수집 안 함 |

### 응답 회귀 감지

각 채널의 **실제 API 응답 샘플을 테스트 리소스로 보관**하고 파싱 회귀 테스트를 둔다.

> 채널 API 사양 변경은 통제 불가 요인이다. 변경을 감지할 수 있는 유일한 수단이 보관된 실제 응답과의 비교다. 샘플 없이 수개월 뒤 파싱 오류를 만나면 원인 파악에만 수일이 걸린다.

### 인증정보

DB 에 저장하고 애플리케이션에서 AES-GCM 으로 암호화한다. 마스터키는 환경변수 `PALIM_CRYPTO_MASTER_KEY` 로 주입한다.

- 저장 형식 — `base64(nonce || ciphertext || tag)`
- **nonce 는 암호화마다 새로 생성한다.** GCM 에서 같은 키로 nonce 를 재사용하면 평문을 복원할 수 있는 치명적 취약점이 생긴다
- 마스터키가 없으면 **기동을 실패시킨다.** 암호화 없이 인증정보를 저장하는 상태로 뜨는 것보다 안전하다
- 평문은 `ChannelCredentialService` 경계에서만 오간다. 암호문도 이 서비스 밖으로 나가지 않는다

채널마다 인증 필드 구성이 달라(쿠팡 accessKey/secretKey/vendorId, 네이버 clientId/clientSecret) 컬럼 대신 key-value 로 저장한다.

환경변수 단독 방식을 쓰지 않는 이유는 웹 관리자에서 인증정보를 등록·갱신할 수 있어야 하기 때문이다(F-09). 발주자가 키를 갱신해도 재배포가 필요 없다.

## 수집 조율

### 흐름

```
CollectScheduler (1분 주기)
  → 수집 시각이 도래한 채널 조회        (Channel.isDueAt 이 판정)
  → ChannelCollectRunner.run(channel)   트랜잭션 없음 — 외부 API 호출
      → 인증정보 복호화
      → 어댑터 호출
      → 주문마다 OrderIngestionService.ingest()   REQUIRES_NEW
      → 커서 갱신 / 실패 기록            CollectStateService (@Transactional)
```

### 수집 커서 — 구간을 겹친다

```
조회 구간 = [collectedUntil - overlap, now]     기본 overlap = 10분
커서 없으면 = [now - initialLookback, now]      기본 24시간
```

> 채널 API 는 주문 시각이 지연 반영되는 경우가 있어 구간을 정확히 이어붙이면 경계에서 주문이 누락된다. **중복은 유니크 제약이 막지만 누락은 아무도 감지하지 못한다.**

### 실패 시 커서를 전진시키지 않는다

| 상황 | 커서 | 실패 카운터 |
|---|---|---|
| 전 주문 처리 성공 | 전진 | 초기화 |
| 일부 주문 실패 | **전진하지 않음** | 올리지 않음 |
| 채널 호출 자체 실패 | **전진하지 않음** | 증가 |

전진시키면 실패한 주문이 영구 유실된다. 전진시키지 않으면 다음 주기에 같은 구간을 다시 조회하고, 성공했던 주문은 유니크 제약이 걸러내며 실패한 것만 재시도된다 — **겹침 수집과 유니크 제약이 이 재시도를 안전하게 만든다.**

일부 주문만 실패한 경우 실패 카운터를 올리지 않는다. 채널은 정상 응답했고 일부 주문만 문제였으므로 채널을 비활성화할 이유가 없다.

### 연속 실패 대응

연속 실패가 임계치(기본 3회)를 넘으면 텔레그램 경고 후 **채널을 자동 비활성화**한다. 쿠팡은 인증 실패나 호출 제한 초과가 지속되면 영구 차단되므로, 실패를 반복하는 것보다 멈추는 편이 안전하다.

## 알림 파이프라인

### Outbox 단독 — 메시지 큐를 쓰지 않는다

```
주문 저장 + outbox 행 삽입        ← 동일 트랜잭션 (원자적)
        │ 커밋
        ▼
NotificationRelay (30초 주기) → 텔레그램 발송 → outbox 상태 SENT
```

RabbitMQ 를 쓰지 않는 근거는 [07-DECISIONS](07-DECISIONS.md) 의 007 항목에 있다. 요약하면 **재시도 근거가 두 곳으로 갈리기 때문**이다.

`NotificationRelay` 는 `ApplicationRunner` 로 기동 시 1회 실행되어 재기동 전에 남은 알림을 이어서 발송한다. 이것이 인수조건 A-14 를 충족시키는 지점이다.

### 발송 실패는 결과 객체로 표현한다

```java
public record TelegramSendResult(boolean success, boolean retryable, String errorMessage)
```

| 응답 | 처리 |
|---|---|
| 4xx | **즉시 `FAILED`.** 잘못된 chat_id·봇 차단·토큰 무효는 재시도해도 성공하지 않고 호출 제한만 소모한다 |
| 5xx · 타임아웃 | `attemptCount` 증가. 한도(기본 5회) 초과 시 `FAILED` |

예외로 표현하면 `retryable` 구분이 예외 타입이나 메시지에 묻힌다.

### 발송 방식 (F-02)

| 설정 | 동작 |
|---|---|
| 즉시 발송 | Outbox 등록 후 다음 relay 주기에 발송 |
| 묶음 발송 | 가장 오래된 알림 + 설정 주기가 지나면 하나로 합쳐 발송 |
| 야간 보류 | `quietHours` 안이면 발송하지 않고 `PENDING` 유지 |

**긴급 알림은 야간 보류·묶음에서 제외한다.**

```java
OVERSELL, OUT_OF_STOCK, COLLECT_FAILURE, STOCK_PUSH_FAILURE, STOCK_MISMATCH
```

> 재고가 음수가 되었거나 수집이 멈춘 상황은 아침까지 기다릴 수 없다. 발주자가 알림 과다를 우려해 야간 보류를 켰더라도 매출 손실로 직결되는 사안은 즉시 알려야 한다.

묶음 대상은 주문 알림뿐이다. 묶음은 주문량이 많을 때 알림 과다로 확인하지 않게 되는 문제를 막기 위한 기능이므로, 빈도가 낮은 다른 알림은 묶을 이유가 없다.

### 텔레그램 미연결 상태

봇 토큰이나 `telegramChatId` 가 없으면 발송을 시도하지 않고 `PENDING` 을 유지한다. 알림은 유실되지 않지만 **연결 전 기간이 길어지면 Outbox 가 쌓이므로** 경고 로그를 남긴다.

봇 토큰이 없어도 기동은 막지 않는다. 암호화 마스터키와 달리 발주자가 나중에 설정하는 항목이다.

## 채널 재고 전송 (F-08)

**이 기능만 채널에 데이터를 기록한다.** 오류 시 실제 판매에 영향을 주므로 안전장치를 함께 둔다.

| 안전장치 | 동작 |
|---|---|
| 시뮬레이션 모드 | 실제 전송 없이 예정 내용만 알림. **기본값 활성** |
| 변동량 상한 | 1회 변경량이 설정값 초과 시 전송 차단 + 경고 |
| 전체 중단 스위치 | 웹에서 즉시 비활성화. **기본값 비활성** |
| 전송 이력 | 시각·채널·SKU·전후 값 기록 (시뮬레이션 포함) |

기본값이 안전한 쪽이다. 재고 계산 오류로 0을 전송하면 상품이 전 채널에서 품절 처리되어 매출 손실이 발생한다.

도입 초기에는 시뮬레이션 모드로 수 주간 운영해 전송 예정 내용을 검증한 뒤 실제 전송으로 전환한다. **선택이 아니라 필수 절차로 취급한다.**

### 버퍼 재고 정책 (전제 설계 — 구현은 Phase 5)

채널에 전송하는 수량은 실재고가 아니다.

```
채널 전송 재고 = max(0, 실재고 − 채널별 버퍼)
```

실재고 3개를 3개 그대로 전 채널에 노출하면, 두 채널에서 거의 동시에 주문이 들어왔을 때 수집
주기(수 분) 안에는 차감이 반영되지 않아 오버셀이 난다. 버퍼는 그 수집 지연 동안의 동시 주문을
흡수하는 여유분이다.

| 설계 결정 | 내용 |
|---|---|
| 버퍼 단위 | 채널별 1개 값. SKU×채널 매트릭스는 1인 운영에서 관리 불가능하다 |
| 버퍼 기본값 | 0 — 켜기 전까지 기존 동작과 동일 |
| 음수 방지 | 실재고 < 버퍼면 0 을 전송한다. 음수 전송은 채널 API 오류다 |
| 저장 위치 | `channel` 테이블 컬럼. 정책 테이블을 따로 만들 만큼 규칙이 많지 않다 |

구현 시점에 이 절만 보고 만들 수 있어야 하며, 설계가 바뀌면 이 절을 먼저 고친다.
