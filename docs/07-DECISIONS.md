# 07. 결정 기록

설계 판단을 여기 모은다. **"왜 이렇게 되어 있지?"** 라는 질문의 답은 이 문서에 있다.

각 항목은 `결정 / 버린 것 / 근거 / 재검토 조건` 으로 쓴다. 재검토 조건이 중요하다 — 지금 옳은 결정이 영원히 옳은 것은 아니고, 어떤 조건이 바뀌면 다시 볼지 적어두지 않으면 아무도 다시 보지 않는다.

**설계를 바꿨으면 항목을 추가한다.** 기존 항목을 지우지 않고 `대체됨` 으로 표시한다.

---

## 001. Java 25 + Spring Boot 4.x + Gradle

**버린 것** — Maven, Kotlin

**근거**

외주 납품물이고 개발자 1인이 장기간 단독 유지보수한다. 이 조건에서는 3년 뒤에 열어봐도 즉시 이해되는 스택이 가장 큰 가치다. 주력 언어라 컨텍스트 전환 비용이 없고 레퍼런스도 두텁다.

Kotlin 은 채널 어댑터의 JSON 파싱에서 null 안정성 이점이 있으나, 회사 주력 언어와 달라 오가는 비용이 생긴다.

Gradle 을 택한 이유는 내부망 제약(배포판·플러그인 포털 차단)이 **빌드 환경의 문제**이지 도구 선택의 근거가 아니기 때문이다. 제약은 CI 로 해소하고 도구는 요건으로 판단한다.

**재검토 조건** — Lombok 이 특정 JDK 를 지원하지 않아 발목을 잡으면 Java 21 LTS 로 내린다. `record`·`sealed`·pattern matching 은 21 에 모두 있어 코드 스타일은 바뀌지 않는다.

## 002. 도메인 축 멀티모듈 10개

**버린 것** — 기술 계층 축(`domain` / `collector` / `notifier` / `web` / `app`)

**근거**

도메인 모듈은 자기 도메인만 알고, 여러 도메인을 관통하는 책임은 조율 계층이 갖는다.

기술 계층으로 나누면 `palim-domain` 한 모듈에 모든 엔티티가 모여 경계가 없어진다. 도메인 축으로 나누면 `palim-sku` 에 web 의존성을 주지 않는 것만으로 재고 도메인에서 `@Controller` 를 **쓸 수 없게** 만들 수 있다.

목적은 작은 jar 가 아니다 — `bootJar` 는 단일 파일이라 의존성 합집합을 포함하므로 크기는 줄지 않는다. **얻는 것은 실수할 수 없는 구조다.**

**재검토 조건** — 처리량이 늘어 발송 워커나 수집기를 별도 프로세스로 분리할 때. 경계가 이미 있어 파일 이동 수준의 작업이 된다.

## 003. UUIDv7 기본키, 애플리케이션에서 생성

**버린 것** — UUIDv4, DB 시퀀스, `@GeneratedValue`

**근거**

랜덤 UUIDv4 는 B-tree 삽입 위치가 무작위여서 페이지 분할·WAL 증가·캐시 미스가 누적된다. UUIDv7 은 상위 48비트가 밀리초 타임스탬프라 시간순 정렬된다.

애플리케이션에서 생성하는 이유는 **저장 전에 식별자가 확정되어야** 로그·알림·Outbox 에 즉시 쓸 수 있고, 도메인 모듈 간 참조를 값으로 표현할 수 있기 때문이다. 시퀀스라면 002 의 모듈 격리가 훨씬 번거로워진다.

**딸려오는 필수 조건** — `@Version Long version`(wrapper). 없으면 `save()` 가 기존 엔티티로 오판해 INSERT 마다 SELECT 가 선행된다.

## 004. 전 계층 `Instant` / `timestamptz`

**버린 것** — `LocalDateTime`

**근거**

채널 API 가 KST 와 UTC 를 섞어 응답한다. 타임존 모호성이 유입되면 중복 판정과 수집 커서 계산이 어긋나고, **그것이 곧 재고 이중 차감이다.**

예외는 하루 중 시점을 표현하는 값(`quietHours`, `dailyReportTime`)이며 `LocalTime` 을 쓴다.

## 005. 비관적 락 + `MANDATORY` 전파

**버린 것** — 낙관적 락 + 재시도, 애너테이션 생략

**근거**

낙관적 락 + 재시도는 **재시도 로직의 결함이 곧 이중 차감**이다. 일 주문 수십 건 규모에서는 경합이 사실상 없어 비관적 락 비용이 무시할 수준이고 흐름이 단순해진다.

`MANDATORY` 를 쓰는 이유는 별개다. 애너테이션을 그냥 생략하면 호출자가 트랜잭션을 잊었을 때 **재고 변경과 이력 기록이 각각 커밋**되어 중간 실패 시 정합성이 깨진 채 조용히 넘어간다. MANDATORY 는 그 실수를 즉시 예외로 드러낸다.

**재검토 조건** — 동시 주문이 초당 단위로 들어오면 락 경합을 측정해 다시 본다.

## 006. 오버셀링 시 음수 재고를 허용한다

**버린 것** — 주문 저장 실패, 재고 미반영

**근거**

채널 재고 동기화는 수 분 내 반영이라 그 사이 실재고 초과 주문이 들어온다. 선택지가 셋인데 나머지 둘이 더 나쁘다.

| 선택지 | 결과 |
|---|---|
| 주문 저장 실패 | **데이터 유실.** 고객은 이미 결제했고 채널에 주문이 존재한다 |
| 재고 미반영 | `stock_applied = false` 로 남아 소급 반영 대상으로 **무한 재시도** |
| 음수 허용 | 사실을 정확히 표현하고 대조 배치가 계속 성립 |

재고 시스템에서 음수는 "출고해야 할 빚"이다. 화면과 알림으로 즉시 인지되고, 이력 누적합과 스냅샷이 여전히 일치하므로 대조 검증이 거짓 경고를 내지 않는다.

**판매 차감만 허용한다.** 폐기·분실은 사람의 입력 실수 가능성이 높아 계속 거부한다.

> 기능 명세서에 규정되지 않은 영역이라 구현 단계에서 정했다. 발주자에게 알릴 사항이며, 화면에 음수 재고를 명확히 표시해야 한다.

## 007. 메시지 큐 미사용, Outbox 단독

**버린 것** — RabbitMQ

**근거**

초기 설계는 `Outbox → relay → RabbitMQ → 워커` 였으나 구현 단계에서 철회했다.

| RabbitMQ 가 주는 것 | 현 상황 |
|---|---|
| 발송 워커 프로세스 분리 | 단일 배포(NAS 1대, JVM 1개)라 무의미 |
| 부하 분산 | 일 주문 수십 건이라 무의미 |
| 재시도·실패 격리 | Outbox 가 `attemptCount` 로 이미 관리 |

**결정적인 문제는 재시도 근거가 두 곳으로 갈린다는 점이다.** relay 가 발행한 뒤 Outbox 를 `PENDING` 으로 두면 같은 알림을 반복 발행하고, `SENT` 로 바꾸면 발송 실패를 Outbox 가 알지 못한다. 어느 쪽이 진실인지 알 수 없게 된다.

미사용 의존성(`spring-boot-starter-amqp`)도 제거했다. 컨텍스트에 불필요한 자동 구성을 붙인다.

**인수조건 A-14 는 그대로 충족된다.** 유실 방지의 실제 근거가 Outbox 이며, relay 가 기동 시 1회 실행되어 재기동 전 알림을 이어서 발송한다.

**재검토 조건** — 발송 워커를 별도 프로세스로 분리하거나 처리량이 늘어날 때. 그 시점에 발송 인터페이스를 추출하면 되고 기계적인 리팩터링이다. **구현체가 하나뿐인 인터페이스를 미리 만들지 않는다.**

## 008. `ErrorCode` 단일 enum

**버린 것** — 도메인별 `ErrorCode` 인터페이스 구현체 7개

**근거**

처음에는 인터페이스로 두고 도메인별 구현체를 만들었다. "새 도메인 추가 시 공통 파일을 고치지 않는다"는 이유였는데 **확장 비용이 오히려 컸다.**

| | 구현체 분리 | 단일 enum |
|---|---|---|
| 새 코드 추가 | enum 파일 + 메시지 2개 + **검증 테스트 수동 등록** + basename | enum 1줄 + 메시지 2줄 |
| 중복 검사 | 전체를 볼 수 없어 테스트에만 의존 | `values()` 자동 순회 |
| 보일러플레이트 | enum 마다 오버라이드 3개 | 없음 |

**실제로 구현체를 분리한 상태에서 `SKU_ID_REQUIRED` 가 두 enum 에 중복 정의됐고**, 파일이 나뉘어 있어 작성 중에는 드러나지 않았다. 검증 테스트에 클래스를 손으로 등록하는 구조라 빠뜨리면 검증 자체가 무력화된다.

"공통 모듈이 도메인 상수를 안다"는 우려는 실체가 없다. **상수 이름이 있을 뿐 의존 방향은 변하지 않는다.**

**재검토 조건** — 코드가 200개를 넘어 한 파일로 관리하기 어려워질 때. 그때는 접두사별로 쪼개면 되고, 검증 테스트를 자동 순회에서 수동 등록으로 바꾸는 대가를 감수해야 한다.

## 009. Thymeleaf + Tailwind CSS 4 / daisyUI 5

**버린 것** — React SPA 분리, Next.js, 커스텀 CSS

**근거**

화면이 7개이고 사용자가 관리자 1명이다. SPA 를 분리하면 인증 처리·빌드 파이프라인·CORS 관리가 추가되지만 얻는 것이 없다. 로그인 뒤에만 있는 내부 도구라 SEO 도 무의미하다.

daisyUI 컴포넌트를 그대로 쓰고 커스텀 CSS 를 만들지 않는다. 관리자 1명이 쓰는 내부 도구에 디자인 시스템을 자체 구축할 이유가 없고, 커스텀 CSS 를 쌓으면 유지보수 대상만 늘어난다.

정적 자원은 빌드 산출물을 jar 에 포함한다. CDN 을 쓰면 콘텐츠 보안 정책에 외부 도메인을 열어야 하고 외부 장애가 화면 장애가 된다.

## 010. 소프트 삭제 전역 적용 금지

**버린 것** — `BaseTimeEntity` 에 `@SQLRestriction` 전역 적용

**근거**

이 도메인에는 삭제 개념이 거의 없다. 주문은 상태 전이로, SKU 단종은 `active` 플래그로 처리하며 이력은 감사 기록이라 삭제가 금지다.

전역 필터를 걸면 **미매핑 주문 소급 반영에서 대상 행이 조용히 제외되고**, 필터링된 사실을 인지할 방법이 없어 재고가 무증상으로 틀어진다.

개별 적용 시 유니크 제약과 충돌하므로 PostgreSQL 부분 인덱스로 해소한다. `@Where` 는 Hibernate 6.3 에서 deprecated 이므로 `@SQLRestriction` 을 쓴다.

## 011. 발송 실패를 결과 객체로 표현

**버린 것** — 예외

**근거**

```java
public record TelegramSendResult(boolean success, boolean retryable, String errorMessage)
```

네트워크는 끊기고 외부 API 는 느려진다. 그때마다 예외를 던져 스택 트레이스를 남기는 것은 과하다.

더 중요한 것은 **`retryable` 을 호출자가 반드시 확인하게 만드는 것**이다. 예외로 표현하면 이 구분이 예외 타입이나 메시지 문자열에 묻힌다. 4xx(잘못된 chat_id·봇 차단)는 재시도해도 성공하지 않아 호출 제한만 소모한다.

## 012. 초기 재고를 이력으로 남긴다

**버린 것** — 스냅샷만 기록

**근거**

대조 배치는 `SUM(stock_movement.delta) == sku.quantity` 를 검산한다. `Sku.register` 가 초기 수량을 받는데 대응 이력이 없으면 **누적합이 항상 그만큼 적게 나와 정상 상태를 매번 불일치로 오판한다.**

실사 조정도 같은 이유로 `delta` 에 변경 전후의 **차이**를 넣는다. 절대값을 넣으면 누적합이 어긋난다.

> 엔티티와 스키마를 정의하는 단계에서 통합 테스트를 쓰다가 발견했다. 테스트 없이 넘어갔다면 대조 배치를 만든 시점에 거짓 경고가 쏟아졌을 것이다.

## 013. 부트스트랩을 도메인 모듈이 소유

**버린 것** — `palim-app` 에 통합 초기화

**근거**

`palim-app` 은 도메인 모듈을 `implementation` 으로만 의존하므로 서비스를 직접 볼 수 없다. 여기에 의존을 추가하면 002 의 모듈 격리가 무너진다.

`ApplicationRunner` 를 쓰는 이유는 별개다. `ApplicationReadyEvent` 리스너에서 던진 예외는 로그만 남고 애플리케이션이 계속 떠서, **설정이 없는 상태로 운영에 들어갈 수 있다.**

## 014. 채널 인증정보를 DB 에 저장하고 앱에서 암호화

**버린 것** — 환경변수·설정 파일 단독

**근거**

기능 명세서 F-09 가 "채널별 API 인증정보 등록" 화면을 요구한다. 환경변수 단독이면 발주자가 키를 갱신할 때마다 개발자가 서버에 접속해 재배포해야 한다.

AES-GCM 을 쓴다. 인증 태그가 포함되어 암호문 변조가 감지되므로, DB 유출 후 값이 조작되는 상황도 드러난다. **nonce 는 암호화마다 새로 생성한다** — GCM 에서 같은 키로 nonce 를 재사용하면 평문 복원이 가능한 치명적 취약점이 생긴다.

마스터키가 없으면 기동을 실패시킨다. 암호화 없이 인증정보를 저장하는 상태로 뜨는 것보다 안전하다.

로컬 프로파일에도 개발용 기본값을 두지 않는다. 설정 파일에 남아 있으면 실수로 운영에 흘러들 수 있다.

## 015. 감시 배치를 별 모듈 `palim-monitor` 로 분리

**버린 것** — `palim-collector` 에 배치 추가

**근거**

| 계층 | 책임 | 방향 | 실패 시 |
|---|---|---|---|
| `palim-collector` | 채널 주문을 내부 상태에 반영 | 외부 → 내부 | 커서를 되돌려 재시도 |
| `palim-monitor` | 내부 상태를 점검해 알림 | 내부 → 알림 | 다음 주기에 다시 본다 |

**수집기가 일일 리포트를 만드는 구조는 이름과 책임이 어긋난다.** 둘은 방향이 반대이고 실패 대응도 다르다 — 수집 실패는 커서를 되돌려야 주문이 유실되지 않지만, 감시 실패는 다음 주기에 다시 보면 된다.

모듈이 11개가 되지만 002 의 도메인 축 원칙과 일관되며 경계가 명확해진다.

**재검토 조건** — 조율 계층이 더 늘어나 관리가 번거로워질 때. 그때는 `palim-orchestration` 하나로 합치고 패키지로 나누는 방안을 본다.

## 016. 재알림 억제를 Outbox 의 `dedupeKey` 로 처리

**버린 것** — `Sku` 에 마지막 알림 시각 필드 추가, 별도 억제 테이블

**근거**

감시 배치는 주기적으로 **같은 상태를 반복 발견한다.** 재고 부족은 입고될 때까지 계속 부족하므로, 매 주기(30분)마다 알림을 등록하면 같은 메시지가 반복되고 **발주자가 알림을 아예 보지 않게 된다.** 그러면 이 시스템의 존재 이유가 무너진다. F-05 가 "반복 알림 주기"를 설정 항목으로 둔 이유다.

마지막 발송 시각을 어디서 추적할지가 문제였다.

| 방안 | 문제 |
|---|---|
| `Sku.lastLowStockAlertedAt` | 알림 관심사가 재고 도메인에 들어온다 |
| 별도 억제 테이블 | 모듈 소속이 애매하고 Outbox 와 정보가 중복된다 |
| **Outbox `dedupeKey`** | Outbox 가 이미 알림 이력이라 추가 저장소가 없다 |

키 형식은 `{알림종류}:{대상식별자}` 다.

```
LOW_STOCK:SKU-001
STOCK_MISMATCH:SKU-001
DAILY_REPORT:2026-07-29
```

**발송 성공 여부가 아니라 등록 시각을 기준으로 판단한다.** 발송이 실패해 재시도 중인 알림이 있는데 또 등록하면 중복이 쌓인다.

일일 리포트 중복 발송 방지에도 같은 메커니즘을 쓴다. 발송 시각이 설정값이라 cron 을 쓸 수 없고 주기 확인 방식이어서, 시각이 지나면 **매 주기마다 조건을 만족**한다. 키에 대상 날짜를 넣어 하루 한 번만 나가게 한다.

## 017. 일일 리포트 수치를 SQL 로 산출

**버린 것** — 애플리케이션에서 조회 후 조합, 언어 모델 계산

**근거**

주문·SKU·채널을 함께 집계해야 하는데 도메인 모듈이 분리되어 JPA 로 조인할 수 없다. 002 규칙 3에 따라 `JdbcClient` 로 직접 SQL 을 쓰고 결과를 `record` 로 받는다.

**이것이 F-10(AI 리포트 요약)의 전제다.** 언어 모델은 이미 확정된 수치를 문장으로 바꾸는 역할만 하며 계산하지 않는다. 언어 모델은 산술에서 오류를 내고, 재고·매출 수치가 잘못 전달되면 발주 판단에 직접적인 손실을 초래한다.

**날짜 경계는 KST 다.** 저장은 `timestamptz`(UTC)지만 발주자가 인지하는 "어제"는 KST 기준이다. UTC 자정으로 자르면 한국 시간 오전 9시까지의 주문이 전일로 집계되어 수치가 실제와 어긋난다.

판매 상위 SKU 집계에서 미매핑 항목은 제외한다. `sku_id` 가 null 이라 조인 대상이 없고 상품명을 알 수 없다. 미매핑 건수는 별도 항목으로 알린다.

## 018. 감사 로그를 DB 에 불변 기록으로 저장

**버린 것** — 파일 로그(레거시 관리자 시스템 방식), 감사 상세를 HTML 로 저장(레거시 관리자 시스템 방식)

**근거**

파일 로그는 화면에서 필터 검색할 수 없다. 발주자가 "지난주에 누가 재고를 바꿨나"를 보려면 서버에 접속해야 하는데, 그 능력을 전제할 수 없다.

변경 전/후 스냅샷은 JSON 으로 저장하고 렌더링 시 이스케이프한다. 레거시 관리자 시스템은 HTML 을 그대로 넣는데, 그 순간 DB 가 저장형 XSS 창고가 된다.

`audit_log` 에는 `updated_at` 도 수정 메서드도 없다. **고칠 수 있으면 감사 기능이 아니다.** `actor_id` 는 FK 가 아니다 — 계정을 지워도 기록은 남아야 하고, 없는 계정으로의 로그인 시도도 기록해야 한다.

조회(VIEW)까지 전부 기록하되, 화면 기본 필터는 인증+변경으로 둔다. 기록은 완전하게, 화면은 조용하게. 조회 기록은 비동기로 남긴다 — 화면 응답에서 감사 INSERT 지연을 제거하기 위해서이며, 인증·변경 기록은 유실 위험을 받아들일 수 없어 동기로 남긴다.

**재검토 조건** — 규제 감사 대상이 되면 "기록 실패 시 본 작업도 중단" 으로 바꿔야 한다. 현재는 기록 실패를 삼키고 본 작업을 살린다.

## 019. 동시 세션 제한을 Spring 에 맡기지 않고 확인 단계를 둔다

**버린 것** — `maximumSessions(1)` 자동 축출(기존 방식), 레거시 관리자 시스템의 인메모리 테이블 세션 보관 + 100ms 폴링

**근거**

`maximumSessions(1)` 은 기존 접속자에게 아무 것도 묻지 않고 세션을 끊는다. 그러면 발주자는 자기 계정이 다른 곳에서 쓰이고 있다는 사실을 알아챌 기회가 없다 — 계정 유출이 가장 먼저 드러나는 신호가 바로 이 상황이다.

새 로그인은 보류(`PendingLogin`)하고 확인 화면에서 기존 접속 IP 를 보여준 뒤 결정하게 한다. 보류 상태는 비밀번호도 `Authentication` 도 담지 않는다 — 검증은 끝났으므로 아이디만 들고 있다가 확인 시점에 계정을 다시 읽는다.

기존 세션 종료는 `SessionRegistry.expireNow()` 에 맡긴다. 레거시 구현처럼 남의 스레드의 세션을 직접 `invalidate()` 하면 경합이 생긴다. 즉시 통보는 SSE 가 담당하고, SSE 가 끊겨도 다음 요청에서 `ConcurrentSessionFilter` 가 만료를 적용하므로 기능은 성립한다. 레거시의 100ms 폴링은 초당 10회 요청에 더해 세션 유휴 타임아웃을 영원히 무력화하는 부작용이 있다.

## 020. 클라이언트 IP 는 ForwardedHeaderFilter 에 위임하고 기본은 신뢰하지 않는다

**버린 것** — `X-Forwarded-For` 직접 파싱, `getRemoteAddr()` 단독 사용(레거시 관리자 시스템 방식)

**근거**

`getRemoteAddr()` 만 쓰면 리버스 프록시 뒤에서 모든 감사 기록의 IP 가 프록시 주소로 찍힌다. 반대로 헤더를 무조건 신뢰하면 클라이언트가 IP 를 위조해 기록에 남긴다. **위조된 IP 는 IP 가 없는 것보다 나쁘다.**

해석은 `server.forward-headers-strategy=framework` 로 Spring 에 맡기고, 프록시가 확실한 운영 환경(Cloudflare Tunnel)에서만 켠다. 기본값은 꺼져 있어 위조가 불가능하다.

## 021. 레거시 관리자 시스템의 기능은 개념만 가져온다

**버린 것** — 결재(Decide) · 역할/권한 · 계정 유효기간 · 공지사항 · 모바일, 그리고 모든 로직 이식

**근거**

레거시 관리자 시스템은 다중 사용자 조직용이고 Palim 은 1인 발주자 운영이다. 조직용 개념은 전부 죽은 무게다. 가져온 것은 감사추적 · 세션 제한 · 수집 모니터(Task) · 알림 이력(Notice) · 인시던트 · 대시보드의 **개념**이며, 구현은 Palim 규모에 맞게 새로 한다. 순서와 근거는 [08-ROADMAP](08-ROADMAP.md).

## 022. 인시던트는 미해결 1행 누적, 수동 해결만 둔다 (#35)

**결정** — 오버셀 · 정합성 불일치 · 미매핑을 도메인 모듈 `palim-incident` 로 기록한다.
미해결(OPEN·ACKNOWLEDGED) 상태의 같은 문제는 부분 유니크 인덱스
(`dedupe_key WHERE status <> 'RESOLVED'`)로 1행을 강제하고 발생 횟수만 누적한다.
해결은 사람이 화면에서 한다. RESOLVED 후 재발은 새 인시던트다.

**버린 것**

| 대안 | 기각 이유 |
|---|---|
| 발생마다 새 행 | 정합성 불일치는 해결 전까지 매일 재감지된다 — 목록이 같은 문제로 도배되어 봐야 할 건이 묻힌다 |
| 자동 해결 (재검산 통과·매핑 등록 시) | 감시 배치·매핑 로직이 인시던트와 결합된다. 1인 운영에서 하루 몇 건 수준이라 수동으로 충분하다 |
| 수집 실패 인시던트 | 수집 모니터(#30)가 현재 상태를 이미 보여준다. 이력 관리 필요가 확인되면 그때 추가한다 |
| `palim-monitor` 소유 | collector(오버셀·미매핑)도 생성 주체다. 조율 계층은 서로 의존하지 않으므로 도메인 모듈로 내렸다 |

**근거**

텔레그램 알림은 도달하면 끝이라 "확인했는지, 조치했는지"가 남지 않는다. 알림 억제
(`enqueueIfNotRecent`)는 스팸 방지가 목적이라 발생 사실 자체를 지운다 — 인시던트는 억제와
무관하게 매 발생을 누적해 "며칠째, 몇 번째 지속 중인지"를 남긴다. `report()` 는 감지
지점의 트랜잭션에 참여(`MANDATORY`)하므로 수집이 롤백되면 유령 인시던트도 남지 않는다.

## 024. 런타임 설정 저장소(SystemConfig) 도입 (#41)

**결정** — 운영 중에 조정하는 값(스코어링 가중치·임계값·주기 등)을 배포 산출물(YAML)이 아니라
**DB `system_config` 테이블**에 두고 화면에서 편집한다. 코드의 `ConfigDefinition` 은 최초 1회
채워 넣는 기본값과 메타데이터(설명·범위·표시명)만 담당하며, **배포는 기존 값을 덮어쓰지 않는다.**

**버린 것**

| 대안 | 기각 이유 |
|---|---|
| `@ConfigurationProperties` + YAML 유지 | 부팅 시 한 번 바인딩이라 값을 바꾸려면 재배포·재기동이 필요하다. 캘리브레이션은 값을 계속 조정하는 작업이라 이 방식으로는 운영되지 않는다 |
| YAML 기본값 + DB 오버라이드 병행 | 기본값 원본이 두 곳이 된다. 어긋나면 테스트는 통과하는데 운영이 다르게 도는 유형의 사고가 나므로 `influencer-scoring.yml` 은 삭제했다 |
| 타입별 컬럼 분리(`int_value`·`text_value`…) | 새 타입마다 스키마가 늘고 읽는 쪽이 매번 분기한다. `jsonb` 한 컬럼 + `value_type` 힌트로 통일했다 — 힌트는 화면이 어떤 위젯을 그릴지 정하는 용도다 |
| 캐시 없이 매번 DB 조회 | 채널 한 건 채점에 임계값 수십 개를 읽는다. 배치가 설정 조회로 시간을 다 쓴다 |
| 설정 변경 이력 생략 | 점수 순위가 갑자기 달라졌을 때 원인을 추적할 단서가 사라진다. `system_config_history` 가 되돌리기의 근거이기도 하다 |

**근거**

확장 지점은 `ConfigDefinitionProvider` 다 — 모듈이 정의를 내놓으면 부팅 시 없는 키가 자동
등록되고 설정 화면에 자동으로 나타난다. 새 설정을 추가할 때 화면 코드도 마이그레이션도 건드리지
않는다.

읽는 쪽은 구현체가 아니라 `ConfigReader` 인터페이스에 의존한다. 덕분에 스코어링 단위 테스트가
DB 없이 같은 기본값으로 돌고, 테스트가 별도 기본값을 들고 있어 운영과 어긋나는 문제가 없다.

값 검증(min/max·타입)을 저장 시점에 하는 이유는 배점에 음수나 비정상 값이 들어가면 점수 체계가
통째로 무너지기 때문이다. 화면 입력 실수를 시스템 동작 오류로 만들지 않는다.

캐시는 인스턴스가 하나인 모놀리스라 성립한다. 다중 인스턴스로 가면 변경 전파가 필요해지며,
그때 바꿀 지점은 `reload()`/`evict()` 두 곳뿐이다.

## 025. 연동 정의 생성 시에는 원본 파일 전체를 AI 에 보낸다 (#53)

**결정** — 범용 데이터 연동 프레임워크에서 **매핑 초안을 만들 때만** 원본 파일 전체를 AI 에
보낸다. 반복 처리(리포트·분석·배치)는 종전대로 필요한 컬럼만 보내고 개인 식별자를 마스킹한다.
`CLAUDE.md` 6번을 이 내용으로 개정했다.

**버린 것**

| 대안 | 기각 이유 |
|---|---|
| 헤더만 전송 | 컬럼명만으로는 타입·포맷을 알 수 없다. `"2026-08-12"` 인지 `"20260812"` 인지, 수량에 천 단위 쉼표가 있는지가 매핑 정확도를 좌우한다 |
| 헤더 + 마스킹된 샘플 | 마스킹이 값의 모양을 지운다. 전화번호가 `010-****-****` 로 오면 포맷 추론이 불가능하고, 그 필드는 사람이 다시 지정해야 한다 |
| 매 실행마다 AI 호출 | 비용이 계속 들고 **같은 파일에 다른 결과가 나올 수 있다.** 재현되지 않는 파이프라인은 대사 결과를 신뢰할 수 없게 만든다 |

**근거**

노출 범위가 **최초 연동 설정 1회**로 한정된다. 확정된 정의로 도는 cron 실행에서는 데이터가 한
번도 외부로 나가지 않는다. 매일 도는 경로가 아니라 사람이 한 번 누르는 경로에만 열려 있다.

개인정보를 담는 표준 모델은 `std_outbound_order` 하나뿐이다(수령자 정보). 품목·재고·이동
모델에는 개인정보가 없어 대부분의 연동은 이 결정과 무관하다.

AI 가 만드는 것은 **선언적 매핑 정의**이고 확정은 사람이 한다. 코드를 만들어 실행하지 않으므로
프롬프트 인젝션이 동작으로 이어지지 않는다 — 최악의 경우 매핑 제안이 엉뚱해질 뿐이고, 그것은
관리자 확인 화면에서 걸러진다.

## 026. 연동 정의를 데이터로 둔다 (#53)

**결정** — 외부 원천을 표준 모델로 들이는 정의(원천·매핑·변환)를 코드가 아니라 **DB 행**으로
둔다. 새 원천이 붙어도 배포가 필요 없고, 양식이 바뀌면 매핑 버전을 올린다. 범용 엔진은
`palim-connector` 에 두고 도메인을 모르게 한다.

**버린 것**

| 대안 | 기각 이유 |
|---|---|
| 원천마다 Java 어댑터를 새로 작성 | 새 발주사·새 원천마다 배포가 필요하고, 파싱 코드와 도메인 로직이 뒤엉킨다 |
| 목표 모델도 런타임 DDL 로 생성 | Flyway 와 충돌하고 앱 계정에 DDL 권한이 필요해진다. 실패 시 롤백 경로가 없다. 기본 제공은 정식 테이블(`std_*`), 커스텀은 JSONB 로 갈랐다 |
| 후처리를 SQL 로 작성 | 공개 저장소이고 임의 SQL 은 한 번 뚫리면 DB 전체가 열린다. 선언적 규칙 + py 훅으로 대체했다 |
| TEST 실행도 표준 테이블에 적재 후 삭제 | UPSERT 로 덮어쓴 행은 소유 실행이 바뀌어 "그 실행분만 삭제"가 성립하지 않는다. 지우기 전에 도메인 로직이 읽으면 오염된 결과가 나온다. TEST 는 `connector_staging` 에만 쓴다 |
| 단위 환산 규칙이 없으면 무조건 실패 | 실측한 두 원천 모두 단위 컬럼이 없어 첫 적재부터 전부 막힌다. **단위가 명시됐는데** 규칙이 없을 때만 실패시킨다 |
| 원천 필드가 하나라도 다르면 중단 | 컬럼 추가만으로 업무가 멈추면 사람이 감지를 꺼버린다. 매핑에 실제로 쓰는 필드가 사라졌을 때만 막는다 |

**근거**

`std_` 접두사를 쓴 이유는 동결 도메인(`palim-sku`)에 이미 `stock_movement` 가 있어서다. 동시에
"표준 모델"이라는 성격이 이름에 드러난다.

자연키 기반 UPSERT 가 재시도 안전성의 전부다. 증분 수집은 **성공한 실행만** 커서를 전진시키고,
실패하면 같은 구간을 다시 읽는다 — 중복은 자연키가 흡수한다. 재시도가 안전해야 사람이 자동화를
켠다.

자연키는 길이 초과 시 절단이 아니라 **해시 축약**이다. 앞부분이 같은 서로 다른 행이 하나로
합쳐지면 UPSERT 가 남의 데이터를 덮어쓰고, 그것은 조용히 사라지는 유형의 사고다.

되돌리기는 **가장 최근 LIVE 실행 하나**로 제한한다. 그 이전까지 거슬러 오르면 이후 실행들과
뒤엉켜 어떤 상태로 돌아가는지 설명할 수 없다. 한 실행에 같은 자연키가 두 번 오면 첫 undo 만
남긴다(부분 유니크 인덱스 + `ON CONFLICT DO NOTHING`) — 두 번째는 이번 실행이 방금 쓴 값이라
복원이 중간 상태로 간다.

## 027. 재고 대조를 최상위 메뉴 그룹으로 올린다

2026-08 피벗(023)에서 **옛 재고 관리 도메인**(sku·order·collector·channel·mapping·incident)을
동결하고 내비게이션에서 제거했다. 이번에 올리는 「재고 맞추기」는 그것과 다른 것이다 — 동결한
것은 재고를 **관리**하던 화면이고, 이번 것은 두 원천의 재고를 **맞춰 보는** 새 모듈
(palim-reconcile)이다.

이름이 겹쳐 혼동될 수 있어 여기 적어 둔다. 동결 도메인 화면은 여전히 메뉴에 없고 코드도
수정하지 않는다.

## 028. 운영 로그를 파일로 남기고, 파일에는 가리지 않는다

**왜 파일이 필요한가** — 배포는 컨테이너를 지웠다 다시 만든다. 콘솔 로그만 있으면 그것은
`docker logs` 로만 볼 수 있고 **다음 배포에서 통째로 사라진다.** 정작 「어제 그 오류」를 봐야 할
때 아무것도 남아 있지 않다. 실제로 연동 실패 원인을 찾으려다 그 사이 배포가 두 번 나가 로그가
없어진 적이 있다.

호스트의 디렉터리를 컨테이너에 연결해 그 밖에 남긴다. 지난 파일은 gzip 으로 압축하고, 보관
기간과 **총 용량 상한**을 함께 건다 — 이 저장소는 다른 프로젝트 여럿과 같은 볼륨을 쓰므로,
로그가 디스크를 채우면 우리만 죽는 것이 아니다.

오류는 한 벌 더 따로 남긴다. 전체 로그에서 ERROR 를 찾으려면 DEBUG 수만 줄을 헤쳐야 하는데
급할 때는 그 시간이 없다.

**왜 파일은 가리지 않는가** — 콘솔은 비밀값을 가린다(09-SECURITY). 파일은 가리지 않는다.
파일은 운영 서버의 마운트된 디렉터리에만 남고 그 서버는 운영자만 접근한다. 문제가 났을 때
**무엇이 오갔는지 그대로** 봐야 원인을 찾을 수 있는데, 가려 두면 정작 필요한 순간에 `***` 만
보인다. 다만 인증키·비밀번호 **자체를 찍는 로그를 새로 만들지는 않는다** — 그것은 진단에
필요하지 않으면서 파일에는 영구히 남는다.

로그 디렉터리 경로는 **배포 Secret 으로만** 둔다. 저장소가 공개이므로 서버 경로를 파일에
적지 않는다(CI 가 검사한다).

## 029. 물류 원천은 파일을 내려받지 않고, 화면이 쓰는 조회 요청을 그대로 부른다

**바꾼 적이 있는데 적어 두지 않아 이 항목을 늦게 쓴다.** 처음에는 「사람이 화면에서 엑셀을
내려받아 올린다」로 잡았다가, 화면을 긁는 방식이 무겁고 잘 깨진다는 이유로 **화면이 부르는
조회 요청을 직접 부르는 쪽으로 바꿨다.** 그 전환을 결정 기록으로 남기지 않아, 나중에 「파일로
받기로 하지 않았나」와 코드가 어긋나 보였다. 판단이 바뀌면 여기 적는다는 규칙이 이래서 있다.

**지금 방식이 맞는 이유** — 실제로 받아 보니 조회 응답에 필요한 값이 다 들어 있다. 품목코드·
품명·정상재고가 순수 문자열로 온다. 파일을 내려받는 경로는 요청 형식을 따로 알아내야 하고,
받은 파일의 칸 구조는 화면과 또 다르다. 이미 되는 길을 두고 모르는 길을 열 이유가 없다.

**대신 이 방식은 상대 화면이 바뀌면 깨진다.** 그래서 실패를 조용히 삼키지 않는다.

### 로그인이 평범하지 않다

입력값을 그대로 보내는 것이 아니라, 로그인 화면에 실려 오는 **공개키로 폼 전체를 암호화해**
한 칸에 담아 별도 주소로 보낸다. 평범한 폼 전송으로는 상대가 **200 과 함께** 「연결에
실패하였습니다」 를 돌려주고 세션을 주지 않는다. 상태 코드가 정상이라 실패로 보이지도 않고,
화면만 봐서는 계정을 의심하게 된다.

공개키는 **코드에 박지 않고 로그인 화면에서 읽는다.** 박아 두면 상대가 키를 바꾼 날 로그인만
조용히 실패하고, 원인은 「계정이 잘못됐나」부터 뒤지게 된다.

키 크기가 곧 평문 한도다(1024비트면 117바이트). 빈 칸까지 실으면 한도를 넘겨 암호화 자체가
실패하므로 **빈 값은 빼고** 보낸다.

## 030. 검증 화면과 수집 코드가 절차를 각자 갖지 않는다

연결 테스트(`FormSessionProbe`)와 실제 수집(`FormSessionClient`)이 같은 절차를 **따로**
구현하고 있었다. 그러다 한쪽만 고쳐졌다.

그리드 응답은 값이 한 겹 더 들어가 있고(`{"id":0,"cell":{…}}`) 숫자에도 HTML 태그가 섞여 온다.
검증 화면은 그것을 벗겼고, 수집 코드는 벗기지 않았다. 결과가 이렇다.

| | 검증 화면 | 실제 적재 |
|---|---|---|
| 보이는 것 | 칸 23개, 값이 깔끔 | 칸 2개(`id`·`cell`), 값은 통째로 한 덩어리 |
| 상태 | 성공 | **성공** |

**틀린 값이 들어가는데 어디에도 실패가 남지 않는다.** 사람은 화면에서 칸이 예쁘게 보이는 것을
보고 넘어가고, 며칠 뒤 대조 결과가 이상할 때에야 안다.

절차는 `FormSessionClient` **한 곳에만** 둔다. 검증 화면은 그것을 부르고, **어느 단계에서
막혔는지 기록하는 일만** 한다. 같은 절차를 두 곳에 두면 반드시 다시 갈라진다.

## 031. 화면 안에 스크립트를 박지 않는다 — 서버가 전부 그린다

이 서비스는 스크립트와 스타일을 **자기 도메인 파일로만** 제한한다(009). 그래서 태그 안에 직접
적은 코드는 브라우저가 **실행하지 않는다.**

문제는 **아무 티가 안 난다**는 것이다. 화면은 200 으로 멀쩡히 열리고 드롭다운도 보인다. 다만
바꿔도 아무 일이 일어나지 않는다. 두 곳이 그 상태로 배포돼 있었다.

| 화면 | 증상 |
|---|---|
| 연결 | 시스템을 바꿔도 문구가 하나도 안 바뀐다 — 물류를 골라도 「API 인증키」를 넣으라고 한다 |
| 등급표·트렌드 | 필터를 골라도 조회되지 않는다 |

**정책은 바꾸지 않는다.** 값을 하나 풀어 주면 그 뒤로 계속 풀게 되고, 이 정책이 막는 것은
「남의 스크립트가 우리 화면에서 도는 일」이다.

**대신 화면을 서버가 전부 그린다.** 고른 값은 주소로 받아 다시 그린다. 화면 절반은 서버가
그리고 절반은 스크립트가 고치는 구조는, 스크립트가 막히는 순간 **둘이 어긋난 채 멀쩡해
보인다.** 서버가 다 그리면 어긋날 곳이 없다.

동작이 꼭 필요하면 `/js` 아래 **파일로** 둔다. 태그에는 표시만 남긴다(`data-auto-submit`).
스크립트가 죽어도 길이 남도록 대체 버튼을 함께 둔다 — 고를 수는 있는데 반영할 방법이 없는
상태를 만들지 않는다.

**렌더 테스트가 이것을 검사한다.** 「열린다」와 「동작한다」는 다르고, 지금까지는 그 차이를
사람 눈으로만 찾을 수 있었다.

## 032. 사용자 자료는 담을 때 다듬고, 화면은 그대로 보여준다

품목코드 `00094` 가 화면에서 `94` 로 보였다. 담긴 값은 멀쩡한데 **화면이 숫자처럼 생긴 글자를
숫자로 다듬었다.** 「진짜로 넣기 전에 눈으로 보는」 화면에서 이러면 확인이 거짓이 된다.

시각도 같은 문제였다. JSON 은 시각을 모르므로 `Instant` 를 그냥 넣으면 「1970년부터 몇 초」
라는 숫자로 굳는다(`1786719600`). 화면이 그것을 되돌리려면 **어느 칸이 시각인지 화면이
알아야** 하고, 판단이 두 군데로 갈린다.

**담을 때 굳힌다.** 스테이징에 넣기 전에 시각을 사람이 읽는 글자로 바꾼다. 그러면 화면은
받은 값을 그대로 보여주기만 하면 되고, 판단이 한 곳에만 있다.

화면에 허용되는 것은 **값을 바꾸지 않는 처리**뿐이다 — 접기·자르기·정렬. 자릿수 구분 기호,
앞자리 0 제거, 소수점 절삭은 모두 값을 바꾸는 일이라 하지 않는다(11-UI-RULES).

**이 결정의 진짜 내용은 「누가 정하는가」다.** 값의 뜻과 표시 방법은 코드가 짐작할 일이 아니다.
짐작이 필요해지면 그것은 설계가 덜 된 신호다.

## 033. 기준 시각의 눈금을 연동마다 고르고, 대조는 자기 눈금을 따로 갖는다

담긴 재고는 `(원천, 기준 시각, 품목, 창고, 로트)` 로 구분된다. 그런데 기준 시각을 **늘 그날
0시로 내리고 있었다.** 그래서 하루에 두 번 담으면 둘이 같은 칸을 차지해 **나중 것이 앞엣것을
덮었다** — 오전 재고를 다시 볼 방법이 없고, 덮였다는 사실조차 남지 않는다. 지금은 수집이
하루 한 번뿐이라 드러나지 않지만, 더 자주 돌리는 순간 조용히 자료가 사라진다.

하나로 고정할 수는 없다. 원천마다 실제 해상도가 다르다 — 전산은 기준일을 **날짜로만** 받고,
물류는 「지금 재고」 를 준다. 잘게 두면 날짜만 주는 원천이 같은 자료를 시각만 다른 여러 벌로
쌓고, 굵게 두면 촘촘히 주는 원천이 서로를 덮는다. 그래서 **연동마다 고른다.**

**대조는 자기 눈금을 따로 갖는다.** 담는 눈금과 견주는 눈금은 다른 값이다 — 앞은 「얼마나
촘촘히 남길 것인가」, 뒤는 「얼마나 굵게 맞춰 볼 것인가」다. 물류를 한 시간마다 담아도 전산이
하루 한 번이면 견주기는 하루로 해야 두 원천이 같은 칸에 들어온다.

두 값을 한 곳에 몰지 않은 이유가 하나 더 있다. **대조가 연동을 알면 도메인끼리 의존이
생긴다**(02-ARCHITECTURE 「도메인 모듈끼리 직접 의존하지 않는다」). 눈금을 읽으려고 커넥터를
뒤지는 순간 그 규칙이 깨진다. 눈금 자체는 두 도메인이 같은 뜻으로 써야 하므로 `palim-common`
에 둔다.

**견줄 눈금이 담는 눈금보다 잘면 저장을 막는다.** 하루에 한 번 담는 원천은 늘 자정에 찍히므로
시간 단위로 견주면 상대가 그 칸에 있을 수 없다. 막지 않으면 대조는 매일 「기준 시각이
다릅니다」 만 남기고, 설정도 실행도 정상이라 **화면 어디에도 원인이 없다.**

「하루」 를 가르는 지역은 눈금 안에 못박는다. 실행 환경의 기본 지역을 쓰면 CI 는 UTC, 운영은
서울이라 **같은 코드가 다른 뜻**이 된다 — 테스트는 통과하는데 운영에서만 어긋난다.

## 034. 품목 잇기는 대조표 한 장이고, 「보고 누른 것」 이 곧 확인이다

품목 잇기 화면이 셋으로 쪼개져 있었다. 「이을 만한 것」 은 좌·우를 **한 칸에 세로로 쌓아**
무엇이 무엇과 짝인지 볼 수 없었고, 「직접 골라서 잇기」 는 좌·우 목록이 서로 무관하게 놓여
**견줄 수가 없었으며**, 「정해 둔 품목」 은 코드와 이름만 보여줘 방금 무슨 일이 일어났는지
알 수 없었다. 대조를 하러 온 사람에게 대조할 수 없는 화면을 준 것이다.

이제 **한 줄이 물건 하나**다. 물건 이름·왼쪽 품목·오른쪽 품목·수량 차이가 나란히 있다.
줄이 만들어지는 근거는 셋뿐이고 순서대로 본다: ①이미 이어 둔 것이면 그 물건 단위로,
②짝 없음으로 표시해 둔 것이면 품목 하나가 한 줄로, ③나머지는 다듬은 이름이 같은 것끼리.
**사람이 정한 것이 규칙보다 앞선다** — 반대로 하면 규칙 한 줄을 고칠 때마다 이미 정해 둔
것이 흩어진다.

**확인 단계를 없앴다.** 확인이 따로 필요했던 것은 화면이 좌·우를 나란히 못 보여주던 때다.
「erp · A0001 · 1」 만 보고는 맞다/아니다를 판단할 수 없으니 한 단계를 더 둔 것인데, 지금은
누르기 전에 그 줄에서 좌·우 품명과 수량 차이가 다 보인다. **보고 누른 것이 곧 확인이다.**
잘못 이었을 때의 안전망은 확인 단계가 아니라 **모든 줄에 있는 「풀기」** 다.

**차이를 잇기 버튼 옆에 둔다.** 없으면 사람이 여러 줄을 눈으로 더해야 하고, 결국 잇고 나서
대조를 돌려야 처음 보인다 — 그때는 이미 늦다. 절대값과 함께 백분율도 적는다. 9,563 중 112 와
5 중 112 는 전혀 다른 이야기다.

**한쪽에만 있는 줄은 잇지 못하게 막는다.** 이으면 합산이 「좌 120 · 우 0」 이 되어 대조가 매일
전량 차이를 올리는데, 사람은 그것을 매칭 문제가 아니라 **재고 사고로 읽는다.** 그 줄의 제 자리는
「짝 없음으로 두기」 다.

## 035. 「짝 없음」 을 표시로 남긴다 — 할 일 개수가 0에 닿아야 하기 때문이다

한쪽에만 있는 품목은 **언제나 남는다.** 단종됐거나, 이쪽 시스템만 쓰는 부자재이거나, 이번
대조 범위 밖이다. 그것들이 계속 「짝을 못 찾은 것 9건」 으로 떠 있으면 사람은 다 했는지 아닌지를
알 수 없고, 결국 그 숫자를 안 보게 된다. **안 보는 숫자는 없는 것과 같다.**

지우지 않고 표시만 하는 이유는 되돌릴 수 있어야 하기 때문이다. 단종인 줄 알았는데 다시 들어오는
일이 실제로 일어난다. 원본 재고 자료를 건드리지 않으므로 재고를 다시 담아도 표시는 남는다.

홈의 「품목 맞추기」 단계도 이 숫자를 쓴다. 예전에는 **하나만 이어 두어도 완료**였다 — 홈이
완료라고 하는데 품목 잇기 화면에는 할 일이 스물두 건 남아 있는, 같은 사실에 대해 두 화면이
반대로 말하는 상태였다.

## 036. 이름 다듬기 규칙에 화면을 준다 — 없으면 이 프로그램은 한 회사에서만 돈다

규칙이 DB 에만 있었다. 표기 습관은 회사마다 다른데 — 어디는 「/」 로 규격을 나누고 어디는
「[2026-10-17]」 로 유통기한을 붙인다 — 자기 습관에 맞는 규칙을 넣을 자리가 없으면 다른 곳에
가져다 놓는 순간 「이을 수 있는 것」 이 늘 비어 있게 되고, 품목을 전부 손으로 이어야 한다.

**저장 전에 걸어 볼 수 있어야 한다.** 잘못 고쳤을 때 눈에 보이는 것은 「이을 수 있는 것이
줄었다」 뿐이고 왜인지는 어디에도 안 나온다. 걸어 보는 표본은 **지금 담긴 실제 품명**이다 —
지어낸 이름으로는 「잘 되는 것처럼」 보이고 끝난다.

미리보기는 **딴 스레드에서 제한 시간을 걸고** 돈다. 사람이 정규식을 직접 넣는 화면인데
**톰캣은 이미 돌고 있는 요청 스레드를 죽이지 않는다** — 브라우저가 기다리다 포기해도 그
스레드는 계속 돈다. 몇 번 반복하면 스레드 풀이 마르고 서버 전체가 응답을 멈춘다. 자바의
`Matcher` 는 인터럽트를 보지 않으므로 **입력을 감싸** 글자를 내줄 때마다 확인하게 만들어야
취소가 실제로 먹는다.

> 자바 21 의 정규식 엔진은 `(a+)+$` 같은 고전적 폭주 패턴을 최적화로 흘려보낸다. 입력 길이를
> 300자로 자르는 것과 합쳐, **오늘의** 엔진에서는 폭주를 재현하지 못했다. 그래도 장치를 두는
> 이유는 그것이 **엔진 구현의 성질이지 보장이 아니기** 때문이다. 시험은 폭주 대신 표본을 늘려
> 「오래 걸리면 요청 스레드가 풀려나는가」 를 확인한다.

## 037. 매칭 후보의 순서만 유사도로 정한다 — 판단은 대신하지 않는다

자동 후보는 다듬은 이름이 **정확히** 같아야 잡힌다. 그래서 「초콜릿 프로틴바」 와 「초콜렛
프로틴바」 는 사람 눈에 명백히 같은데도 영영 안 만난다. 그런 품목이 수십 개면 목록을 처음부터
끝까지 눈으로 훑어야 하고, 그게 이 화면에서 제일 지치는 일이다.

그래서 줄 안에서 짝을 고를 때 **반대쪽 목록을 닮은 순서로 늘어놓는다**(글자 두 개씩 잘라
겹치는 비율). **점수로 확정하지 않는다.** 점수가 판단을 대신하면 규칙이 틀렸을 때 엉뚱한 품목을
합쳐 놓고 「재고가 맞는다」 고 보고하게 되는데, 그건 못 찾는 것보다 나쁘다 — 틀렸다는 사실조차
드러나지 않는다.

## 038. 대조 결과는 이름으로 부르고, 합계 뒤를 뜯어볼 수 있어야 한다

결과 화면이 「U-6668d23b · 전산 318 · 물류 307 · +11」 이라고만 말했다. 두 가지가 잘못돼 있었다.

**이름 자리에 코드가 나왔다.** 이름은 물건에 이미 있었는데 화면이 코드를 그리고 있었다. 무슨
물건인지 모르는 줄은 손대지 않게 되고, 손대지 않는 줄이 쌓이면 화면 전체를 안 보게 된다.

**그 이름조차 틀렸다.** 여럿을 묶을 때 **첫 품목의 이름을 그대로** 물건 이름으로 썼다. 그래서
로트 넷을 묶은 물건이 「클래식 850g (27.03.16)」 이 되었다 — **특정 로트 날짜가 전체를 대표**하게
된 것이다. 이제 여럿이면 이름들의 **공통 부분**만 쓴다. 지어내는 것이 아니라 담긴 자료에 실제로
있는 글자에서 잘라 내는 것이고, **사람이 언제든 고칠 수 있다.** 이미 만들어진 것은 옛 이름을 그대로
달고 있으므로 「담긴 품명으로 다시 짓기」 를 둔다 — 다만 **일괄로 덮지 않고 고른 것만** 바꾼다.
사람이 직접 지은 이름을 코드가 말없이 되돌리면 다음부터는 이름을 짓지 않는다.

**합계 하나로는 무슨 일인지 알 수 없다.** 위 +11 의 정체는 「재고가 11개 빈다」 가 아니라
**「물류가 오래된 로트 3종을 이미 0으로 털었고 최신 로트는 정확히 맞는다」** 였다. 전혀 다른
이야기이고 할 일도 다르다. 그래서 줄을 펼치면 그 물건에 든 품목을 **좌·우로 나란히** 놓는다.

짝은 **원본 품명**으로 짓는다. 다듬은 이름을 쓰면 날짜가 떨어져 한 물건 안의 모든 로트가 같은
이름이 되어 짝을 가릴 수 없다. 점수가 높은 쌍부터 맺고, 사람이 이미 「같은 물건」 이라고 정해 둔
것들이므로 **맺을 수 있는 만큼 다 맺는다.** 한쪽이 남으면 그 줄이 대개 **잘못 이어 둔 품목**이다 —
실제로 「오가닉 425g」 에 다른 로트(26.05.05)가 섞여 있는 것이 이 방식으로 드러났다.

**「몇 개가 합쳐진 값인가」 를 배지로 말한다.** 「4↔4건」 과 「1↔2건」 은 전혀 다른 상태인데
합계만 보면 둘 다 그냥 숫자 하나다. 좌·우 개수가 어긋나면 그것만으로 경고다.

**뜯어보기는 「지켜볼 것」 에도 있다.** 확정될 때까지 기다려야 속을 볼 수 있다면, 정작 원인을
일찍 잡을 기회를 놓친다.

## 039. 회차마다 원천별 기준 시각을 남긴다

실행에 남는 것은 두 원천이 공유하는 **칸** 시각뿐이었다. 그런데 합산은 원천마다 자기 시각으로
한다 — 한쪽은 자정, 한쪽은 그날 오후일 수 있다. 그래서 칸 시각만으로는 **그 회차가 실제로 본
자료를 다시 불러올 수 없다.**

결과를 나중에 뜯어보려 할 때 그 값이 없으면 지금 담긴 최신 재고로 다시 계산하는 수밖에 없고,
그 사이 수집이 한 번 더 돌았으면 **화면에 적힌 합계와 뜯어본 내역의 합이 어긋난다.** 사람은 둘 중
무엇이 맞는지 알 방법이 없다 — 화면이 스스로 모순되는데 그 이유가 어디에도 없는 상태다.

옛 회차는 이 값이 비어 있다. 그때는 회차 시작 이전의 가장 최근 스냅샷으로 되짚고, **화면이 그
사실을 말한다.** 되짚었다는 것을 숨기면 위와 똑같은 상태가 된다.

## 040. 뜯어보는 기준을 코드에 박지 않는다 — 표준 모델의 칸에서 고른다

합계를 품목별로 뜯어보는 기능을 만들면서 짝짓는 기준을 **「품명이 닮은 것끼리」 하나로
못박았다.** 어느 발주사의 자료에서는 로트가 **품명 안에** 들어 있어 그것만으로 잘 맞았기
때문이다. 그런데 그건 **그 자료의 사정**이지 이 프로그램의 성질이 아니다.

- 로트를 **별도 칸**으로 주는 시스템에서는 품명이 전부 같아 그 기준으로 아무것도 못 가린다
- **창고별**로 갈라 봐야 하는 회사가 있다
- 품목코드를 양쪽이 **똑같이 쓰는** 곳도 있다

기준이 코드에 박혀 있으면 그런 곳에서는 이 화면이 통째로 쓸모없어지고, **고칠 방법도 없다.**

그래서 기준을 **표준 모델의 칸 목록**에서 고른다. 칸이 늘면 고를 것도 저절로 는다 — 새 기준을
넣으려고 코드를 고칠 일이 없다. 재는 값(수량)과 한쪽 안에서 늘 같은 값(원천·기준 시각)은 뺀다.
칸 이름이 SQL 로 들어가므로 **실제로 있는 칸 목록과 대조해서만** 받아들인다.

기준은 세 갈래다. **품명이 닮은 것끼리**(어디서나 일단 도는 기본값 — 값이 정확히 같지 않아도
된다), **그 칸 값이 같은 것끼리**, **짝짓지 않고 그대로**. 마지막이 필요한 이유는 견줄 근거가
없는데 억지로 맺으면 그 줄의 차이가 거짓이 되기 때문이다 — **못 맺는 것이 잘못 맺는 것보다
낫다.**

**고른 기준이 그 자료에 안 맞으면 말한다.** 한쪽에 그 칸 값이 아예 없으면 짝을 지을 수 없는데,
그때 조용히 「전부 짝 없음」 을 보여주면 사람은 **자료가 잘못된 줄 안다.** 「이쪽에는 그 값이
없습니다」 라고 해야 다른 기준을 골라 볼 생각을 한다.

기준은 **대조마다 기억한다.** 즉석으로 바꿔 보는 것과 「우리는 늘 이 기준으로 본다」 는 다른
이야기다 — 매번 골라야 하면 결국 기본값만 쓰게 되고, 그 기본값이 안 맞는 회사에서는 이 화면을
안 보게 된다.

> **이 판단이 나온 경위를 남겨 둔다.** 화면을 지금 자료에 맞춰 고친 뒤 사장님이 말했다 —
> 「지금 이 도메인에서만 특화되게 잘 작동하고 싶은 게 아니라, 전혀 다른 구조의 품목과 상황이
> 발생하더라도 유연하게 대처할 수 있는 UI를 원한다. 현재 UI만 바라보고 그것에 맞게만 수정하지
> 마라.」 **눈앞의 자료로 검증하되 눈앞의 자료에 맞추지 않는다** — 이 원칙을 화면을 만들 때마다
> 다시 확인한다.

## 041. 화면은 「이걸 하면 무엇이 어떻게 되는지」 를 말해야 한다

사장님이 말했다 — **「뭘 어떻게 잇고 뭘 어떻게 합쳐서 계산하고, 합치면 어떻게 되고, 지금
기준이 뭔지도 모르겠고, 어떻게 커스텀해야 될지도 모르겠고, 뭐부터 문제인지 모르겠다.」**

원인은 기능이 모자라서가 아니었다. **화면이 자기 이야기를 한 번도 하지 않았다.**

이 화면의 실제 이야기는 네 줄이다 — 그런데 어디에도 안 적혀 있었다.

1. 두 시스템은 같은 물건을 **다른 이름으로 부르고 줄도 다르게 쪼갠다**
2. 그래서 **같은 것끼리 묶어** 둔다
3. 맞춰 볼 때는 **묶음 안의 수량을 시스템별로 각각 더해서** 두 합계를 견준다
4. 차이가 나면 그 묶음을 **품목 하나하나로 갈라** 본다

이걸 모르면 「묶기」·「이 묶음에 넣기」·「4↔4건」 이 전부 뜻 없는 글자다. 버튼을 아무리 잘
만들어도 소용없다.

**셋을 함께 고쳤다.**

**① 안내를 «자기 자료» 로 한다.** 지어낸 예시는 「그런가 보다」 로 끝난다. 실제로 자기 화면에
있는 줄이 나와야 이어진다 — 그래서 안내 화면이 담긴 자료에서 **여러 품목으로 쪼개진 줄
하나**를 뽑아 「이렇게 묶으면 이렇게 계산됩니다」 를 보여준다. 1↔1 짜리를 보여주면 「그냥
코드끼리 맞추면 되잖아」 로 읽혀 설명이 안 되므로 고르지 않는다.

**② 말을 통일한다.** 한 화면에 물건·묶음·잇기·더 잇기·풀기·짝·계수가 섞여 있었고, 같은 것을
가리키는 말이 둘씩 있었다. **품목**(각 시스템이 가진 줄)과 **묶음**(같다고 정한 것) 두 단어로
줄이고, 동작은 **묶기 / 이 묶음에 넣기 / 묶음 풀기** 로 맞췄다.

**③ 조절할 수 있는 것을 한 자리에 모은다.** 이름 다듬기 규칙은 별도 화면, 뜯어보기 기준은
맞춰 본 결과 안쪽, 몇 개로 칠지는 품목 줄 안쪽에 흩어져 있었다. **무엇을 조절할 수 있는지
보여주는 자리가 없으면** 자기 자료에 안 맞아도 그냥 참고 쓴다. 각 항목에 「무엇을 바꾸는지」
와 「지금 값」 을 함께 적는다 — 이름만 늘어놓으면 눌러 봐야 아는 목록이 된다.

**묶음 이름 규칙도 고를 수 있게 했다.** 「공통 부분만」 이 모든 자료에 옳지는 않다 — 품명이
아예 다른 두 시스템에서는 공통 부분이 「초콜」 같은 토막으로 남는다. 그때는 첫 이름을 그대로
두거나, 아예 코드가 짓지 않고 「이름 없음」 으로 둬서 사람이 반드시 짓게 하는 편이 낫다.
**그럴듯한 이름을 지어 두면 아무도 안 고친다.**

## 042. 다시 짓기 제안은 «지금 이름보다 나은 것만»

이름 다시 짓기 제안에 이런 줄이 섞여 있었다.

```
초콜렛 프로틴바   →   초콜릿 프로틴바 70g_26.12.12
```

**거꾸로다.** 지금 이름이 더 깔끔한데 로트 붙은 이름으로 바꾸라고 권했다. 원인은 제안 조건을
「담긴 품명과 다르면」 으로 둔 것 — 1↔1 로 묶인 것까지 걸렸다.

고치려는 것은 하나뿐이다. **여러 품목을 묶었는데 그중 하나의 이름이 묶음 전체를 대표하게 된
것.** 하나뿐인 묶음은 애초에 그 문제가 없다. 그래서 **한쪽에 품목이 둘 이상일 때만**, 그리고
**제안이 지금 이름보다 짧을 때만** 제안한다 — 다시 짓기는 군더더기를 떼는 일이지 붙이는 일이
아니다.

**나쁜 제안을 한 번 보면 그 목록 전체를 안 믿게 된다.** 제안하는 기능은 맞는 것을 놓치는 것보다
틀린 것을 권하는 쪽이 훨씬 비싸다.

## 043. 묶는 과정은 «되돌리기가 싼가» 로 결정된다

묶기 버튼을 누르면 즉시 묶였고, 되돌리려면 <b>다른 갈래로 가서 그 줄을 다시 찾아</b> 「묶음
풀기」 를 눌러야 했다. 그러면 확신이 없을 때 사람은 **아예 안 누른다** — 그리고 일이 안 끝난다.

**되돌리기를 그 자리에 둔다.** 방금 한 것 옆에 「되돌리기」 가 있으면 반쯤 확신해도 누를 수
있다. 판단을 미루게 만드는 것은 어려운 판단이 아니라 **비싼 실수**다.

단, **하나만 묶었을 때만** 되돌리기를 준다. 여럿을 한꺼번에 되돌리면 무엇이 풀렸는지 알 수
없어 되돌리기가 또 다른 사고가 된다.

**묶고 나면 그 줄이 사라진다** — 「묶어 둔 것」 갈래로 옮겨 가기 때문이다. 어디로 갔는지
말하지 않으면 사람은 방금 무슨 일이 일어났는지 모른다. 그래서 결과 안내에 **간 곳으로 가는
길**을 함께 둔다.

**고를 때는 판단 근거를 그 자리에 둔다.** 짝 후보 목록에 수량만 있으면 「묶으면 차이가 얼마가
되는가」 를 사람이 머리로 빼야 하고, 후보가 열 개면 열 번 뺀다 — 그러다 대충 고른다. 그
뺄셈은 코드가 한다.

**열두 줄을 묶으려고 열두 번 누르게 두지 않는다.** 화면 안에 코드를 넣을 수 없으므로
「이 쪽 전부 고르기」 도 폼 제출로 푼다 — 지금 보이는 줄을 전부 고른 채로 다시 그린다.

## 044. 묶음을 «통째로만» 다루면 코드가 정해 버리는 셈이다

사장님이 말했다 — **「너무 커스텀이 안 되고 네가 정해 준 대로 해야 되는 느낌이 강하다.
이게 잘 보면 네가 맘대로 묶어 버린 거잖아. 저걸 각각 떼어서 볼 수도 있고 그렇잖아.」**

맞는 말이었다. 묶음에 할 수 있는 일이 **만들기와 통째로 풀기** 둘뿐이었다.

| 되던 것 | 안 되던 것 |
|---|---|
| 줄 전체를 한 묶음으로 | **품목 하나만 빼기** |
| 묶음에 품목 더 넣기 | **묶음을 여러 개로 쪼개기** |
| 묶음 통째로 풀기 | **묶음끼리 합치기**(막혀 있었다) |
| | **나눠서 묶기** |

로트 셋이 든 줄은 「+50 하나」 로 볼 수도 있고 「+24 · +26 · 맞음」 셋으로 볼 수도 있다.
**어느 쪽이 맞는 운영인지는 회사가 정할 일**인데, 고를 자리가 없으면 코드가 정해 버린 셈이다.
그리고 마지막 로트가 정확히 맞는다는 사실이 통째로 보면 +50 안에 묻힌다.

**합치기를 막아 두기만 한 것도 같은 잘못이다.** 「이미 서로 다른 묶음에 속한 품목입니다」 로
막은 이유는 있었다 — 어느 이름을 남길지가 사람의 판단이니까. 그런데 **막기만 하고 할 길을
안 주면 그건 그냥 못 하는 일**이다. 나눠 묶어 놓고 보니 하나로 봐야 하더라는 것은 늘 생긴다.

### 어디서 고치게 하나

**만들 때**는 줄에 「통째로 하나로」 와 「나눠서」 를 나란히 둔다. **만든 뒤**는 묶음 편집
화면에서 품목 하나 단위로 손댄다 — 빼기(×), 넣기(+), 쪼개기, 합치기, 이름, 통째로 풀기.

**목록 안에서 다 하게 하지 않는다.** 표 안에 조작을 다 넣으면 표가 빽빽해져 정작 이 화면이
하려던 일 — 좌·우를 나란히 놓고 견주는 것 — 이 안 된다. 한 묶음에 집중할 때는 목록을 벗어난다.

**가르기 전에 결과를 보여준다.** 쪼개기는 되돌리려면 다시 합쳐야 해서 실수 비용이 크다.
누르기 전에 「이렇게 세 묶음이 되고 각각 차이는 이렇습니다」 를 못 보면 사람은 안 누르거나,
눌러 놓고 수습한다. 미리보기와 실제 가르기는 **같은 계산**을 쓴다 — 두 벌로 두면 미리 본 것과
결과가 달라져 미리보기가 있으나 마나다.

### 드래그앤드롭에 대해

「화면에 코드를 넣을 수 없다(CSP)」 고 여러 번 적었는데 **틀렸다.** 막혀 있는 것은 인라인
스크립트뿐이고 `script-src 'self'` 라 **자체 호스팅한 .js 파일은 돈다** — 이미 세 개가 돌고
있었다. 스스로를 과하게 묶어 놓고 그 제약을 설계 근거로 삼았다.

그래도 이번에는 **× / + 버튼**으로 만들었다. 품목이 수십 개일 때 스크롤하며 끌기는 어렵고,
키보드·모바일에서 아예 안 되며, 무엇보다 **같은 일을 더 적은 실패 경로로** 할 수 있기
때문이다. 끌어 놓기가 정말 나은 자리가 생기면 그때 얹는다.

## 045. 자동 수집이 깨졌을 때 파일로 계속 돌린다 — 「같은 원천 이름」 으로

공개 API 가 없는 원천은 **상대 화면이 쓰는 경로를 그대로 흉내 내서** 가져온다. 로그인 페이지의
JS 에서 공개키를 정규식으로 뽑고, 그 키로 암호화한 값을 보내 세션을 받고, 화면이 호출하는 조회
요청을 같은 형식으로 보내 그리드 JSON 을 받는다. **엑셀도 HTML 스크래핑도 아니다.**

깨지는 지점이 다섯이다 — 공개키를 심는 형태, 로그인 주소, 폼 칸 이름, 조회 주소와 조건, 응답
모양. 지금은 마지막 하나만 방어돼 있다(받은 행이 상대가 말한 전체 건수보다 적으면 오류).
**나머지 넷은 실패하면 실패로 뜨긴 하지만 그때 할 수 있는 게 없었다.**

### 우회로는 「같은 원천 이름」 이어야 한다

파일 업로드 뼈대는 이미 있었다 — `UPLOAD` 원천 유형, 엑셀 파서, 파일 받는 실행 엔드포인트.
그런데 **리더를 연동 «유형» 으로 골랐다.** 그래서 파일을 올려도 API 를 부르고, 그 API 가 죽어
있어서 파일을 올린 것이므로 **우회로가 우회로가 아니었다.**

별도 연동을 새로 만드는 길도 답이 아니다. **원천 이름이 달라져 그동안 묶어 둔 품목이 통째로
무용지물이 된다** — 급할 때 쓰는 길인데 그때 묶기부터 다시 하라는 셈이다.

그래서 **같은 연동에 「길」 을 둘 둔다.** 자동 수집용과 파일 업로드용. 담기는 자리는 같으므로
묶음이 그대로 산다.

### 칸 맞추기는 길마다 따로다

**엑셀 열 이름은 API 칸 이름과 다르다** — API 는 `stock_qty`, 내려받은 표는 「재고수량」.
한 벌로 두면 파일을 올리는 순간 칸이 안 맞아 **전 행이 실패**한다. 확정판도 길마다 하나씩이라
부분 유니크 인덱스를 `(connector_id, intake)` 로 넓혔다 — 연동당 하나로 두면 파일용을 확정하는
순간 자동 수집용이 밀려난다.

**「파일이 왔다」 는 사실로 리더를 고르되, 원래 파일로 받는 연동은 예외다.** 그쪽에게 파일은
정상 경로이지 우회로가 아니므로 파일 길로 보면 여태 맞춰 둔 칸을 못 찾아 전 실행이 죽는다.

### 안내가 없으면 우회로가 아니다

급할 때 쓰는 길인데 **그때 방법을 찾아다니게 하면** 우회로가 아니다. 프리셋이 「① 로그인 ②
재고관리 > 재고현황 ③ 조건 맞추기 ④ 엑셀 내려받기」 를 심어 두고, **사람이 그 자리에서 고칠 수
있게** 한다 — 상대 사이트는 언젠가 바뀌고, 그때 고쳐 둔 것이 다음부터 정답이 된다. 코드를
고쳐야 하면 그 사이 아무도 못 쓴다.

인증키를 다시 넣을 때 안내를 덮지 않는다. 고쳐 둔 내용이 조용히 사라지면 다음부터 아무도 안 적는다.

**칸을 안 맞춰 뒀으면 올리기 «전에» 말한다.** 안 그러면 급할 때 올려 놓고 전 행 실패를 본
뒤에야 안다.

## 046. 메뉴 경로는 코드에 적지 않고 «물어본다»

파일로 대신 채우는 길에 「어느 메뉴로 들어가 엑셀을 받나」 를 적어야 했다. 처음에는 프리셋에
「① 로그인 ② 재고관리 > 재고현황 ③ 엑셀」 을 **지어서** 심었다 — 실제 화면을 보지 않고 흔한
구조로 적은 것이다.

**그건 안 적어 둔 것보다 나쁘다.** 사람은 그 안내를 믿고 없는 메뉴를 찾는다. 그리고 상대가
메뉴를 바꾸는 날 코드에 박힌 안내는 그대로 거짓말이 된다.

**그래서 물어본다.** 수집이 실제로 보는 화면 코드(`template=I100`)를 이미 알고 있으므로,
로그인한 화면에서 그 코드를 가리키는 메뉴 항목의 글자를 읽어 온다. 상대가 메뉴를 바꾸면
**다시 눌러 다시 읽으면 된다.**

**계정은 서버 밖으로 나가지 않는다.** 매일 도는 수집과 같은 자리에서 같은 계정으로 로그인한다.

**못 찾으면 지어내지 않는다.** 빈 값을 주고 화면이 「찾지 못했습니다 — 직접 적어 주세요」 라고
말한다. 그럴듯한 경로를 지어내는 것이 이 기능에서 제일 나쁜 결과다.

> **여기서 한 번 잘못 갔다가 되돌아왔다.** 사장님이 「저장된 계정으로 들어가 확인」 을
> 승인해 줬을 때, 나는 운영 DB 에서 암호문을 꺼내고 마스터키를 찾아 **내 쪽에서 복호화하려
> 했다.** 컨테이너 환경변수에도 파일에도 키가 없어 막혔는데, 거기서 더 파고드는 대신 멈췄다 —
> 메뉴 이름 네 줄을 얻자고 운영 암호화 키를 꺼내 발주사 계정을 내 손에 쥐는 것은 승인받은
> 범위보다 깊다. **제품이 스스로 하게 만드는 쪽이 더 안전하고, 다음에 또 필요할 때도 쓸 수
> 있다.**

### 안내는 「연결 저장」 때만 심겼다

기본 안내를 연결 저장 시점에만 넣어서 **그 전에 만들어진 연동에는 비어 있었다.** 정작 오래 쓴
연동일수록 안내가 없는 셈이고, 그게 급할 때 제일 아프다. 「기본 안내 넣기」 를 화면에 두되
**비어 있을 때만** 넣는다 — 사람이 실제 메뉴를 확인해 고쳐 둔 것을 코드가 말없이 되돌리면
다음부터는 아무도 안 적는다.
