## Phase 구분

| 단계 | 범위 | 대응 기능 |
|---|---|---|
| Phase 1 | 골격 + **쿠팡 1채널** 수집 → 텔레그램 알림 | F-01, F-02 |
| Phase 2 | 재고 · 매핑 · 안전재고 | F-03, F-04, F-05 |
| Phase 3 | 채널 확장 (네이버 → 나머지) | F-01 확장 |
| Phase 4 | 일일 리포트, 엑셀 내보내기 | F-06, F-07 |
| Phase 5 | 채널 재고 전송 (시뮬레이션 선행) | F-08 |
| Phase 6 | AI 리포트 요약, 대화형 조회 | F-10, F-11 |

### Phase 1 을 수직 슬라이스로 구성하는 이유

채널 1개를 수집부터 알림까지 관통하면 인증·페이징·응답 형식·호출 제한을 실제로 모두 겪게 되고, 이후 채널은 같은 틀의 반복이 된다. 반대로 어댑터 6종을 먼저 구현하면 첫 알림 발송 시점에 6종을 동시에 수정하게 된다.

### Phase 5 를 후반에 두는 이유

F-08 은 **채널에 데이터를 기록하는 유일한 기능**이며 오류 시 매출 손실로 직결된다. 재고 계산이 수 주간 정확했다는 근거가 쌓인 후에 활성화한다. 시뮬레이션 모드 선행 운영은 선택이 아닌 필수 절차다.

## 다음 작업

### 1. 쿠팡 어댑터

`ChannelOrderCollector` 구현. HMAC-SHA256 인증, 페이징, rate limiter.

**발주자 인증정보(P-02) 없이도 WireMock 으로 구현·검증할 수 있다.** 실제 API 호출과 실주문 알림 도달 확인(A-01)만 인증정보를 요구한다.

실제 응답 샘플을 테스트 리소스로 보관하는 자리를 함께 만든다 — 채널 API 사양 변경을 감지할 유일한 수단이다.

### 2. 관리자 화면

| 화면 | 기능 |
|---|---|
| 대시보드 | 금일 판매, 재고 부족, 채널 수집 상태 |
| 재고 관리 | SKU 조회·수정, 임계치 설정, 변동 이력 |
| 상품 매핑 | 채널 상품과 SKU 연결 |
| 주문 조회 | 검색·조회, 엑셀 내보내기 |
| 채널 설정 | 인증정보 등록, 수집 주기, 사용 여부 |
| 알림 설정 | 텔레그램 연결, 알림 조건·방식 |
| 시스템 로그 | 수집·전송 성공/실패 이력 |

daisyUI 컴포넌트 기준. 보안 요건은 [06-OPERATIONS](06-OPERATIONS.md) 를 따른다.

**채널 인증정보는 화면에 값을 표시하지 않는다.** 등록 여부와 키 이름만 보여준다.

## 미해결 항목

### Q-00 — 발주자 확인 필요 (최우선)

기능 명세서 6.1 이 최우선으로 규정한 항목이 여전히 미확정이다.

> 기존 통합솔루션을 사용하면서도 수작업이 남는 지점이 정확히 어디인가

**A(통합솔루션 → ERP 이관을 수동 수행)로 확인되면 F-07 과 제외 항목을 개정해야 한다.** ERP 연동이 제외 기능에서 핵심 기능으로 바뀐다.

| 항목 | 영향 |
|---|---|
| 모듈 구조 | **영향 없음** — `palim-collector` 와 대칭 위치에 내보내기 조율 계층이 추가된다 |
| 개발 범위 · 견적 | **변경됨** |
| Phase 1~3 착수 | 영향 없음 |

**Phase 4 진입 전까지 답이 확정되어야 한다.**

### 자동 검증이 없는 규칙

| 규칙 | 현재 상태 |
|---|---|
| 도메인 모듈 간 의존 금지 | `build.gradle.kts` 와 `package-info.java` 로만 표현. **ArchUnit 미도입** |
| 트랜잭션 경계 | `MANDATORY` 로 런타임 검출. 컴파일 차단은 불가 |
