# Palim(팔림) — 다채널 판매 실시간 알림·재고 관리 시스템

**기능 명세서**

- **프로젝트명**: Palim (팔림)
- **작성일**: 2026-07-28
- **문서 상태**: 초안 (발주자 확인 대기 항목 있음)
- **문서 성격**: 본 문서는 개발 범위를 정의하는 계약 부속 문서다. 여기에 적히지 않은 기능은 개발 범위에 포함되지 않는다.

> **구현 세부가 변경된 항목이 있다.** 기능 정의와 인수 조건은 그대로 유효하며, 아래는 그것을 달성하는 방법이 바뀐 것이다. 근거는 [07-DECISIONS](07-DECISIONS.md) 에 있다.
>
> | 본 문서의 서술 | 실제 구현 | 인수조건 영향 |
> |---|---|---|
> | 메시지 큐(RabbitMQ)로 알림 비동기 처리 (4.2 · 4.5) | PostgreSQL Outbox 단독 | **없음** — A-14 의 유실 방지 근거가 Outbox 다 |
> | 오버셀링 방지 (1.1) | 동기화 지연 중 발생 시 **음수 재고를 허용**하고 즉시 알림 | 없음 — 주문 유실을 막기 위한 선택 |

## 1. 배경과 목적

### 1.1 현재 상황

발주자는 여러 온라인 판매채널(쿠팡, 네이버, 롯데 등)에서 상품을 판매한다. 현재 각 채널의 주문과 재고를 **엑셀로 채널별로 따로 관리**하며, 이 작업을 사람이 수동으로 수행한다.

이로 인해 다음 문제가 발생한다.

| 문제 | 원인 |
|---|---|
| 재고 수량 불일치 | 채널별 엑셀을 수동 대조하는 과정의 누락·오기입 |
| 판매 인지 지연 | 각 채널에 개별 로그인해야 주문 확인 가능 |
| 초과판매(오버셀링) 위험 | 채널별 재고가 독립 관리되어 실제 재고를 초과한 주문 접수 가능 |

ERP(이카운트)를 보유하고 있으나 사용 난이도로 인해 재고 관리 목적으로는 실질적으로 활용되지 못하고 있다.

### 1.2 목적

본 시스템은 **판매 발생을 사람이 확인하지 않아도 알 수 있게 하고, 채널 간 재고를 자동으로 일치시키는 것**을 목적으로 한다.

### 1.3 시스템의 성격 — 상용 솔루션과의 차이

시장에는 사방넷·플레이오토·샵링커 등 상용 통합관리 솔루션이 존재하며, 본 시스템의 기능 중 일부(주문 수집, 재고 동기화)를 이미 제공한다.

본 시스템을 자체 구축하는 근거는 다음과 같다.

| 구분 | 상용 솔루션 | 본 시스템 |
|---|---|---|
| 성격 | **관리 도구** — 사용자가 접속해서 확인 | **감시 도구** — 접속하지 않아도 통보 |
| 알림 대상 | 구매 고객 (알림톡) | **판매자 본인** |
| 알림 수단 | 이메일, 웹 화면 내 표시 | **텔레그램 실시간 푸시** |
| 동기화 주기 | 통상 30분 | 채널 한도 내 최단 (5~10분 목표) |
| 알림 규칙 | 고정 | **발주자가 직접 설정 가능** |

즉, 본 시스템은 상용 솔루션의 대체재가 아니라 **상용 솔루션이 제공하지 않는 능동적 알림 기능**을 목적으로 한다.

## 2. 개발 범위

### 2.1 포함 기능 (MVP)

| # | 기능 | 설명 |
|---|---|---|
| F-01 | 다채널 주문 자동 수집 | 각 채널 공식 API를 통해 주문을 주기적으로 수집 |
| F-02 | 실시간 판매 알림 | 신규 주문 발생 시 텔레그램으로 즉시 통보 |
| F-03 | 통합 재고 관리 | 전 채널 판매를 반영한 SKU 단위 단일 재고 관리 |
| F-04 | 상품 매핑 관리 | 채널별 상품코드와 자사 SKU를 연결하는 웹 화면 |
| F-05 | 안전재고 경고 | 재고가 설정 임계치 미만일 때 텔레그램 경고 |
| F-06 | 일일 요약 리포트 | 지정 시각에 전일 판매·재고 현황을 텔레그램 발송 |
| F-07 | 판매내역 엑셀 내보내기 | 이카운트 업로드용 판매 내역 파일 생성 |
| F-08 | 채널 재고 자동 동기화 | 재고 변동 시 각 채널의 판매 가능 수량을 자동 갱신 |
| F-09 | 웹 관리자 페이지 | 위 기능의 설정 및 조회 화면 |
| F-10 | AI 리포트 요약 | 일일 리포트를 자연어 문장으로 재작성 |
| F-11 | AI 대화형 조회 | 텔레그램에서 자연어로 재고·매출을 묻고 답변 |

### 2.2 제외 기능

다음 기능은 **본 계약 범위에 포함되지 않는다.** 추가를 원할 경우 별도 협의 및 비용 산정이 필요하다.

| 제외 기능 | 제외 사유 |
|---|---|
| 송장 등록·배송 처리 | 택배사 연동이 별도로 필요한 독립 영역 |
| 상품 등록·수정 (채널 송신) | 알림·재고와 무관, 채널별 상품 규격 대응 부담이 큼 |
| 고객 문의(C/S) 통합 관리 | 별도 영역 |
| 반품·교환·취소 처리 | 알림 대상에는 포함하나, 처리 기능은 제외 |
| 이미지 호스팅 | 무관 |
| 챗봇 / AI 자동응답 | 무관 |
| 이카운트 ERP API 연동 | 엑셀 내보내기로 대체 (2.3 참조) |
| 세트상품·합포장·사은품 처리 | 상용 솔루션도 완전 자동화하지 못하는 영역 |

### 2.3 2차 개발 검토 항목

MVP 운영 후 필요성이 확인되면 별도 협의한다.

- 채널별 재고 할당 (채널마다 판매 가능 수량을 나누어 배정하는 오버셀링 방지 고도화)
- 이카운트 ERP API 직접 연동
- 송장 등록 자동화
- 추가 판매채널 연동

## 3. 기능 상세

### F-01 다채널 주문 자동 수집

**동작**

각 채널의 공식 Open API를 통해 신규 주문을 주기적으로 조회하여 데이터베이스에 저장한다.

**대상 채널**

| 등급 | 채널 | 연동 방식 | 상태 |
|---|---|---|---|
| 1군 | 쿠팡 | 공식 API (HMAC-SHA256) | 연동 가능 확인됨 |
| 1군 | 네이버 스마트스토어 | 공식 API (OAuth2 + 전자서명) | 연동 가능 확인됨 |
| 1군 | 롯데온 | 공식 API (인증키) | 연동 가능 확인됨 |
| 1군 | 11번가 | 공식 API (API Key) | 연동 가능 확인됨 |
| 1군 | G마켓 / 옥션 (ESM) | 공식 API (JWT) | 연동 가능 확인됨 |
| 2군 | SSG닷컴 | 공식 API | 입점 및 MD 승인 선행 필요 |
| 3군 | 롯데백화점 | **공식 API 없음** → 엑셀 업로드 | 수동 처리 |
| 제외 | 카카오 선물하기/톡스토어 | 카카오 측 연동사 선정 필요 | **범위 제외** |

> **주의 — 카카오 채널 제외 사유**
> 카카오쇼핑 Open API는 모든 판매자에게 제공되지 않으며, 카카오가 연동 대행사를 선정하는 구조다. 승인 여부와 시점을 개발자가 통제할 수 없으므로 본 계약 범위에서 제외한다. 카카오 측 승인이 확보될 경우 별도 협의한다.

> **주의 — "롯데" 채널 확인 필요**
> 롯데온(오픈마켓)과 롯데백화점(입점)은 서로 다른 시스템이다. 롯데온은 공식 API가 제공되어 자동 연동이 가능하나, 롯데백화점은 공식 API가 없어 파트너 포털에서 내려받은 엑셀을 업로드하는 방식으로만 처리 가능하다. **발주자의 실제 판매 채널이 어느 쪽인지 확인이 필요하다.**

**수집 방식**

전 채널이 주문 발생 시점에 알려주는 기능(webhook)을 제공하지 않으므로, **주기적 조회(polling) 방식**으로 동작한다. 따라서 주문 발생과 알림 사이에는 **수집 주기만큼의 지연**이 발생한다.

**채널별 호출 제한 준수**

각 채널은 API 호출 횟수를 제한하며, 초과 시 차단될 수 있다. 시스템은 채널별 제한을 준수하도록 호출을 조절한다.

| 채널 | 확인된 제한 | 기본 수집 주기(안) |
|---|---|---|
| 쿠팡 | 초당 10회, 지속 초과 시 영구 차단 | 5분 |
| 네이버 | 초당 2회 | 5분 |
| G마켓/옥션 | **주문조회 5초당 1회** | 10분 |
| 11번가 | 미공개 | 10분 |
| 롯데온 | 미공개 | 10분 |

수집 주기는 웹 관리자에서 채널별로 변경 가능하다.

**중복 방지**

동일 주문이 반복 수집되더라도 채널 주문번호를 기준으로 중복을 제거하여, 재고가 이중 차감되지 않도록 한다.

**완료 조건**
- 각 대상 채널에서 실제 주문 1건 발생 시, 설정된 수집 주기 내에 데이터베이스에 저장된다.
- 동일 주문을 반복 수집해도 재고는 1회만 차감된다.

### F-02 실시간 판매 알림

**동작**

신규 주문이 수집되면 텔레그램으로 알림을 발송한다.

**알림 내용**

```
🛒 신규 주문

채널   : 쿠팡
상품   : [SKU-001] 상품명
수량   : 2개
금액   : 39,800원
주문시각: 07-28 14:32

현재 재고: 18개
```

**설정 항목 (웹 관리자)**

| 설정 | 설명 | 기본값 |
|---|---|---|
| 발송 방식 | 건별 즉시 / N분 단위 묶음 발송 | 건별 즉시 |
| 묶음 주기 | 묶음 발송 선택 시 주기 | 30분 |
| 알림 대상 SKU | 전체 / 선택한 SKU만 | 전체 |
| 알림 대상 채널 | 전체 / 선택한 채널만 | 전체 |
| 야간 발송 | 지정 시간대 발송 보류 후 익일 일괄 | 사용 안 함 |

> **설계 근거**: 발주자는 초기에 "알림이 많아도 무방"하다고 판단하였으나, 주문량에 따라 알림 과다로 인해 알림을 확인하지 않게 되는 문제가 발생할 수 있다. 이에 발송 방식을 설정으로 조절 가능하도록 한다.

**완료 조건**
- 신규 주문 수집 시 설정된 방식에 따라 텔레그램 메시지가 도달한다.
- 웹에서 발송 방식을 변경하면 재시작 없이 즉시 반영된다.

### F-03 통합 재고 관리

**동작**

SKU 단위로 단일 재고 수량을 관리한다. 어느 채널에서 판매되든 동일한 재고에서 차감된다.

**재고 원본 정책**

본 시스템의 데이터베이스가 **재고의 유일한 기준**이다. 이카운트 ERP는 회계·세무 목적으로 계속 사용하되, 재고 수량에 대해서는 본 시스템을 기준으로 한다.

> **설계 근거**: 현재 이카운트의 재고 데이터는 수동 입력 지연·누락으로 인해 실제와 불일치할 가능성이 높다. 부정확한 데이터를 기준으로 삼으면 시스템 전체가 무의미해지므로, 본 시스템을 원본으로 정의한다.

**초기 재고 설정**

시스템 도입 시점에 발주자가 실물 재고를 실사하여 웹 관리자에서 직접 입력한다. (SKU 21종 기준, 1회성 작업)

**재고 변동 사유**

| 사유 | 발생 시점 | 처리 |
|---|---|---|
| 판매 | 주문 수집 시 | 자동 차감 |
| 입고 | 발주자 입력 | 수동 증가 |
| 취소·반품 | 채널에서 취소 정보 수집 시 | 자동 복원 |
| 실사 조정 | 발주자 입력 | 수동 보정 |
| 폐기·분실 | 발주자 입력 | 수동 차감 |

모든 재고 변동은 사유·수량·시각과 함께 이력으로 기록되어 추적 가능하다.

**완료 조건**
- 임의 채널에서 주문 발생 시 해당 SKU 재고가 정확히 차감된다.
- 재고 변동 이력에서 각 변동의 원인을 확인할 수 있다.

### F-04 상품 매핑 관리

**동작**

채널마다 상이한 상품코드를 자사 SKU와 연결한다. 매핑되지 않은 상품의 주문은 재고에 반영되지 않으므로, 매핑은 시스템 동작의 필수 전제다.

**화면 구성**

- 각 채널에서 조회한 상품 목록 표시
- 목록에서 자사 SKU를 선택하여 연결
- 매핑되지 않은 항목을 별도 표시

**미매핑 주문 처리**

매핑되지 않은 상품의 주문이 수집되면 다음과 같이 처리한다.

1. 주문 자체는 정상 저장한다 (데이터 유실 방지)
2. 재고는 차감하지 않는다
3. **텔레그램으로 매핑 필요 알림을 발송한다**
4. 발주자가 매핑을 완료하면 해당 주문의 재고를 소급 반영한다

> **설계 근거**: 신규 상품 등록 시 매핑 누락이 발생할 수 있으며, 이를 방치하면 재고가 조용히 틀어진다. 미매핑을 즉시 인지할 수 있도록 알림 대상에 포함한다.

**규모**

자사 SKU 21종 × 채널 3~5개 = 최대 약 105건. 도입 시 1회성 작업이며, 이후 신규 상품 추가 시에만 발생한다.

**완료 조건**
- 웹에서 채널 상품과 SKU를 연결할 수 있다.
- 미매핑 상품 주문 발생 시 알림이 발송되고, 매핑 후 재고에 소급 반영된다.

### F-05 안전재고 경고

**동작**

SKU별로 설정한 임계치 미만으로 재고가 감소하면 텔레그램으로 경고한다.

**알림 내용**

```
⚠️ 재고 부족

[SKU-001] 상품명
현재 재고: 3개 (임계치: 5개)

최근 7일 평균 판매: 2.1개/일
예상 소진: 약 1.4일 후
```

**설정 항목**

| 설정 | 설명 | 기본값 |
|---|---|---|
| SKU별 임계치 | 경고를 발생시킬 재고 수량 | SKU별 개별 설정 |
| 반복 알림 | 임계치 미만 상태가 지속될 때 재알림 주기 | 1일 1회 |
| 품절 즉시 알림 | 재고 0 도달 시 별도 긴급 알림 | 사용 |

**완료 조건**
- 재고가 임계치 미만이 되는 시점에 경고가 발송된다.
- 동일 SKU에 대해 설정된 주기보다 자주 중복 발송되지 않는다.

### F-06 일일 요약 리포트

📊 일일 리포트 (07-27)

  1. [SKU-003] 상품명 — 9개

### F-07 판매내역 엑셀 내보내기

**동작**

기간을 지정하여 판매 내역을 엑셀 파일로 생성한다. 발주자는 이 파일을 이카운트에 업로드하여 회계 처리에 사용한다.

**범위 한계**

본 기능은 **파일 생성까지만** 담당한다. 이카운트로의 업로드는 발주자가 수행한다. 이카운트 API 연동은 본 계약 범위에 포함되지 않는다.

**완료 조건**
- 기간 지정 후 엑셀 파일이 생성되어 다운로드된다.
- 파일에 채널·상품·수량·금액·일자가 포함된다.

### F-08 채널 재고 자동 동기화

**동작**

통합 재고가 변동되면 각 채널의 판매 가능 수량을 자동으로 갱신한다. 이를 통해 실제 재고를 초과하는 주문 접수를 방지한다.

**안전장치**

본 기능은 각 채널에 데이터를 **기록**하므로, 오류 발생 시 실제 판매에 영향을 줄 수 있다. 다음 안전장치를 함께 구현한다.

| 안전장치 | 설명 |
|---|---|
| 시뮬레이션 모드 | 실제 전송 없이 전송 예정 내용만 알림. 도입 초기 검증용 |
| 변동량 상한 | 1회 변경량이 설정값을 초과하면 전송을 중단하고 경고 발송 |
| 전체 중단 스위치 | 웹에서 재고 전송 기능을 즉시 비활성화 |
| 전송 이력 기록 | 전송 시각·채널·SKU·변경 전후 값을 모두 기록 |
| 전송 실패 알림 | 채널 전송 실패 시 텔레그램 통보 |

> **설계 근거**: 재고 계산 오류로 0을 전송할 경우 해당 상품이 전 채널에서 품절 처리되어 매출 손실이 발생한다. 변동량 상한과 시뮬레이션 모드는 이러한 사고를 예방하기 위한 필수 장치다.

**제약**

- 채널 API 호출 제한으로 인해 즉시 반영이 아닌 **수 분 내 반영**이다.
- 재고 전송 중 해당 채널에서 주문이 발생하면 일시적 불일치가 발생할 수 있다. 시스템은 다음 동기화 주기에 이를 보정한다.

**완료 조건**
- 통합 재고 변동 시 각 채널의 재고 수량이 갱신된다.
- 시뮬레이션 모드에서 실제 전송 없이 예정 내용만 알림된다.
- 변동량 상한 초과 시 전송이 중단되고 경고가 발송된다.

> **설계 근거**: 알림 수신은 텔레그램이 담당하므로 앱의 푸시 기능이 중복된다. 설정 변경은 빈도가 낮은 작업이므로 전용 앱의 필요성이 낮다.

**접근 제어**

관리자 계정 1개로 로그인한다. 다중 사용자·권한 분리는 범위에 포함하지 않는다.

**완료 조건**
- PC·모바일 브라우저에서 정상 표시되고 조작 가능하다.
- 로그인하지 않은 상태에서 접근이 차단된다.

### F-10 AI 리포트 요약

**동작**

F-06의 일일 리포트에서, 데이터베이스가 산출한 수치를 언어 모델이 자연어 문장으로 재작성한다.

```
📊 Palim 리포트 (07-27)

어제는 24건 487,600원 팔렸습니다. 지난주 같은 요일보다
30% 늘었고, 쿠팡이 대부분(14건)을 차지했습니다.

⚠️ 확인이 필요합니다
SKU-003이 어제만 9개 나갔는데 재고가 4개 남았습니다.
현재 판매 속도라면 내일 오후 품절이 예상됩니다.

SKU-011은 3주째 판매가 없습니다. 재고 40개가 묶여 있습니다.
```

**역할 한계 — 반드시 준수**

언어 모델은 **이미 확정된 수치를 문장으로 변환하는 역할만** 수행한다. 판매량·재고량·증감률 등 모든 수치는 데이터베이스 조회와 코드 연산으로 산출하며, 언어 모델은 이를 계산하지 않는다.

> **설계 근거**: 언어 모델은 산술 연산에서 오류를 발생시킬 수 있다. 재고·매출 수치가 잘못 전달되면 발주 판단에 직접적인 손실을 초래하므로, 수치 산출과 문장 생성을 엄격히 분리한다.

**장애 시 동작**

언어 모델 호출이 실패하면 F-06의 기본 형식(수치 나열) 리포트를 발송한다. 리포트 자체가 누락되지 않는다.

**완료 조건**
- 일일 리포트가 자연어 문장 형태로 발송된다.
- 문장에 포함된 수치가 데이터베이스 값과 일치한다.
- 언어 모델 장애 시에도 기본 형식 리포트가 발송된다.

### F-11 AI 대화형 조회

**동작**

발주자가 텔레그램에서 자연어로 질문하면, 시스템이 데이터를 조회하여 답변한다.

```
발주자: 지금 재고 얼마나 남았어?
Palim : 전체 21개 SKU 중 재고 부족이 3건입니다.
        SKU-003 (4개), SKU-007 (2개), SKU-015 (1개)

발주자: 이번달 쿠팡 얼마나 팔렸어
Palim : 7월 쿠팡 매출은 3,240,000원입니다. 전월 대비 12% 증가했습니다.

발주자: 3번 상품 재고 50개로 바꿔줘
Palim : SKU-003의 재고를 4 → 50으로 변경합니다.
        [확인] [취소]
```

> **설계 근거**: 발주자는 기존 ERP(이카운트)의 사용 난이도를 문제로 제기하였다. 메뉴 탐색 없이 대화로 조회할 수 있게 하여 접근성 문제를 해소한다.

**역할 한계 — 반드시 준수**

언어 모델은 **자연어 질문을 조회 조건으로 변환하는 역할만** 수행한다. 실제 데이터 조회와 집계는 데이터베이스가 수행하며, 언어 모델은 그 결과를 문장으로 전달한다.

**데이터 변경 요청 시 확인 절차**

재고 수정 등 데이터를 변경하는 요청은 **반드시 변경 전후 값을 명시하여 확인을 받은 후** 실행한다. 확인 없이 즉시 실행하지 않는다.

**제한 사항**

- 조회 및 재고 수정에 한정한다. 채널 재고 전송(F-08)의 직접 실행 명령은 지원하지 않는다.
- 등록된 관리자의 텔레그램 계정에서만 동작한다.

**장애 시 동작**

언어 모델 호출이 실패하면 질문에 답하지 못했음을 안내한다. 알림 발송(F-02, F-05) 등 다른 기능은 영향을 받지 않는다.

**완료 조건**
- 재고·매출 관련 자연어 질문에 정확한 수치로 답변한다.
- 답변 수치가 웹 관리자 화면의 값과 일치한다.
- 재고 변경 요청 시 확인 절차를 거친다.
- 등록되지 않은 계정의 요청에 응답하지 않는다.

### AI 기능 적용 범위

언어 모델은 다음 영역에만 사용하며, 그 외 영역에는 사용하지 않는다.

| 영역 | 사용 여부 | 사유 |
|---|---|---|
| 리포트 문장 생성 (F-10) | ✅ 사용 | 오류가 발생해도 문구 품질에만 영향 |
| 자연어 질의 해석 (F-11) | ✅ 사용 | 조회 조건 변환에 한정 |
| **재고 수량 계산** | ❌ 미사용 | 오류 시 재고 정합성 훼손 |
| **주문 데이터 해석** | ❌ 미사용 | API 응답은 정형 데이터, 코드로 처리 |
| **채널 재고 전송 판단** | ❌ 미사용 | 오류 시 매출 손실 발생 |
| **중복 주문 판정** | ❌ 미사용 | 오류 시 재고 이중 차감 |

> **원칙**: 언어 모델은 데이터베이스가 산출한 결과를 언어로 표현할 뿐, 수치를 생성하거나 판단하지 않는다.

## 4. 시스템 구성

### 4.1 구조

```
┌─────────── 판매 채널 ───────────┐
│ 쿠팡  네이버  롯데온  11번가  G마켓 │  ← API 연동
│ 롯데백화점                        │  ← 엑셀 업로드
└────────────────┬─────────────────┘
                 │ 주기적 조회
                 ▼
        ┌─────────────────┐
        │  수집 스케줄러    │  ← 채널별 호출 한도 준수
        └────────┬────────┘
                 ▼
        ┌─────────────────┐
        │  채널 어댑터 계층  │  ← 채널별 형식을 공통 형식으로 변환
        └────────┬────────┘
                 ▼
        ┌─────────────────┐
        │   주문 처리기     │  ← 중복 제거, SKU 매핑, 재고 반영
        └────────┬────────┘
                 ▼
        ┌─────────────────┐
        │  PostgreSQL     │  ← 재고 원본 (유일한 기준)
        │  주문·재고·발송상태 │
        └──┬────────┬─────┘
           │        │
           │        └──────────┐
           ▼                   ▼
    ┌────────────┐      ┌─────────────┐
    │  메시지 큐   │      │  웹 관리자   │
    │ (발송 대기)  │      └─────────────┘
    └──────┬─────┘
           ▼
    ┌────────────┐
    │  발송 워커   │ → 텔레그램
    └────────────┘
```

### 4.2 구성 요소

| 요소 | 역할 |
|---|---|
| 수집 스케줄러 | 채널별 주기에 따라 수집 실행, 호출 한도 준수, 실패 시 재시도 |
| 채널 어댑터 | 채널별 인증·응답 형식 차이를 흡수하여 공통 형식으로 변환 |
| 주문 처리기 | 중복 제거, SKU 매핑, 재고 반영 |
| **PostgreSQL** | 주문·재고·매핑·설정·알림 발송 상태 저장. **재고의 유일한 기준** |
| 메시지 큐 | 알림 발송을 비동기 처리. 재시도 및 실패 메시지 격리 |
| 발송 워커 | 큐에서 메시지를 꺼내 텔레그램 발송 속도 제한을 준수하며 전송 |
| 웹 관리자 | 설정 및 조회 화면 |

채널 어댑터는 채널마다 독립적으로 구성되어, 신규 채널 추가 시 기존 코드에 영향을 주지 않는다. 롯데백화점의 엑셀 업로드 역시 어댑터의 한 형태로 처리한다.

### 4.3 장애 격리 원칙

**메시지 큐 또는 검색 엔진의 장애가 재고 정합성에 영향을 주어서는 안 된다.**

이를 위해 다음을 준수한다.

- 알림 발송 대상은 **PostgreSQL에 먼저 기록**한 후 큐에 투입한다. 큐가 유실되어도 데이터베이스 기록으로 복구할 수 있다.
- 주문 수집과 재고 계산은 큐의 상태와 무관하게 동작한다. 큐 장애 시 알림만 지연되며 재고는 정상 반영된다.
- 언어 모델 장애 시 F-10은 기본 형식으로, F-11은 응답 불가 안내로 대체된다. 다른 기능은 영향받지 않는다.

### 4.4 확장을 고려한 구조

향후 데이터 증가에 대비하여 다음을 설계 단계에서 반영한다. **현 시점에는 별도 구성 요소를 도입하지 않는다.**

| 대비 항목 | 설계 반영 내용 |
|---|---|
| 검색·통계 부하 분리 | 조회 로직을 별도 계층으로 분리하여, 향후 검색 엔진(Elasticsearch 등) 도입 시 해당 계층만 교체 가능하도록 구성 |
| 큐 제품 교체 | 큐 접근을 추상 계층으로 감싸, 메시지 큐 제품 변경 시 해당 계층만 교체 |
| 증분 색인 | 모든 주문·재고 레코드에 변경 시각(updated_at)을 기록하여, 향후 증분 색인이 가능하도록 함 |

> **설계 근거**: 현재 데이터 규모(SKU 21종, 일 주문 수십 건)에서는 PostgreSQL만으로 충분하며, 검색 엔진 도입은 자원 소모와 데이터 동기화 부담만 증가시킨다. 다만 향후 규모 확대 시 구조 변경 없이 확장할 수 있도록 조회 계층을 분리한다.

### 4.5 운영 환경

**MVP 단계**

개발자가 보유한 NAS에 Docker로 구성한다. 별도 인프라 비용이 발생하지 않는다.

| 구성 | 비고 |
|---|---|
| 애플리케이션 (수집·처리·알림) | Docker 컨테이너 |
| PostgreSQL | Docker 컨테이너 |
| 메시지 큐 | **RabbitMQ** — NAS에 기구축된 인스턴스 활용 |
| 웹 관리자 | Docker 컨테이너 |
| 외부 노출 | **Cloudflare Tunnel** — 포트 개방 없이 안전하게 노출, 도메인·HTTPS 포함. 무료 |

**향후 클라우드 이전**

컨테이너 및 환경변수 기반으로 구성하여, 동일한 구성 파일로 클라우드 서버에 이전 가능하도록 한다. 메시지 큐 역시 관리형 서비스가 아닌 컨테이너로 구성하여 이전 시 추가 학습·비용이 발생하지 않도록 한다.

### 4.6 인프라 비용

| 단계 | 월 비용 | 비고 |
|---|---|---|
| **MVP (NAS)** | **0원** | 개발자 보유 장비 활용 |
| 클라우드 이전 시 (최소 구성) | 약 2.5만원 | 서버 1대에 데이터베이스 직접 설치 |
| 클라우드 이전 시 (관리형 DB) | 약 5.5만원 | 관리형 데이터베이스 사용 |

> 클라우드 이전 시 발생하는 서버 비용은 **발주자 부담**이다. 이전 시점 및 구성은 별도 협의한다. 언어 모델 API 사용료(F-10, F-11)는 별도이며, 사용량에 따라 월 수천 원 수준으로 예상된다.

### 4.4 고정 IP 요건

네이버·11번가·롯데온·SSG닷컴은 API를 호출하는 서버의 IP 주소를 사전 등록하도록 요구한다.

**따라서 시스템이 설치되는 서버는 고정 IP를 사용해야 한다.**

유동 IP 환경에서 IP가 변경되면 해당 채널의 수집이 중단된다. 이 경우 주문이 없는 것처럼 보여 문제 인지가 늦어질 수 있으므로, 시스템은 **수집 실패를 감지하여 텔레그램으로 즉시 경고**한다.

## 5. 발주자 제공 사항

다음 항목은 발주자가 제공해야 하며, 미제공 시 해당 기능의 개발·검증이 불가능하다.

| P-02 | 각 채널 API 인증정보 | **사업자 명의로 발주자가 직접 발급** |

## 6. 확인 대기 항목

다음 항목은 발주자 확인 후 본 명세서에 반영한다.

| # | 확인 항목 | 영향 |
|---|---|---|

| Q-07 | 기존 솔루션 계속 사용 여부 (병행 / 대체) | 본 시스템의 위치 결정 |

### 6.1 Q-00 상세 — 최우선 확인 사항

발주자는 이미 통합관리 솔루션을 사용 중인 것으로 파악되었으나, "수작업에서 막힌다", "결국 사람이 입력한다"는 문제를 제기하였다.

**기존 솔루션을 사용함에도 수작업이 남는 지점을 특정하지 못하면, 본 시스템도 동일한 지점에서 동일한 한계에 부딪힌다.** 따라서 다음을 확인해야 한다.

| 후보 | 내용 | 본 시스템의 해결 가능 여부 |
|---|---|---|
| A | 통합솔루션 → ERP(이카운트) 데이터 이관을 수동으로 수행 | **해결 가능** — 단, ERP 연동이 필요하므로 현재 범위(2.2 제외 항목)를 변경해야 함 |
| B | 솔루션이 연동하지 못하는 판매채널이 있어 해당 채널만 엑셀 처리 | **부분 해결** — 해당 채널에 공식 API가 없다면 본 시스템도 엑셀 업로드가 최선 |
| C | 솔루션의 주문 수집을 사람이 수동으로 실행 | **해결 가능** — 자동 스케줄러로 대체 |

> **A로 확인될 경우 본 명세서의 F-07 및 2.2 제외 항목을 개정해야 한다.** 현재는 이카운트 API 연동을 범위에서 제외하고 엑셀 내보내기로 대체하도록 정의하고 있으나, 수작업의 원인이 A라면 ERP 연동이 핵심 기능이 된다.

## 7. 제약 사항 및 책임 한계

### 7.1 기술적 제약

| 제약 | 내용 |
|---|---|
| 알림 지연 | 전 채널이 실시간 통지를 제공하지 않아 수집 주기만큼 지연이 발생한다 |
| 채널 API 의존 | 채널 측 API 장애·점검·사양 변경 시 해당 채널 기능이 영향을 받는다 |
| 호출 제한 | 채널별 호출 한도로 인해 수집 주기를 무제한으로 단축할 수 없다 |
| 완전 자동화의 한계 | 세트상품·합포장·사은품 등 복합 주문 형태는 자동 처리 대상이 아니다 |

### 7.2 책임 한계

- 본 시스템은 재고 관리를 **보조**하는 도구이며, 최종적인 재고 확인 및 판매 의사결정의 책임은 발주자에게 있다.
- 채널 API의 장애, 사양 변경, 계정 정지 등 개발자가 통제할 수 없는 사유로 인한 손실에 대해 개발자는 책임지지 않는다.
- 재고 동기화 기능은 안전장치를 포함하나, 발주자는 도입 초기 시뮬레이션 모드로 충분히 검증한 후 실제 적용할 것을 권장한다.
- AI 기능(F-10, F-11)이 생성하는 **문장 표현**은 언어 모델의 특성상 어색하거나 부자연스러울 수 있다. 다만 문장에 포함되는 **수치는 데이터베이스에서 산출된 값**이며, 언어 모델이 계산하지 않는다.
- 외부 언어 모델 서비스의 장애·정책 변경·요금 변경은 개발자가 통제할 수 없다. 해당 사유로 AI 기능이 중단되더라도 알림·재고 관리 등 핵심 기능은 정상 동작한다.

### 7.3 유지보수

- 납품 후 **[기간 협의 필요]** 동안 결함 수정은 무상으로 제공한다.
- 채널 API 사양 변경에 따른 대응은 **[유·무상 여부 협의 필요]**.
- 신규 채널 추가, 제외 기능 추가는 별도 협의 및 비용 산정 대상이다.
