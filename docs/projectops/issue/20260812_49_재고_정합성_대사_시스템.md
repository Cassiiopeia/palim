## 📝 개요

발주사 최우선 요구사항. **전산재고(이카운트)와 실재고(3PL)의 정합성을 매일 자동으로 확인**하고, 그 전 단계인 **발주서 생성**까지 자동화한다.

인플루언서 모듈(#41·#43·#45)은 완료 상태로 두고 추가 개발을 멈춘다. 이 작업이 1순위다.

### 현재 업무 흐름

```
이카운트에서 엑셀 추출 → 사람이 3PL 발주서 양식으로 변환 → 3PL 전달 → 3PL 이 발송
```

양쪽 모두 사람이 손으로 다루므로 휴먼에러가 상시 존재하고, 그 결과 두 재고가 어긋난다.

### 발주사가 지목한 불일치

| 유형 | 상태 | 결과 |
|---|---|---|
| 발송 누락 반영 | 실제로 발송했는데 체크가 안 됨 | 전산엔 있는데 실물이 없다 → 판매 후 출고 불가 |
| 유령 발송 | 발송 안 했는데 발송한 것으로 되어 있음 | 전산엔 없는데 실물이 있다 → 팔 수 있는 걸 못 판다 |

## 🛠️ 작업 상세 내용

### 착수 전 반드시 풀어야 할 것

- [ ] **시점 정합** — 두 재고를 다른 시각에 뽑으면 그 사이 출고분만큼 무조건 차이가 난다. "발송했는데 체크 안 됨"도 실제로는 반영 지연일 수 있다. 이걸 분리하지 않으면 매일 수백 건이 떠서 아무도 보지 않게 된다
- [ ] **품목 매칭** — 두 시스템의 품명이 다르다. 매칭이 안 되면 대사 자체가 성립하지 않으므로 "나중에"가 아니라 선행 과제다. 띄어쓰기면 정규화로 되지만 세트 구성이 있으면 매핑 테이블이 필요하다
- [ ] **수집 경로 확인** — 이카운트 OpenAPI 가능 여부, 3PL 어드민 API 여부

### 구현 범위

- [ ] **발주서 생성** — 이카운트 데이터 → 3PL 양식 변환. 시스템이 발주 내역을 갖게 되면 대사가 "예상 재고 vs 실제 재고"로 바뀌어 원인을 발주 건 단위로 추적할 수 있다
- [ ] **재고 정합성 대사** — 스냅샷 수집 → 시점 보정 → 품목 매칭 → 대조 → 유형별 분류 → 금액 환산 정렬 → 조치 상태 추적
- [ ] **품목 매핑 관리 화면** — 자동 매칭 결과, 미매칭 수동 연결, 세트 정의
- [ ] **재고 스냅샷 업로드·조회 화면**
- [ ] 텔레그램 알림 (임계 초과 시)

### 자동·수동 둘 다 1급 경로

연동은 반드시 막히는 날이 있고(인증 만료·점검·양식 변경) 그때 업무가 멈추면 안 된다. 모든 단계에 두 입구를 두고 뒷단은 하나로 합친다.

| 단계 | 자동 | 수동 |
|---|---|---|
| 재고 수집 | API·예약 추출 | 엑셀 업로드 |
| 발주서 | 배치 생성·전달 | 화면에서 생성·다운로드 |
| 대사 실행 | 매일 정해진 시각 | 화면에서 즉시 실행 |
| 결과 확인 | 텔레그램 알림 | 화면 조회 |

### 이번에 하지 않는 것

- 이카운트 재고 입력 자동화 (발주사가 당분간 수동 유지)
- 3PL 내부 프로세스 개선 (통제 밖)
- 재고 예측·발주량 자동 산정 (데이터 축적 후)

### 받아야 할 레퍼런스

| 자료 | 왜 필요한가 |
|---|---|
| 이카운트 재고 엑셀 샘플 | 파서 설계의 입력 |
| 3PL 재고 엑셀·화면 샘플 | 상동 |
| 3PL 발주서 양식 (빈 양식 + 예시) | 발주서 생성의 출력 규격 |
| **실제 불일치 사례 3~5건** | **가장 중요** — 유형과 원인 파악 |
| 이카운트 API 사용 가능 여부 | 자동 수집 성립 여부 |

### 확인 필요 (레퍼런스 수령 후)

1. 두 시스템의 재고 반영 시점이 각각 언제인가 (실시간 / 마감 후 / 익일)
2. 세트 상품이 있는가, 있다면 어느 쪽이 세트로 잡는가
3. 발주서를 3PL 에 어떻게 전달하는가 (메일 / 어드민 업로드 / 연동)
4. 실사는 주기적으로 하는가, 결과는 어디에 반영되는가
5. 불일치를 지금은 어떻게 발견하고 조치하는가
6. 품목이 몇 종인가 (매칭 작업량 산정)
