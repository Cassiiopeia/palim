## 📝 하루에 두 번 담으면 앞엣것이 조용히 사라진다

담긴 재고는 `(원천, 기준 시각, 품목, 창고, 로트)` 로 구분된다. 그런데 기준 시각을 **늘 그날
0시로 내리고 있었다.**

그래서 하루에 두 번 담으면 둘이 **같은 칸을 차지해 나중 것이 앞엣것을 덮는다.** 오전 재고를
다시 볼 방법이 없고, **덮였다는 사실조차 남지 않는다** — 실패도 경고도 아니어서 화면 어디에도
흔적이 없다.

지금은 수집이 하루 한 번뿐이라 드러나지 않는다. 더 자주 돌리는 순간 조용히 자료가 사라진다.

### 하나로 고정할 수 없다

원천마다 실제 해상도가 다르다.

| 원천 | 주는 것 | 필요한 눈금 |
|---|---|---|
| 전산 | 기준일을 **날짜로만** 받는다 | 하루보다 잘게 나눠도 의미가 없다 |
| 물류 | 「지금 재고」 를 준다 | 부른 시각이 곧 기준 시각이다 |

잘게 두면 날짜만 주는 원천이 같은 자료를 **시각만 다른 여러 벌**로 쌓고, 굵게 두면 촘촘히
주는 원천이 **서로를 덮는다.**

### 담는 눈금과 견주는 눈금은 다른 값이다

앞은 「얼마나 촘촘히 남길 것인가」, 뒤는 「얼마나 굵게 맞춰 볼 것인가」다. 물류를 한 시간마다
담아도 전산이 하루 한 번이면 **견주기는 하루로 해야** 두 원천이 같은 칸에 들어온다.

## ✅ 고칠 것

- [ ] 기준 시각의 눈금(하루 / 한 시간 / 십 분 / 받은 그대로)을 **연동마다** 고른다
- [ ] 대조도 **자기 눈금**을 갖는다. 두 기준 시각을 그 눈금으로 내려 같은 칸에 들어오면
      견주고, 합산은 **각 원천이 실제로 가진 시각**으로 한다
- [ ] 견줄 눈금이 담는 눈금보다 **잘면 저장을 막는다.** 안 막으면 대조가 매일 「기준 시각이
      다릅니다」 만 남기는데 설정도 실행도 정상이라 **화면 어디에도 원인이 없다**
- [ ] 두 값 모두 화면에서 고를 수 있어야 한다 — 코드에만 있으면 서버 로그를 뒤져야 하는데
      그럴 수 있는 사람이 쓰는 화면이 아니다
- [ ] 기본값은 **하루** — 지금까지의 동작 그대로라 이미 담긴 자료의 뜻이 바뀌지 않는다

## 🧩 설계 판단

**눈금을 읽으려고 대조가 연동을 뒤지면 안 된다.** 도메인 모듈끼리 직접 의존하지 않는다는
규칙(`docs/02-ARCHITECTURE.md`)이 깨진다. 그래서 대조가 자기 눈금을 따로 들고, 눈금 자체는
두 도메인이 같은 뜻으로 써야 하므로 공용 모듈에 둔다.

**「하루」 를 가르는 지역은 코드 안에 못박는다.** 실행 환경의 기본 지역을 쓰면 CI 는 UTC,
운영은 서울이라 **같은 코드가 다른 뜻**이 된다 — 테스트는 통과하는데 운영에서만 어긋난다.

## 🧪 검증

- 하루 눈금은 같은 날 아침과 오후를 한 칸으로 보고, 시간 눈금은 따로 남긴다
- 하루 경계가 UTC 자정이 아니라 우리 자정이다
- 하루 눈금 대조는 아침에 뽑은 전산과 오후에 뽑은 물류를 견준다 (합산은 각자의 실제 시각으로)
- 시간 눈금 대조는 같은 날이어도 시간이 다르면 여전히 거부한다
- 담는 눈금보다 잘게 잡으면 막고, **어느 연동이 걸렸는지와 무엇을 해야 하는지**를 말한다
- 담는 쪽을 먼저 촘촘하게 바꾸면 견주기도 촘촘해진다 (막다른 길이 아니다)
- 테스트 566건 통과 (신규 12건), 로컬 전체 빌드 성공
