## 📝 창고를 나누지 않고 전부 더해서 견주고 있다

재고를 맡긴 곳은 **자기가 보관 중인 것만** 안다. 그런데 전산 쪽에는 창고가 여럿이다 — 위탁 창고,
사무실, 매장. **지금 대조는 그것을 전부 더해서 견준다.**

`palim-reconcile` 모듈 전체에서 `warehouse` 를 **한 번도 쓰지 않는다.**

```java
// ReconcileDefinition 의 필드 전부 — 창고가 없다
leftSource, rightSource, targetTable, compareField,
tolerance, alertThreshold, breakdownAxis, unitNameRule

// SnapshotAggregator — 창고를 빼고 품목별로 전부 더한다
sum(s.base_quantity) ... WHERE source = :source GROUP BY s.item_ref
```

`std_stock_snapshot` 에는 `warehouse_code`·`warehouse_name` 컬럼이 **있고**, 자연키 인덱스에도
창고가 들어 있다.

```sql
ux_std_stock_snapshot_natural
  ON std_stock_snapshot (tenant_id, source, base_at, item_ref, warehouse_code, lot_code)
```

**자료 구조는 창고를 처음부터 지원했고, 견주는 쪽만 그것을 안 보고 있었다.**

### 무엇이 잘못되나

같은 자료로 두 방식을 견줘 봤다.

| | 전 창고 합산 (지금) | 위탁 창고만 |
|---|---|---|
| 일치한 품목 | **3건** | **11건** |
| 수량이 다른 품목 | **17건** | 4건 |

**맞던 품목까지 틀린 것으로 나온다.** 총합이 크게 벌어지는 것보다 이쪽이 더 나쁘다 — 사람이
「이건 왜 안 맞지」 하고 붙잡는 줄이 실제로는 멀쩡한 줄이기 때문이다.

품목 잇기 화면도 같다. 맡기지 않은 창고에만 있는 품목이 「상대쪽에 짝이 없음」 으로 뜨고,
사람은 있지도 않은 짝을 찾게 된다.

### 확인된 사실

- 상대 시스템의 조회 API 는 창고를 **준다** — 응답에 창고코드·창고명이 들어 있고, 요청에도
  창고를 좁히는 칸이 있다. 지금은 그 칸을 비워 보내 전체를 받는다
- 담당자 확인: **맡긴 곳 = 위탁 창고 하나**. 사무실·매장은 비교군이 없어 사람이 수기로 확인한다

## ✅ 고칠 것

- [ ] 대조 정의에 **견줄 창고**를 둔다. 좌·우 각각 여러 개를 고를 수 있어야 한다
      (한쪽이 여럿이고 반대쪽이 하나인 경우가 흔하다)
- [ ] **비우면 전부** — 지금 동작이므로 이미 만들어 둔 정의가 깨지지 않는다
- [ ] 창고가 여럿인데 고르지 않았으면 **화면이 경고**한다. 조용히 틀린 답을 내는 것보다 낫다
- [ ] 고를 창고 목록은 **담긴 자료에서** 뽑는다. 수량을 함께 보여줘 어느 창고가 맡긴 곳인지
      규모로 알아볼 수 있게
- [ ] 합계·미매칭·품목 잇기 **모든 조회에 같은 범위**를 건다. 한 곳이 빠지면 그 곳만 다른
      숫자를 내고, 「합계는 이런데 뜯어보면 다르다」 가 되어 어느 쪽을 믿을지 알 수 없다

## 어떻게 막을 것인가

원천 이름만 넘기던 시절에는 **창고를 넘길 자리가 없어서** 빠뜨렸다. 원천과 창고를 한 묶음으로
만들어, 새 조회를 만들 때 원천을 넘기는 순간 창고도 함께 넘어가게 한다.
