## 📝 합계는 창고로 좁히는데 뜯어보기는 전 창고를 더한다

대조에 「견줄 창고」 를 넣었지만 **뜯어보기·이름짓기·나누기는 그것을 받지 않는다.**

```java
// 합계 — 창고로 좁힌다
sum(s.base_quantity * m.factor) ... WHERE ... AND s.warehouse_code IN (...)

// 뜯어보기 — 창고 조건이 «전혀 없다»
LEFT JOIN std_stock_snapshot s ON ... AND s.base_at = :baseAt
```

결과 화면에서 **줄의 합계와 그 바로 아래 상세가 다른 수를 말한다.** 두 값이 붙어 있어 어긋남이
즉시 눈에 띄는데, 어느 쪽을 믿을지 알 방법이 없다.

품목 편집 화면은 더 나쁘다. 같은 요청 안에서 멤버 표는 좁힌 수량을, 뜯어보기는 안 좁힌 수량을
만들어 **한 화면에 같은 품목의 서로 다른 수량이 나란히** 그려진다.

### 나누기는 자료까지 바꾼다

「쪼개기」 는 화면만 그리는 게 아니라 묶음을 **실제로 가른다.** 전 창고 값으로 가르면 정의가
안 보기로 한 창고 때문에 묶음이 갈라지고, 쪼개기는 되돌리기가 번거롭다.

### 창고와 무관한 두 번째 통로

뜯어보기가 **`compareField` 도 무시한다.** 엔진은 정의가 고른 칸으로 합산하는데 뜯어보기는
`base_quantity` 를 고정으로 쓴다. 다른 칸을 고른 정의에서는 창고와 별개로 어긋난다.

## ✅ 고칠 것

- [ ] 뜯어보기·이름짓기·나누기가 **원천과 함께 창고를 받는다** (`Pairing`)
- [ ] 견줄 칸도 함께 — 허용 목록을 한 곳에 모은다
- [ ] 창고 조건은 **`ON` 절**에 붙인다. `WHERE` 로 내리면 범위 밖 품목이 줄에서 통째로 사라져
      그 품목을 손댈 자리도 없어진다
- [ ] 범위 밖 품목은 **「없음」 으로 그린다.** `0` 으로 그리면 「재고가 0 이다」 라는 없는 이야기가 된다
- [ ] 이름은 **창고와 무관하게** 가져온다 — 이름은 「무엇」 이지 「얼마」 가 아니다
- [ ] 「고른 기준이 이 자료에 없다」 판정을 **재고가 실제로 있는 품목만** 보고 한다.
      범위 밖까지 세면 원인이 창고인데 「기준을 잘못 골랐다」 고 말하게 된다

## 하지 말 것

**기준 시각을 고르는 조회에는 창고를 걸지 않는다.** 좁히면 그 창고에 자료가 없는 회차를 건너뛰어
더 옛 시각을 고르게 되고, 엔진과 화면이 서로 다른 회차를 견주게 된다.
**시각은 「언제」 이고 창고는 「얼마」 다.**
