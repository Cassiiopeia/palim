# 범용 데이터 연동 프레임워크 — 설계

> 2026-08-12. 외부 시스템 데이터를 표준 모델로 들이는 과정을 **코드가 아니라 화면에서 정의**하는
> 구조. 재고 정합성 대사(#49)를 첫 구현체로 삼되, 연동 엔진 자체는 도메인을 모른다.

## 1. 배경

발주사 업무를 자동화하려면 외부 시스템의 데이터를 우리 안으로 들여와야 한다. 그런데 원천은
회사마다·시스템마다 다르다 — 엑셀로 주기도, JSON으로 주기도, API로 주기도 한다.

원천마다 Java 코드를 새로 쓰면 다음 세 가지가 따라온다.

- 새 발주사·새 원천이 붙을 때마다 배포가 필요하다
- 원천 양식이 바뀌면 코드를 고쳐야 한다
- 도메인 로직과 파싱 코드가 뒤엉켜 어느 쪽도 손대기 어려워진다

**연동 정의를 데이터로 두면 셋 다 사라진다.** 새 원천은 화면에서 커넥터를 하나 더 만드는 일이
되고, 양식 변경은 매핑 버전을 올리는 일이 된다.

## 2. 설계 원칙

| 원칙 | 의미 |
|---|---|
| **수동이 1급, AI는 보조** | AI 버튼을 한 번도 누르지 않아도 전 과정이 완주된다. AI는 빈 칸을 미리 채워줄 뿐이다 |
| **정의는 데이터, 이관은 코드** | AI는 매핑 정의를 만들 때만 개입한다. 매일 도는 실행에는 개입하지 않는다 |
| **런타임 DDL 없음** | 스키마 변경은 전부 Flyway를 거친다. 앱 계정에 DDL 권한을 주지 않는다 |
| **실패는 드러나야 한다** | 애매하면 조용히 통과시키지 않고 실패시킨다. 조용한 오류는 대사 결과가 이상해질 때까지 발견되지 않는다 |
| **재시도가 안전해야 한다** | 자연키 기반 UPSERT. 안심할 수 없으면 사람이 자동화를 켜지 않는다 |

## 3. 전체 구조

```
palim-connector          범용 연동 엔진 (도메인을 모른다)
    ↑
palim-automation         재고 대사 등 도메인 기능
    ↑
palim-web                화면
```

`palim-automation` 안에 두지 않는 이유는, 나중에 다른 도메인이 붙을 때 재고 코드에 의존이
생기기 때문이다. 연동 엔진은 "무엇을 옮기는지" 몰라야 한다.

```
회사마다 원천이 다르다              우리가 원하는 건 하나다
────────────────────           ────────────────────
엑셀 업로드          ┐
JSON 파일            ├→  [커넥터 정의]  →  표준 모델  →  도메인 기능
API 응답             │    (화면에서 만듦)              (대사·리포트·알림)
DB / FTP / 웹훅…     ┘
```

## 4. 핵심 개념 — Connector

**커넥터** = *어떤 원천에서 어떤 목표 모델로 데이터를 가져오는 정의*. 코드가 아니라 DB 행이다.

```
Connector
├─ Source     어디서 가져오나      업로드 / HTTP API (→ 확장 가능)
├─ Schema     원천 필드 구조       헤더에서 자동 추출, AI 초안 선택
├─ Mapping    원천 → 목표 연결     버전을 갖는다
├─ Transform  값 변환·필터·파생    선언적 규칙 + py 훅
└─ Target     목표 모델            기본 제공 or 커스텀
```

## 5. 온보딩 흐름

```
1  연동 만들기      이름 · 목표 모델 선택 (기본 제공 or 새로 정의)

2  원천 붙이기      파일 업로드 / API 등록(URL·인증·응답 경로)
                   → 샘플 데이터 확보, 헤더에서 필드 목록 자동 추출

3  (선택) AI 분석   샘플 → AI → 매핑 초안 + 필드별 신뢰도
                   ※ 여기서만 AI를 부른다. 건너뛰어도 된다

4  관리자 확인      좌: 원천 필드 / 우: 목표 필드, 선으로 연결
                   사람이 끌어서 고치고 변환 규칙 지정
                   원본 5행 → 변환 결과 5행 나란히 미리보기

5  테스트 연동      실제로 적재해본다. run_mode = TEST
                   성공 N · 실패 M · 사유별 목록 · 롤백 버튼

6  후처리 설정      선언적 규칙 / py 훅 지정 → 테스트 재실행으로 확인

7  확정 + 자동화    매핑 ACTIVE 전환, cron 주기 · 실패 알림 대상 등록

8  운영            실행 이력 · 성공률 · 실패 행 조회 · 수동 실행 · 정의 수정
```

각 단계에서 나갔다 돌아와도 이어서 진행한다(매핑은 `DRAFT` 상태로 보존).

## 6. 데이터 모델

### 6-1. 연동 정의 계층

| 테이블 | 역할 |
|---|---|
| `target_model` | 목표 모델. `kind`(BUILTIN/CUSTOM) · `storage`(TABLE/JSONB) · `table_name`(builtin) · `natural_key_fields`(JSONB) |
| `target_field` | 목표 모델의 필드. 키 · 표시명 · 데이터 타입 · 필수 여부 · 기본값 · 순서 |
| `connector` | 연동 하나. 목표 모델 · 원천 유형 · 접속 정보 참조 · cron · 증분 커서 · 활성 여부 |
| `connector_mapping` | **매핑 버전**. `version` · `status`(DRAFT/ACTIVE/ARCHIVED) · 원천 스키마 스냅샷 · 훅 정의 |
| `connector_field_map` | 필드 연결. 원천 필드 → 목표 필드 + 변환 규칙(JSONB) |
| `unit_conversion` | 단위 환산 규칙. 품목별 또는 전역 |

### 6-2. 실행 계층

| 테이블 | 역할 |
|---|---|
| `connector_run` | 실행 1건. **`run_mode`(TEST/LIVE)** · 트리거(MANUAL/SCHEDULED) · **사용한 매핑 버전** · 건수 · 소요 |
| `connector_run_error` | 실패 행. 행 번호 · **원본 행(JSONB)** · 에러 코드 · 메시지 |
| `custom_record` | 커스텀 모델 데이터. `target_model_id` · `run_id` · `payload`(JSONB, GIN 인덱스) |

기본 제공 모델은 각자의 정식 테이블(`item` · `stock_snapshot` · `stock_movement` ·
`outbound_order` — 7장)에 적재하되 `run_id`와 `tenant_id`를 함께 기록한다.

`item_ref`는 품목을 가리키는 문자열 식별자다. 원천의 `item_code`를 우선 쓰고, 코드가 없거나
두 원천의 코드 체계가 무관하면 **정규화된 품명**을 쓴다. 어느 것을 썼는지는 커넥터의 매핑
정의에 남는다 — 실측상 두 원천의 코드 체계가 무관해 이번 구현에서는 품명이 기준이 된다.

### 6-3. 저장 방식 — 하이브리드

```
기본 제공 모델                        커스텀 모델
──────────────────                ──────────────────
정식 테이블                          custom_record
 · 컬럼 · 인덱스 · 제약               · payload JSONB + GIN
 · 평범한 SQL로 조회                  · 모델 정의는 데이터
 · 도메인 기능을 미리 만들 수 있다      · DDL 없이 즉시 추가
```

둘 다 같은 파이프라인을 탄다. 커넥터·매핑·변환·테스트·cron은 목표가 정식 테이블인지 JSONB인지
구분하지 않고, **저장 직전에만 갈라진다.**

동적 DDL을 쓰지 않는 이유:
- Flyway 마이그레이션과 충돌한다. 배포마다 "이 테이블은 누가 만들었나"가 생긴다
- 앱 계정에 DDL 권한이 필요해져 사고 반경이 DB 전체로 커진다
- 실패 시 롤백 경로가 없다

**커스텀 모델 위에는 도메인 기능이 자동으로 붙지 않는다.** 커스텀은 수집·변환·저장·조회·
내보내기까지고, 그 위의 판단 로직이 필요해지면 기본 제공 모델로 승격시킨다. 이 경계를 흐리면
아무 데도 쓸 수 없는 추상화가 된다.

## 7. 기본 제공 목표 모델

물품이면 무엇이든 담기도록 성격이 다른 셋으로 나눈다. 빈 칸을 허용해 업종을 가리지 않는다.

```
품목(Item)          변하지 않는 것 — 이게 무엇인가
재고(Stock)         특정 시점·위치의 상태 — 지금 얼마나 있나
이동(Movement)      사건 — 언제 얼마가 왜 움직였나
```

### 7-1. `item` — 품목 마스터

| 그룹 | 필드 |
|---|---|
| 식별 | `item_code`* · `item_name`* · `barcode` · `external_id` · `spec` · `option_name` |
| 분류 | `category_code` · `category_name` · `brand` · `manufacturer` · `origin_country` |
| 공급 | `supplier_code` · `supplier_name` · `supplier_item_code` · `supplier_item_name` |
| 단위 | `base_unit` · `pack_size` · `weight` · `volume` |
| 금액 | `standard_cost` · `sale_price` · `currency` |
| 상태 | `is_active` · `discontinued_at` |
| 확장 | `attributes` JSONB |

`supplier_item_code`/`supplier_item_name`을 따로 두는 이유 — 같은 물건을 공급처가 다르게
부르는 일은 업종을 가리지 않고 발생한다.

### 7-2. `stock_snapshot` — 시점별 재고

| 그룹 | 필드 |
|---|---|
| 연결 | `item_ref` |
| 시점 | `base_at`* · `source`* · `collected_at` |
| 위치 | `warehouse_code` · `warehouse_name` · `location_code` · `zone_code` |
| 로트 | `lot_code` · `expiry_date` · `manufacture_date` · `serial_no` |
| 수량 | `quantity`* · `unit` · **`base_quantity`** · **`base_unit`** · `available_quantity` · `reserved_quantity` · `defective_quantity` · `incoming_quantity` · `outgoing_quantity` |
| 금액 | `unit_cost` · `amount` · `currency` |
| 상태 | `quality_status` |
| 원본 | `raw_item_name` · `normalized_name` · `product_key` |
| 확장 | `attributes` JSONB |

식품·의약품은 `expiry_date`, 전자제품은 `serial_no`, 원자재는 `lot_code`를 쓴다. 셋 다 두고
빈 칸을 허용한다.

### 7-3. `stock_movement` — 입출고 이력

| 그룹 | 필드 |
|---|---|
| 연결 | `item_ref` · `occurred_at`* |
| 구분 | `movement_type`*(입고·출고·조정·이동·반품·폐기) · `reason_code` |
| 수량 | `quantity`* · `unit` · `base_quantity` · `base_unit` |
| 위치 | `from_warehouse` · `to_warehouse` · `from_location` · `to_location` |
| 로트 | `lot_code` · `expiry_date` |
| 문서 | `document_no` · `document_name` · `reference_no` |
| 주체 | `operator` |
| 확장 | `attributes` JSONB |

### 7-4. `outbound_order` — 출고 주문

| 그룹 | 필드 |
|---|---|
| 주문 | `order_no`* · `order_line_no` · `ordered_at` · `channel` |
| 품목 | `item_ref`* · `quantity`* · `unit_price` |
| 배송 | `receiver_name` · `receiver_phone` · `receiver_address` · `postal_code` · `delivery_memo` · `carrier` · `tracking_no` |
| 상태 | `status` · `shipped_at` |

**이 모델만 개인정보를 담는다.** 보존기간·마스킹·접근권한을 여기에만 걸 수 있도록 분리했다.
다른 모델과 섞었다면 재고 조회 화면까지 개인정보 취급 대상이 됐을 것이다.

### 7-5. `attributes` 확장 슬롯

표준에 없는 필드는 버리지 않고 `attributes` JSONB에 보존한다.

```
원천 컬럼 100개  →  표준 필드에 매핑
                 →  나머지는 attributes 에 그대로
```

처음에는 필요 없어 보이던 컬럼이 나중에 필요해지는 일이 반복된다. 버렸다면 원천에서 다시
받아야 하는데, **과거 시점 데이터는 다시 받을 수 없다.**

**승격 경로**: `attributes`의 특정 키가 여러 커넥터에서 반복 사용되면 정식 마이그레이션으로
표준 필드에 추가한다. 런타임 DDL 없이, Flyway를 거쳐서. 모델이 실사용을 따라 자란다.

## 8. 확장성 장치

### 8-1. 멀티테넌시 — 문만 열어둔다

모든 테이블에 `tenant_id`를 둔다. 지금은 기본 테넌트 하나로 운영한다.

조회의 테넌트 필터는 **리포지토리 기반 클래스 한 곳에서 강제**한다. 각 쿼리에 맡기면 반드시
빠뜨리는 곳이 생기고, 그것이 곧 데이터 유출이다.

나중에 넣으려면 모든 테이블 컬럼 추가 + 모든 쿼리 수정 + 기존 데이터 소급이 필요하다. 지금은
컬럼 하나와 인덱스 하나 값이다.

### 8-2. 단위 환산

수량은 원본과 환산값을 **둘 다** 저장한다.

```
quantity       12        원본 수량
unit           BOX       원본 단위
base_quantity  144       기준 단위 환산값   ← 대사·집계는 이것만 쓴다
base_unit      EA        기준 단위
```

`unit_conversion`에서 품목별 규칙 → 전역 규칙 순으로 찾는다.

**규칙이 없으면 1:1로 넘기지 않고 실패시킨다.** 조용히 통과시키면 BOX 12개가 EA 12개로
둔갑하고, 그 오류는 대사 결과가 이상해질 때까지 아무도 모른다. 적재 실패로 드러나는 편이 낫다.

### 8-3. 증분 수집과 자연키

```
incremental_mode   FULL | INCREMENTAL
cursor_field       updated_at / occurred_at 등
cursor_value       마지막으로 가져온 값
```

성공한 실행만 커서를 전진시킨다. 실패하면 그대로 두어 다음 실행이 같은 구간을 다시 가져온다.

그래서 **자연키**가 필수다. 목표 모델마다 "무엇이 같으면 같은 행인가"를 정의하고
(`target_model.natural_key_fields`), 적재는 INSERT가 아니라 **UPSERT**로 한다.

```
stock_snapshot 자연키 = tenant + source + base_at + item_ref + warehouse + lot
```

같은 구간을 두 번 가져와도 중복이 생기지 않는다. 재시도가 안전해야 자동화가 안심되고,
안심돼야 사람이 실제로 자동화를 켠다.

## 9. 안정성 장치

### 9-1. 스키마 드리프트 감지

이런 시스템의 최악 실패는 **원천 양식이 바뀌었는데 조용히 잘못된 데이터가 들어가는 것**이다.

매 실행마다 원천 필드 목록을 `connector_mapping`의 스냅샷과 대조하고, 다르면 **적재하지 않고
중단 + 알림**한다. 사람이 새 매핑 버전을 확정해야 재개된다.

### 9-2. 부분 실패를 기본으로

1000행 중 3행이 깨졌다고 전체를 버리지 않는다. 성공분은 적재하고 실패 3행은 원본째로
`connector_run_error`에 남긴다. `전부-아니면-전무` 모드는 옵션으로 둔다.

### 9-3. 실행 단위 롤백

모든 적재 행에 `run_id`가 있어 한 실행분만 정확히 지운다. 테스트가 부담 없어지고, 잘못 돌린
운영 실행도 되돌릴 수 있다. **부담 없이 테스트할 수 있어야 사람이 실제로 테스트한다.**

### 9-4. 동시 실행 차단

cron과 수동 실행이 겹치는 순간은 반드시 온다. 커넥터 단위 락을 건다.

### 9-5. 비밀값 분리

API 키·비밀번호는 기존 암호화 저장을 재사용하고 `connector`에는 참조만 둔다. 이 저장소는
PUBLIC 이며, **DB 덤프가 유출돼도 키가 새지 않아야 한다.**

## 10. AI의 역할과 경계

| | 수동 (기본) | AI (보조) |
|---|---|---|
| 스키마 파악 | 헤더를 읽어 필드 목록 자동 생성 | — |
| 필드 매핑 | 화면에서 좌↔우 연결 | **초안 채우기** — 제안만, 확정은 사람 |
| 변환 규칙 | 드롭다운 선택 | 제안 |
| 검증 | 미리보기로 눈 확인 | — |

- AI 출력은 **구조화 출력(json_schema)** 으로 받아 코드가 검증한다
- AI가 만드는 것은 **선언적 매핑 정의**뿐이다. 코드를 만들어 실행하지 않는다
- AI 호출 실패·미설정이어도 흐름이 끊기지 않는다. 빈 칸으로 시작할 뿐이다
- **매일 도는 실행에는 AI가 개입하지 않는다.** 비용이 들지 않고, 같은 입력에 같은 결과가 나온다

### 원본 전송 범위 — 규칙 충돌 기록

연동 정의 생성 시 **파일 전체를 AI에 보낸다**(오너 결정). 이는 `CLAUDE.md` 6번
("AI 에는 필요한 컬럼만 보낸다 — 개인 식별자·전화번호는 마스킹 후 전송")과 충돌한다.

완화 요소:
- AI 호출은 **최초 연동 설정 1회**뿐이다. 이후 cron 실행에서는 한 번도 나가지 않는다
- 재고·품목·이동 모델에는 개인정보가 없다. `outbound_order`만 해당된다

**구현 전에 `CLAUDE.md` 6번을 개정하거나 예외를 명시해야 한다.** 그대로 두면 리뷰·CI에서
혼선이 생긴다.

## 11. 후처리

| 층 | 무엇 | 정의 방식 |
|---|---|---|
| **선언적 규칙** | 값 변환(날짜 포맷·코드 치환) · 행 필터 · 파생 컬럼 · 기본값 | 화면에서 선택 |
| **py 훅** | 규칙으로 안 되는 커스텀 | `scripts/` 스크립트 |

SQL 직접 실행은 넣지 않는다. 공개 저장소이고 여러 사용자가 쓸 제품이라 임의 SQL은 한 번
뚫리면 DB 전체가 열린다.

py 훅은 **DB에 직접 손대지 않는다.** 데이터를 받아 가공된 데이터를 돌려줄 뿐이라 잘못 짜도
테이블이 날아가지 않고, 단독 실행으로 테스트할 수 있다. 호출 규약은 `04-CONVENTIONS`의
py 규약(인자 배열 · stdout JSON only · `PYTHONIOENCODING=utf-8` · 타임아웃 +
`destroyForcibly` · 전용 스레드풀)을 그대로 따른다.

## 16. 실측 근거

원천 두 곳을 실제로 열어 확인한 결과다. 시스템 이름은 코드·문서에 남기지 않고
`ERP`(전산재고) / `WAREHOUSE`(실재고) 일반명으로 표기한다.

| 확인 항목 | ERP | WAREHOUSE |
|---|---|---|
| API 제공 | 있음 (무료) | 있음 (유료 — 발주사 판단 필요) |
| 재고 조회 | 기준일 지정 가능 | 기준일 지정 가능 (과거 재고 조회) |
| 입출고 이력 | — | 전표 단위로 존재 |
| 단가·금액 | 재고단가·재고금액 제공, 원가 기준 4종 선택 | 원가 컬럼 존재 |
| 품목코드 체계 | 의미 기반 (`{제품약어}_{유통기한}`) | 5자리 순번 |
| 품목명 | `제품명 용량 (유통기한)` | **동일 형식, 문자열까지 일치** |
| 로트 관리 | 유통기한별 별도 품목 | 유통기한별 별도 품목 |
| 품목 규모 | 24종 | 24종 |

**설계에 반영된 사실:**

- 두 시스템의 **품목코드 체계가 무관**하다 → 코드는 매칭 키로 쓸 수 없다
- **품목명은 완전히 일치**한다 → 품명(로트 포함)이 매칭 키
- **양쪽 모두 로트별 별도 품목**이다 → 로트 단위 대사가 자연스럽다
- ERP가 **기준일 지정 조회**를 지원한다 → 시점 정합 문제의 절반이 해결된다
- WAREHOUSE의 출고 주문 양식 필수 필드에 **수령자명**이 있다 → 개인정보 모델을 분리해야 한다

주의: 발주사 상호·브랜드·제품명·계정명·채널 URL은 이 문서를 포함해 저장소 어디에도 남기지
않는다(`CLAUDE.md`).
