# 재고 정합성 대사 — 요구사항 정리

> 2026-08-12 발주사 통화 내용을 정리한 초안. **확정 설계가 아니라 착수 전 합의용 문서**다.
> 레퍼런스(엑셀 샘플·발주서 양식·불일치 사례)를 받으면 이 문서를 갱신한 뒤 설계로 넘어간다.
>
> 이 작업이 **최우선**이며, 인플루언서 모듈(#41·#43·#45)은 완료 상태로 두고 추가 개발을 멈춘다.

## 1. 배경

발주사는 재고를 두 시스템으로 관리한다.

| 시스템 | 성격 | 관리 방식 |
|---|---|---|
| 이카운트 | **전산재고** — 장부상 수량 | 수동 입력 (자동화는 후속 과제) |
| 3PL | **실재고** — 창고의 물리적 수량 | 3PL 담당자 수동 처리 |

현재 업무 흐름:

```
이카운트에서 엑셀 추출
   → 사람이 3PL 발주서 양식에 맞춰 변환
   → 3PL 에 전달
   → 3PL 이 보유 재고에서 발송
```

두 시스템 모두 사람이 손으로 다루므로 **휴먼에러가 상시 존재**하며, 그 결과 전산재고와 실재고가
어긋난다. 이 불일치를 **매일 자동으로 확인**하는 것이 이번 과제다.

## 2. 문제 — 불일치의 유형

발주사가 지목한 것은 두 가지다.

| 유형 | 상태 | 결과 |
|---|---|---|
| **발송 누락 반영** | 3PL 이 실제로 발송했는데 체크가 안 됨 | 전산은 재고가 있다고 보는데 실물이 없다 → 판매 후 출고 불가 |
| **유령 발송** | 발송하지 않았는데 발송한 것으로 되어 있음 | 전산은 재고가 없다고 보는데 실물이 있다 → 팔 수 있는 것을 못 판다 |

여기에 실무상 함께 나타나는 유형을 더하면:

| 유형 | 내용 |
|---|---|
| 수량 오차 | 발송은 맞는데 수량이 다르다 |
| 입고 미반영 | 입고했는데 한쪽에만 잡혀 있다 |
| 반품·교환 미반영 | 되돌아온 물량이 반영되지 않았다 |
| 파손·분실 | 실물만 줄었다 |
| **품목 매칭 실패** | 같은 제품인데 두 시스템의 품명이 달라 대조 자체가 안 된다 |

**조치 방법이 유형마다 다르므로, 시스템은 "몇 개 차이난다"가 아니라 "어떤 유형인지"를 말해야 한다.**

## 3. 착수 전에 반드시 풀어야 할 것 세 가지

### 3-1. 시점 정합 — 가짜 불일치를 먼저 없애야 한다

**두 시스템의 재고를 서로 다른 시각에 뽑으면 그 사이 출고분만큼 무조건 차이가 난다.** 오전에
이카운트를 뽑고 오후에 3PL 을 뽑으면 그날의 출고가 전부 불일치로 잡힌다.

"3PL 이 발송했는데 체크가 안 된다"는 현상도 **실제로는 반영 지연일 수 있다** — 발송은 됐는데
전산 반영이 다음 날 아침이라면 그건 오류가 아니라 정상 시차다.

이걸 분리하지 않으면 매일 수백 건이 뜨고, 그러면 아무도 보지 않는다. **이 시스템의 성패가 여기서
갈린다.**

필요한 것:

- 양쪽 스냅샷의 **기준 시각을 맞추는 규칙** (예: 전날 자정 마감 기준으로 통일)
- 시스템별 **반영 지연 시간**을 설정값으로 두고, 지연 범위 안의 차이는 "확인 대기"로 분류
- 며칠 연속 같은 차이가 유지되면 그때 진짜 불일치로 승격

### 3-2. 품목 매칭 — 이것이 실질적 1번 과제다

"띄어쓰기 정도 다르다"고 들었으나, **매칭이 되지 않으면 대사 자체가 성립하지 않는다.** 대조
로직을 만들어놓고 품목이 붙지 않아 못 쓰는 것이 이런 과제의 전형적인 실패 방식이다.

띄어쓰기·대소문자만이면 정규화로 끝나지만, 실무에서는 보통 다음이 섞여 있다:

| 유형 | 예 | 해결 |
|---|---|---|
| 표기 차이 | `상품A 블랙` / `상품A블랙` | 정규화(공백·특수문자 제거) |
| 옵션 표기 | `블랙/L` / `블랙 L사이즈` | 정규화 + 규칙 |
| 약어·모델명 | `XY-100` / `XY100` | 정규화 |
| **세트 구성** | 이카운트 세트 1개 = 3PL 낱개 3개 | **정규화 불가 — 매핑 테이블 필요** |

세트가 있으면 자동 매칭으로 해결되지 않는다. 필요한 것:

- 정규화 규칙 + **품목 매핑 테이블**(화면에서 관리)
- **미매칭 리포트** — 자동으로 붙지 않은 품목을 사람이 한 번 이어주면 그 뒤로는 자동
- 매칭률을 화면에 노출 — 매칭률이 낮으면 대사 결과 자체를 신뢰할 수 없다는 신호다

레퍼런스를 받으면 **이 부분부터 확인**한다.

### 3-3. 자동과 수동을 <b>둘 다</b> 1급 경로로 만든다

**"자동이 기본이고 수동은 예비"가 아니다.** 두 경로 모두 상시 동작해야 한다. 이유가 셋이다.

1. API 사용 가능 여부가 아직 확정되지 않았다 — 안 되면 수동이 유일한 경로가 된다
2. 되더라도 **연동은 반드시 막히는 날이 있다**(인증 만료·점검·양식 변경). 그때 업무가 멈추면 안 된다
3. 특정 날짜를 다시 대사하거나 결과를 검증할 때 사람이 직접 넣을 수 있어야 한다

그래서 **모든 단계에 자동·수동 두 입구를 만들고, 뒷단은 하나로 합친다.**

| 단계 | 자동 | 수동 | 뒷단 |
|---|---|---|---|
| 이카운트 재고 | API 또는 예약 추출 | 엑셀 업로드 | 동일한 표준 스냅샷 |
| 3PL 재고 | API 또는 예약 추출 | 엑셀 업로드 | 동일한 표준 스냅샷 |
| 발주서 생성 | 배치가 만들어 전달 | 화면에서 생성·다운로드 | 동일한 발주 기록 |
| 대사 실행 | 매일 정해진 시각 | 화면에서 "지금 실행" | 동일한 대조 로직 |
| 결과 확인 | 텔레그램 알림 | 화면 조회 | 동일한 리포트 |

```
[이카운트 API]  ┐                    ┌ 자동: 매일 배치
                ├→ 표준 재고 스냅샷 →┤            → 품목 매칭 → 대조 → 리포트 → 알림
[엑셀 업로드]   ┘                    └ 수동: 지금 실행
[3PL API]       ┐
                ├→ 표준 재고 스냅샷
[엑셀 업로드]   ┘
```

**핵심은 스냅샷을 표준 형태로 통일하는 것**이다. 어디서 들어왔든 저장된 뒤에는 구분이 없고,
대조·리포트·알림은 출처를 알 필요가 없다. 스냅샷에 <b>출처(API/업로드)와 기준 시각</b>만 남겨
나중에 "이 결과는 무엇으로 대사한 것인가"를 설명할 수 있게 한다.

수집 경로 확인이 필요한 항목:

| 시스템 | 확인할 것 |
|---|---|
| 이카운트 | OpenAPI 사용 가능 여부(유료 옵션일 수 있음). 불가 시 예약 추출·엑셀 내려받기 방식 |
| 3PL | 어드민에 API 가 있는지, 엑셀 내려받기만 되는지 |

<b>확인 결과와 무관하게 착수할 수 있다</b> — 수동 경로를 먼저 만들면 그것만으로 지금 수작업을
대체하고, API 가 열리면 자동 경로를 추가로 꽂으면 된다.

## 4. 범위

### 이번에 만드는 것

**① 발주서 생성** (자동 생성 · 수동 생성 모두)

```
이카운트 엑셀/API → 발주 대상 산출 → 3PL 양식으로 변환 → 발주 기록 저장
                                                        → 다운로드 또는 자동 전달
```

반복 수작업을 없애는 것 자체가 가치이지만, 더 중요한 것은 **시스템이 발주 내역을 갖게 된다**는
점이다. 그러면 대사가 단순 총량 비교에서 다음으로 바뀐다:

```
어제 실재고 − 발주 수량 = 오늘의 예상 실재고
                            ↕ 비교
                        오늘 3PL 실재고
```

차이가 나면 **어느 발주 건에서 어긋났는지**까지 짚인다. 두 총량만 비교하면 "10개 차이남"만 알고
원인을 찾을 수 없다.

**② 재고 정합성 대사** (매일 자동 + 화면에서 즉시 실행)

- 양쪽 스냅샷 수집 → 시점 보정 → 품목 매칭 → 대조
- 불일치를 **유형별로 분류**하고 원인을 추정
- **금액으로 환산해 정렬** — 1개 차이나는 저가품 50건보다 3개 차이나는 고가품 1건이 먼저 보여야 한다
- 조치 상태 추적(확인·해결) — 같은 건을 매일 다시 보고하지 않기 위해
- 텔레그램 알림 (임계 초과 시)

**③ 품목 매핑 관리 화면**

- 자동 매칭 결과 확인, 미매칭 품목 수동 연결, 세트 구성 정의

**④ 재고 스냅샷 업로드·조회 화면**

- 엑셀 업로드(수동 경로의 입구), 수집 이력, 스냅샷별 출처·기준 시각 확인

### 이번에 하지 않는 것

| 항목 | 이유 |
|---|---|
| 이카운트 재고 입력 자동화 | 발주사가 당분간 수동으로 하겠다고 확인 |
| 3PL 내부 프로세스 개선 | 우리 통제 밖 |
| 재고 예측·발주량 자동 산정 | 데이터 축적 후 |

## 5. 허용 오차 — 0을 목표로 하지 않는다

양쪽 다 수동 처리이므로 오차는 상시 존재한다. 완전 일치를 목표로 하면 매일 경고가 뜨고 곧
무시된다.

- 품목별 **허용 오차**와 **금액 임계**를 설정값으로
- 임계 미만은 기록만, 초과분만 알림
- 며칠 연속 유지되는 차이를 우선 노출 (일시적 시차와 구분)

## 6. 기술 스택 — 현재 구성으로 충분하다

| 필요 | 현재 보유 |
|---|---|
| 엑셀 파싱 | `scripts/` py 규약 + pandas (04-CONVENTIONS) |
| 대조·저장 | Spring Boot + PostgreSQL |
| 매일 자동 실행 | `@Scheduled` 배치 |
| 알림 | `palim-notification` 텔레그램 Outbox |
| 화면 | Thymeleaf + daisyUI |
| 설정 변경 | `SystemConfig` — 임계·허용오차를 재기동 없이 조정 |
| AWS 이전 | Docker 단일 이미지 — 이미지 이동이 곧 이전(06-OPERATIONS) |

**새로 추가할 스택은 없다.** 신규 모듈은 `palim-automation` 에 만든다.

> 기존 재고 도메인(`palim-sku`·`palim-order` 등)은 **동결 상태이며 수정하지 않는다**
> (07-DECISIONS 023). 개념만 참고하고 코드는 새로 작성한다.

## 7. 레퍼런스로 받아야 할 것

| 자료 | 왜 필요한가 |
|---|---|
| 이카운트 재고 엑셀 샘플 | 실제 컬럼 구조 — 파서 설계의 입력 |
| 3PL 재고 엑셀·화면 샘플 | 상동 |
| **3PL 발주서 양식** (빈 양식 + 작성 예시) | 발주서 생성의 출력 규격 |

| 이카운트 API 사용 가능 여부 | 자동 수집 성립 여부 |
| 3PL 어드민 기능 범위 | 상동 |

## 8. 열린 질문 (레퍼런스 확인 후 답할 것)

1. 두 시스템의 재고 반영 시점이 각각 언제인가? (실시간 / 마감 후 / 익일)
2. 세트 상품이 있는가? 있다면 어느 쪽이 세트로 잡는가?
3. 발주서를 3PL 에 어떻게 전달하는가? (메일 / 어드민 업로드 / 시스템 연동)
4. 재고 조사(실사)는 주기적으로 하는가? 그 결과는 어디에 반영되는가?
5. 불일치를 지금은 어떻게 발견하고 조치하는가? — 현재 프로세스를 알아야 대체할 수 있다
6. 품목이 몇 종인가? (매칭 작업량 산정)
