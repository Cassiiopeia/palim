# API 원천 수집과 칸 연결 설계

**상태**: 확정 대기
**관련**: 이슈 #68 (연동 준비 상태판), #49 (재고 정합성 대사)

## 무엇을 푸는가

이카운트 API 연결(인증)은 동작한다. 그런데 **그 뒤가 끊겨 있다.**

연결을 마치고 매핑 화면에 가면 엑셀 파일을 올리라고 한다. API 로 칸 이름을 이미 받아왔는데도
그렇다. 실행(시험·적재)도 파일 업로드뿐이라 **매일 자동으로 수집할 경로가 없다.**

원인은 하나다. `SourceReader` 구현체가 `UploadSourceReader` 하나뿐이고 `HTTP_API` 용이 없다.
그래서 API 로 연결해도 그 뒤 모든 단계가 파일 경로로만 흐른다.

## 이미 있는 것 — 새로 만들지 않는다

| 갖춰진 것 | 역할 |
|---|---|
| `SourceReader` (인터페이스) | `readSchema()` 칸+샘플 · `read()` 전체. 매핑용과 실행용을 나눠 둠 |
| `SourceReaderRegistry` | 원천 유형 → 어댑터. 분기 없이 구현체만 늘리면 됨 |
| `SourceContext` | `config` 로 원천별 설정을 받음. 파일은 UPLOAD 전용 |
| `Connector` | `sourceType` · `credentialRef` · `scheduleCron` |
| `ConnectorMapping` | 매핑 버전 + 확정 당시 칸 목록(양식 변화 대조용) |
| `connector_staging` | 시험 실행 결과. 운영 테이블에 닿지 않음 |
| `custom_record` | 표준 모델에 없는 자료. 런타임 DDL 없이 늘어남 |
| `StandardModelFields` | 표준 모델 정의. 구현체를 빈으로 등록하면 필드가 자동 등록됨 |

**뼈대는 맞게 서 있다.** 빠진 조각을 채우고 화면을 고치는 일이다.

## 만들 것

### 1. `EcountSessionClient` — 인증을 검증에서 떼어낸다

지금 지역조회·로그인·조회 로직이 `ZoneSessionProbe` 안에 있다. 그런데 그 클래스는 **연결
확인용**이라 단계별 성공/실패를 기록하는 것이 목적이다. 실행 경로에서 필요한 것은 데이터뿐이다.

```
EcountSessionClient          지역조회 → 로그인 → 데이터조회 (순수 기능)
  ├── ZoneSessionProbe       단계별로 기록      (연결 확인 화면)
  └── HttpApiSourceReader    데이터만 받음      (매핑·시험·적재)
```

같은 인증을 두 벌 짜지 않는다. 연결 확인에서 이미 검증된 코드로 실제 수집이 돈다.

### 2. `HttpApiSourceReader` — 빠진 조각

`SourceType.HTTP_API` 를 담당한다.

- `readSchema()` — 소량 조회 후 칸 이름과 샘플 5행. 매핑 화면과 양식 변화 대조에 쓴다
- `read()` — 전체 조회. 호출자가 청크로 소비한다
- 인증 정보는 `Connector.credentialRef` 로 `ConnectorSecretService` 에서 꺼낸다.
  `SourceContext.config` 에는 비밀값을 넣지 않는다

이것 하나로 매핑 화면·시험 실행·자동 수집이 전부 API 로 흐른다.

### 3. 칸 연결 화면 재작성

지금 화면은 「목표 필드 / 원천 컬럼 / 변환 / 변환 값」 네 칸이고 `fieldKey`·`STRING`·`NONE`
같은 것이 그대로 노출된다. **무엇보다 원천 값이 보이지 않아 무엇을 고를지 판단할 수 없다.**

바꿀 형태:

```
우리 항목        저쪽 칸              실제로 들어올 값
품목 *          [PROD_CD ▾]         A16P_26.11.07 · B227P_26.10.17
수량 *          [BAL_QTY ▾]         112 · 9,451 · 4      ⚠ 음수 1건
출처 *           자동                 이 연동 이름이 들어갑니다
기준 시각 *      자동                 받아온 시각이 들어갑니다
단위            [직접 입력] EA        모든 줄에 EA
```

원칙 넷:

- **고르면 그 칸의 실제 값이 옆에 뜬다.** 이 화면의 존재 이유다
- **표준 항목은 전부 보여주되 성격별로 묶는다.** 숨기지 않는다
- **`source`·`base_at` 은 「자동」.** 원천에 있을 수 없는 값이므로 묻지 않는다
- **「변환」·「변환 값」 칸은 없앤다.** 아래 5번 참고

화면을 열 때마다 `readSchema()` 로 최신 값을 다시 받는다. 상대가 칸을 바꾸면 그 자리에서
드러난다. 실패하면 확정 당시 저장된 칸 목록을 쓴다.

### 4. 표준에 자리가 없는 칸

원천은 자기만의 칸을 준다(규격·비고·담당자). 지금도 버리지 않고 보관하지만 화면이 작은 글씨로
`attributes 에 보존됩니다` 라고만 써서 **사람은 자기 자료가 어디 갔는지 모른다.**

별도 구역을 두고 값과 함께 보여준다. 셋 중 하나를 고른다:

- **그대로 보관** — 값은 남지만 대조·집계에 쓰지 않는다 (기본값)
- **받지 않기** — 저장하지 않는다
- **우리 항목으로 만들기** — 이름을 붙여 표준 항목으로 승격한다

세 번째가 확장점이다. 새 원천이 낯선 칸을 줄 때마다 코드를 고쳐야 한다면 확장성이 없다.

### 5. 변환은 자동으로, 실패만 보여준다

표준 테이블은 타입을 갖는다(`quantity numeric(19,3)`, `base_at timestamptz`). 원천은 전부
문자열로 온다. 그러므로 변환은 불가피하다 — 수량이 문자열이면 `"112"` 와 `"112.000"` 이 다른
값이 되어 합산도 비교도 못 하고, **재고 대조 자체가 성립하지 않는다.**

그러나 **변환 규칙을 사람에게 고르게 하지 않는다.** 무엇을 골라야 할지 알 수 없고, 골라도
맞았는지 확인할 방법이 없다.

```
"9,451"          → 9451     자동
"-1.0000000000"  → -1       자동
"2026-08-13"     → 시각      자동
"-"              → 실패      → 그 줄만 시험 실행 결과에 나온다
```

`TransformType` 에 **`CONSTANT`** 를 더한다. 「직접 입력」(단위 = EA)을 저장하는 데 쓴다.
원천 칸 없이 값만 갖는 매핑이다.

### 6. 시험 실행 결과 화면 재작성

`connector_staging` 과 조회·화면이 이미 있지만 `payload` JSON 을 그대로 뿌려 읽을 수 없다.

```
시험 실행 결과            45건 중 43건 담김 · 2건 실패
진짜 자료에는 아직 아무것도 들어가지 않았습니다.

품목            창고            수량      단위   기준 시각
A16P_26.11.07   200 본사 창고     112      EA    2026-08-13 18:33
A16P_26.11.07   300 외부 물류    9,451     EA    2026-08-13 18:33

담지 못한 줄 2건 — 이 줄만 빠지고 나머지는 담깁니다
  2번째 줄   수량이 「-」 라 숫자로 바꿀 수 없습니다   [건너뛰기 ▾]
  17번째 줄  품목 칸이 비어 있습니다                [건너뛰기 ▾]

▸ 저쪽이 보낸 값 그대로 보기
```

「아직 안 들어갔다」를 가장 먼저 말한다. 이걸 모르면 확인을 대충 하게 된다.

### 7. 파일 없이 실행

매핑 화면의 시험 실행·실제 적재가 파일 업로드를 강제한다. API 커넥터면 파일칸 대신
**「지금 가져와서 실행」** 을 보여준다. `ConnectorRunner` 는 이미 레지스트리로 어댑터를
고르므로 뒷단은 그대로다.

### 8. 스케줄

`Connector.scheduleCron` 이 이미 있다. 확정된 매핑을 가진 API 커넥터를 주기 실행하는
스케줄러를 붙인다. 이것이 붙으면 **#49 재고 대조의 입력이 매일 자동으로 쌓인다.**

실패는 조용히 넘어가지 않는다. 연속 실패·양식 변화는 목록 화면에 드러나야 한다 —
매일 도는 일은 잘 돌 때 아무도 보지 않으므로, 멈췄을 때 찾아와 말해주지 않으면 몇 주가 지나간다.

## 자동 추천은 이 문서에 없다

원천 칸을 어느 표준 항목에 연결할지 **짐작하는 일**은 관심사가 다르다. 별도 문서로 분리한다.
→ `2026-08-13-field-suggestion-design.md`

이 문서의 화면은 추천 결과를 **미리 골라진 상태**로 받기만 한다. 추천이 없어도 화면은 동작한다.

## 다루지 않는 것

- **원천 SQL·스크립트 직접 입력** — 참조한 레거시 관리자 시스템에는 있으나 넣지 않는다.
  그것이 있는 순간 개발자만 쓸 수 있는 화면이 된다
- **여러 응답 합치기(조인)** — 이카운트·3PL 은 한 번에 온다. 필요해질 때 넣는다
- **DB 직결·LDAP 원천** — `SourceReader` 를 구현하면 붙지만 지금 필요 없다

## 검증

- `HttpApiSourceReader` — 로컬 HTTP 서버를 띄워 `readSchema`/`read` 가 칸과 행을 돌려주는지
- `CONSTANT` 변환 — 원천 칸 없이 고정값이 모든 행에 들어가는지
- 시험 실행 — 실패 행이 운영 테이블에 닿지 않고 스테이징에만 남는지
- 화면 — 값이 비었을 때 오류 코드가 아니라 사람 문장이 나오는지 (이미 회귀 테스트 있음)
