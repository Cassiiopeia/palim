# 칸 연결 자동 추천 설계

**상태**: 확정 대기
**관련**: 이슈 #68, `2026-08-13-api-source-and-mapping-design.md`

## 무엇을 푸는가

원천이 준 칸(`BAL_QTY`)을 어느 표준 항목(`quantity`)에 연결할지 **미리 골라 둔다.**

빈 화면을 주면 사람은 표준 항목 29개를 하나씩 훑으며 매번 처음부터 고른다. 원천이 늘 때마다
그 일이 반복되고, 시스템이 열 개가 되면 열 번 한다.

**추천일 뿐 확정이 아니다.** 사람이 보고 고친다. 틀린 추천은 빈 칸보다 나쁘지 않다 — 어차피
확인해야 하고, 맞은 것은 그냥 두면 된다.

## 왜 따로 두는가

칸을 **연결하는 일**(화면)과 어디로 갈지 **짐작하는 일**(추론)은 관심사가 다르다. 섞으면
화면 코드에 점수 계산이 들어가고, 추론을 고칠 때마다 화면을 건드리게 된다.

분리하면 추천 없이도 화면이 동작한다. 화면은 "미리 골라진 상태"를 받기만 한다.

## 근거 네 가지를 점수로 합친다

하나만 쓰면 반드시 틀린다. 각 근거가 독립적으로 점수를 내고 합산한다.

| 근거 | 무엇을 보나 | 점수 | 한계 |
|---|---|---|---|
| **사전** | 표준 항목에 미리 적어 둔 별칭과 일치하나 | 100 | 우리가 아는 이름만 |
| **예전 기록** | 전에 이 이름을 어디에 연결했나 | 90 | 처음엔 비어 있음 |
| **이름 규칙** | 이름에 `QTY`·`수량`·`STOCK` 이 들어있나 | 60 | 오탐 가능 |
| **값 모양** | 전부 숫자인가 · 날짜 꼴인가 | 40 | 수량과 단가를 구분 못함 |

합산 최고점을 미리 고른다. 동점이거나 최고점이 낮으면(임계 미만) 고르지 않고 비워 둔다 —
**틀린 추천보다 빈 칸이 나은 경우는 근거가 약할 때뿐이다.**

## 네 가지 중 「예전 기록」이 핵심이다

사전은 우리가 아는 이름만 잡는다. 이카운트·3PL 은 적어 둘 수 있지만 **다음에 붙일 시스템의
칸 이름은 알 수 없다.**

```
사장님이 새 시스템의 STOCK_BALANCE 를 「수량」에 한 번 연결한다
      ↓  그 사실을 기록한다
다음에 STOCK_BALANCE 가 오면 시스템이 먼저 골라 둔다
```

쓸수록 맞는다. 우리가 모르는 시스템도 **한 번만 손대면 그 뒤로는 자동**이다. 이것이 "어디서든
잘 작동한다"의 실체다.

## 구조

```
palim-connector/suggest/
  FieldSuggester        진입점. 원천 칸 목록 + 샘플 → 항목별 추천
  SuggestionSource      근거 하나 (인터페이스)
    ├ AliasSource         사전
    ├ HistorySource       예전 기록
    ├ NamePatternSource   이름 규칙
    └ ValueShapeSource    값 모양
  FieldSuggestion       결과 — 표준 항목 · 점수 · 근거 목록
```

근거를 더할 때 `SuggestionSource` 구현체를 빈으로 등록하면 된다. `FieldSuggester` 는 고치지
않는다. 원천 어댑터가 `SourceReader` 로 늘어나는 것과 같은 방식이다.

**근거를 결과에 남긴다.** "왜 이걸 골랐는지"를 화면이 말할 수 있어야 한다 —
`전에 3번 이렇게 연결하셨습니다` 처럼.

## 사전은 표준 모델 정의에 함께 둔다

별칭은 표준 항목의 성질이지 별도 자료가 아니다. `FieldDefinition` 에 함께 적는다.

```java
required("quantity", "수량", DECIMAL,
         aliases("BAL_QTY", "QTY", "STOCK_QTY", "수량", "재고수량"))
```

새 필드를 추가할 때 별칭도 같은 자리에 적게 되므로 따로 관리할 것이 늘지 않는다.
기존 호출부는 별칭 없이도 그대로 컴파일된다(오버로드).

## 예전 기록 저장

```sql
CREATE TABLE field_mapping_memory
(
    id              uuid         NOT NULL,
    tenant_id       uuid         NOT NULL,
    -- 원천 칸 이름. 대소문자·공백을 정규화해 저장한다
    source_field    varchar(200) NOT NULL,
    target_model    varchar(100) NOT NULL,
    target_field    varchar(100) NOT NULL,
    -- 몇 번 이렇게 연결했나. 잦을수록 점수가 높다
    hit_count       integer      NOT NULL DEFAULT 1,
    last_used_at    timestamptz  NOT NULL,
    created_at      timestamptz,
    updated_at      timestamptz,
    CONSTRAINT pk_field_mapping_memory PRIMARY KEY (id)
);
CREATE UNIQUE INDEX ux_field_mapping_memory
    ON field_mapping_memory (tenant_id, source_field, target_model, target_field);
```

PG14 문법만 쓴다. `NULLS NOT DISTINCT`·`MERGE` 를 쓰지 않고 `INSERT ... ON CONFLICT` 로
카운트를 올린다.

**매핑을 확정할 때 기록한다.** 화면에서 고르는 중에는 기록하지 않는다 — 고민하며 이것저것
눌러 본 것까지 학습하면 기억이 오염된다.

**테넌트 안에서만 공유한다.** 다른 회사의 연결 습관이 섞이면 안 된다.

## 값 모양 판정

샘플 몇 행으로 본다. 전부 맞아야 인정한다 — 하나만 달라도 아니다.

| 모양 | 조건 | 후보 |
|---|---|---|
| 숫자 | 콤마·공백 제거 후 전부 수로 파싱됨 | 수량류 |
| 날짜 | `yyyy-MM-dd` 또는 `yyyyMMdd` 로 전부 파싱됨 | 날짜류 |
| 짧은 코드 | 20자 이하 · 공백 없음 · 값 종류가 적음 | 코드류 |
| 긴 문장 | 20자 초과 또는 공백 포함 | 이름류 |

날짜·숫자 구분은 이미 변환 단계가 하는 일이므로 그 판정을 재사용한다.

## 화면에 어떻게 나타나나

```
수량 *   [BAL_QTY ▾]   112 · 9,451 · 4
         └ 전에 3번 이렇게 연결하셨습니다
```

추천으로 채워진 칸은 표시를 남긴다. 사람이 직접 고른 것과 구분되어야 "이건 내가 안 골랐는데"가
생기지 않는다.

## 다루지 않는 것

- **AI 로 추론** — 별칭·기록·규칙으로 대부분 잡힌다. 외부 호출은 느리고 비용이 들며,
  틀렸을 때 왜 틀렸는지 설명할 수 없다
- **자동 확정** — 추천은 항상 사람이 확인한다. 확정까지 자동으로 하면 조용히 잘못된 자료가 쌓인다
- **테넌트 간 학습 공유** — 다른 회사의 연결 습관이 섞이면 안 된다

## 검증

- 사전에 있는 이름이 최고점을 받는가
- 기록이 쌓이면 사전에 없는 이름도 추천되는가
- 근거가 약하면(임계 미만) 비워 두는가
- 확정 시에만 기록되고, 화면에서 고르는 중에는 기록되지 않는가
- 테넌트가 다르면 서로의 기록이 보이지 않는가
