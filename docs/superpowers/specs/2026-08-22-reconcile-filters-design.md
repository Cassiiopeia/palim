# 대조가 무엇을 볼지 거르는 조건 — 설계

> 창고 하나만 고를 수 있던 것을 **어느 칸으로든** 걸 수 있게 넓힌다.

## 왜 필요한가

전산 쪽에는 창고가 여럿인데 재고를 맡긴 곳은 자기가 보관 중인 것만 안다. 전부 더해서 견주면
맡기지 않은 물량만큼 무조건 어긋난다 — 이 문제는 이미 `WarehouseScope` 로 한 번 풀었다
(07-DECISIONS, V30).

**그 해법이 창고 한 칸에만 붙어 있는 것이 문제다.** 실제로 걸러야 하는 조건은 창고만이 아니다.

| 걸러야 하는 것 | 지금 가능한가 |
|---|---|
| 위탁 창고만 | O — 창고 전용 화면이 있다 |
| 불량·보류 재고 제외 | X — `quality_status` 로 거를 방법이 없다 |
| 유통기한이 지난 것 제외 | X — `expiry_date` 로 거를 방법이 없다 |
| 특정 로트 제외 | X |
| 원천 고유 구분값으로 거르기 | X — `attributes` 에 담겨 있는데 꺼낼 길이 없다 |

칸마다 화면과 컬럼을 새로 만들면 다섯 번째 요구에서 무너진다. **거르는 방법 자체를 하나
만들고, 창고를 그 중 한 줄로 흡수한다.**

### 거는 자리가 하나여야 하는 이유

지금 창고 조건이 걸려야 하는 쿼리가 네 곳이다 — 합계·미매칭·뜯어보기·품목 묶기. 쿼리마다 따로
적으면 한 곳이 빠지고, **빠진 곳만 다른 숫자를 낸다.** 그러면 「합계는 이런데 뜯어보면 다르다」
가 되어 어느 쪽을 믿어야 할지 알 수 없다. 이 프로젝트는 그 어긋남을 이미 두 번 겪었다
(07-DECISIONS 030·032). 조건이 늘어날수록 이 위험은 곱으로 커진다.

## 거르는 단계 — 담긴 뒤

```
   원천 ─(전부)─▶ 담긴 자료 ─(볼 조건)─▶ 품목 묶기 ─▶ 대조
                     ▲                    ▲
                  다 남는다            여기서 좁힌다
```

**수집 단계에서 거르지 않는다.** 이유 셋.

**하나.** 안 받은 자료는 영영 없다. 재고는 시점 자료라 지난 시점을 다시 받을 수 없다. 조건을
잘못 걸었다는 것을 한 달 뒤에 알면 그 한 달이 통째로 비어 있다.

**둘.** 조건을 바꿔도 다시 수집할 필요가 없다. 「위탁 창고만」 과 「전 창고」 를 오가며 견줘 보는
것이 원인을 찾는 방법인데, 그때마다 수집을 다시 돌려야 하면 아무도 안 한다.

**셋.** 회차에 조건을 남기면 과거를 그대로 재현할 수 있다. 수집에서 거르면 「그때 무엇을 안
받았는지」 가 어디에도 안 남는다.

**후처리 스크립트와 겹치지 않는다.** 스크립트는 값을 *다듬고*(담기 전), 이 조건은 줄을
*고른다*(담긴 뒤). 스크립트가 줄을 버리게 만들지 않는 이유가 이것이다 — 버린 줄은 복구할 수
없다.

## 무엇을 걸 수 있는가 — 칸 카탈로그

`field_key` 는 **카탈로그에 있는 것만** SQL 이 된다. 없으면 실행을 거부한다.

```
   key              화면 이름   타입    컬럼 표현식              허용 연산자
   warehouse_code   창고       TEXT    s.warehouse_code        IN NOT_IN IS_EMPTY
   quality_status   품질상태    TEXT    s.quality_status        IN NOT_IN IS_EMPTY
   lot_code         로트       TEXT    s.lot_code              IN NOT_IN IS_EMPTY
   location_code    로케이션    TEXT    s.location_code         IN NOT_IN IS_EMPTY
   zone_code        구역       TEXT    s.zone_code             IN NOT_IN IS_EMPTY
   unit             단위       TEXT    s.unit                  IN NOT_IN
   expiry_date      유통기한    DATE    s.expiry_date           GTE LTE BETWEEN IS_EMPTY
   manufacture_date 제조일     DATE    s.manufacture_date      GTE LTE BETWEEN IS_EMPTY
   base_quantity    기준수량    NUMBER  s.base_quantity         GTE LTE BETWEEN
   raw_item_name    원본 품명   TEXT    s.raw_item_name         (TEXT 전체)
   normalized_name  다듬은 품명 TEXT    s.normalized_name       (TEXT 전체)
   available_quantity 가용수량  NUMBER  s.available_quantity    (NUMBER 전체)
   reserved_quantity  할당수량  NUMBER  s.reserved_quantity     (NUMBER 전체)
   defective_quantity 불량수량  NUMBER  s.defective_quantity    (NUMBER 전체)
   attributes.«키»  (원천 칸)   TEXT    s.attributes->>'«키»'    (TEXT 전체)
```

허용 연산자는 칸마다 고르지 않고 **타입이 정한다**(아래 「연산자」 참고). 칸마다 고르면 그
판단이 칸 수만큼 늘어나고, 늘어난 만큼 「왜 이 칸엔 이게 없지」 가 생긴다.

**표준에 없는 원천 칸도 전부 걸 수 있다.** 매핑되지 않은 원천 컬럼을 `attributes` jsonb 에
통째로 살려 두기 때문이다(`MappedRow`·`TransformEngine`). 그 키 목록은 담긴 자료에서 실제로
뽑는다 — **계정이 바뀌어 칸 구성이 달라져도 화면이 그대로 동작한다.** 코드에 칸 이름을 박지
않는 이유가 이것이다.

### 왜 칸 이름을 자유 입력으로 받지 않는가

**드롭다운으로 고르게 한다.** 자유 입력이면 오타가 저장되고 대조가 돌 때 터진다 — 매일 아침
스스로 도는 일에서 그것은 「어제까지 되던 것이 오늘 죽었다」 로만 드러난다. 그리고 원천 구성이
바뀌어 칸이 없어졌을 때, 카탈로그를 거치면 화면이 「이 칸이 더는 없습니다」 를 말할 수 있다.
자유 입력이면 조건이 사라진 채로 대조가 계속 돈다.

인젝션은 이 선택과 무관하다 — 아래 「식」 절의 방식으로 막는다.

## 연산자 — 타입별로 빠짐없이

칸 이름은 자료에서 뽑는데 연산자는 코드에 박는다. 비대칭이지만 이유가 있다.

**연산자 하나마다 SQL 틀 · 값 개수 규칙 · 화면 위젯 · 이름 넷이 붙는다.** 전부 코드다. 표로
빼도 그 중 셋은 여전히 코드라 「확장 가능한 척」 만 된다. 자유 SQL 말고는 이 넷을 없앨 방법이
없는데 그것은 접었다.

**그래서 확장 지점을 칸에 둔다.** 칸은 자료에서 나오니 무한하고, 연산자는 그 칸을 다루는
문법이라 유한하다. 유한하다면 **타입별로 빠짐없어야** 「이 연산자가 없어서 못 한다」 가 나오지
않는다. 새 칸을 붙이는 데 코드가 필요 없고, 코드가 필요한 것은 **새 타입**뿐이다 — 그리고
타입은 넷이다.

```
   TEXT     IN  NOT_IN  CONTAINS  NOT_CONTAINS  STARTS_WITH  ENDS_WITH
            MATCHES  IS_EMPTY  IS_NOT_EMPTY
   NUMBER   EQ  NE  GT  GTE  LT  LTE  BETWEEN  NOT_BETWEEN  IS_EMPTY  IS_NOT_EMPTY
   DATE     EQ  GT  GTE  LT  LTE  BETWEEN  NOT_BETWEEN  IS_EMPTY  IS_NOT_EMPTY
   BOOL     IS_TRUE  IS_FALSE  IS_EMPTY
```

**부정형을 짝으로 둔다.** `IN` 만 있고 `NOT_IN` 이 없으면 「불량만 빼고 전부」 를 하려고 나머지
값을 전부 체크해야 하는데, 값이 늘어나는 날 조건이 조용히 낡는다 — 새로 생긴 값이 빠진 채로
돈다. 부정형은 편의가 아니라 **자료가 늘어도 안 낡는 조건**을 쓸 수 있게 하는 것이다.

`MATCHES` 는 정규식이다. 이 저장소에는 이미 `RegexGuard` 가 있어(정규화 규칙에서 쓴다) 폭주하는
패턴을 막는 장치를 다시 만들지 않는다.

### 날짜는 상대값이어야 한다

```
   [유통기한 ▾] [이후 ▾] [ 2026-08-22 ]     ← 내일부터 틀린다
   [유통기한 ▾] [이후 ▾] [ 오늘 ▾ ]         ← 매일 맞는다
```

대조는 **매일 아침 스스로 돈다.** 고정 날짜를 박으면 그날만 맞고 다음 날부터 조용히 어긋난다 —
그리고 그것은 「어제는 됐는데 오늘은 안 된다」 로만 드러나 원인을 찾기 어렵다.

그래서 DATE 값은 두 가지를 받는다.

```
   고정   "2026-08-22"
   상대   "TODAY"  "TODAY+30"  "TODAY-7"
```

상대값은 **회차가 돌 때 그 회차의 기준 시각으로 푼다.** 저장 시점에 풀면 저장한 날짜로 굳어
같은 문제가 된다. 회차에 남기는 `filters_json` 에는 **푼 값과 원래 표현을 함께** 적는다 —
「그때 무슨 날짜로 걸렸나」 와 「무슨 규칙이었나」 는 다른 질문이고, 둘 다 필요하다.

### 값 개수는 연산자가 정한다

```
   IS_EMPTY  IS_NOT_EMPTY  IS_TRUE  IS_FALSE      0개
   BETWEEN   NOT_BETWEEN                          2개
   IN        NOT_IN                               1개 이상
   나머지                                          정확히 1개
```

저장은 언제나 배열이고, 개수 규칙은 연산자가 들고 있다. 화면과 서버가 **같은 규칙을 한 곳에서**
읽으므로 「화면은 됐는데 저장이 거부한다」 가 생기지 않는다.

## 저장

```sql
CREATE TABLE reconcile_filter
(
    id            uuid         NOT NULL,
    tenant_id     uuid         NOT NULL,
    definition_id uuid         NOT NULL,
    side          varchar(10)  NOT NULL,                        -- LEFT | RIGHT
    ordinal       integer      NOT NULL,
    row_type      varchar(20)  NOT NULL DEFAULT 'FIELD',
    field_key     varchar(200) NOT NULL,
    operator      varchar(20)  NOT NULL,
    values_json   jsonb        NOT NULL DEFAULT '[]'::jsonb,
    created_at    timestamptz,
    updated_at    timestamptz,
    CONSTRAINT pk_reconcile_filter PRIMARY KEY (id),
    CONSTRAINT fk_reconcile_filter_definition
        FOREIGN KEY (definition_id) REFERENCES reconcile_definition (id) ON DELETE CASCADE
);
CREATE INDEX ix_reconcile_filter_definition ON reconcile_filter (definition_id, side, ordinal);
```

**값은 언제나 배열이다.** `EQ` 는 원소 하나, `BETWEEN` 은 둘, `IS_EMPTY` 는 없음. 모양이 하나면
화면·검증·SQL 조립이 전부 한 갈래로 끝난다. 연산자마다 저장 모양이 다르면 그 조합만큼 분기가
생기고, 안 쓰는 분기부터 썩는다.

`row_type` 은 `FIELD`(조건 줄)와 `EXPRESSION`(식)을 가른다. 식은 `field_key`·`operator` 를
쓰지 않고 `values_json` 에 글 하나를 담는다 — 한 side 에 식은 최대 하나다. 둘을 한 표에 두는
이유는 **순서(`ordinal`)와 좌우(`side`)가 같은 개념**이기 때문이고, 표가 갈리면 「어느 쪽이
먼저인가」 를 두 곳에서 맞춰야 한다.

`ON DELETE CASCADE` 는 정의를 지울 때 조건이 남지 않게 한다(#150 에서 같은 문제를 겪었다).

### 창고 설정 옮기기

```sql
INSERT INTO reconcile_filter (id, tenant_id, definition_id, side, ordinal,
                              row_type, field_key, operator, values_json, created_at, updated_at)
SELECT ..., d.tenant_id, d.id, 'LEFT', 0,
       'FIELD', 'warehouse_code', 'IN',
       to_jsonb(string_to_array(d.left_warehouses, ',')), now(), now()
  FROM reconcile_definition d
 WHERE d.left_warehouses IS NOT NULL AND d.left_warehouses <> '';
-- RIGHT 도 같은 모양으로
```

이미 설정해 둔 창고는 그대로 살아난다.

**옛 컬럼은 지우지 않는다.** `reconcile_definition.left_warehouses`·`right_warehouses` 는
컬럼으로 남기되 **코드가 더는 읽지 않는다**(엔티티 필드와 `leftScope()`·`rightScope()` 를
걷어낸다). 마이그레이션이 잘못 옮겼을 때 원본을 볼 곳이 있어야 하고, 컬럼을 지우는 것은
되돌릴 수 없다. `reconcile_run` 쪽 옛 컬럼은 **계속 읽는다** — 그것이 지난 회차의 유일한 기록이다.

## 회차 재현

```sql
ALTER TABLE reconcile_run ADD COLUMN filters_json jsonb;
```

회차가 돌 때 쓴 조건을 통째로 찍는다. V32 가 창고 CSV 로 하던 일을 넓힌 것이다.

**표로 쪼개지 않는 이유** — 회차는 편집 대상이 아니라 기록이다. 조회도 「그때 뭐였나」 를 통째로
읽는 것뿐이라 조인만 늘어난다. 그리고 카탈로그에서 사라진 칸도 그대로 남길 수 있다 — 정규화된
표라면 없는 칸을 가리키는 행이 되어 무결성이 애매해진다.

`filters_json` 이 비어 있으면 V32 의 옛 컬럼을 읽는다. 그 이전 회차는 「전 창고를 봤다」 로
읽는다 — 실제로 그랬다.

## SQL 조립 — `FilterSpec`

`WarehouseScope` 의 계약을 그대로 넓힌다. 한 자리에서만 조각을 만들고, 네 쿼리가 그것을 쓴다.

```java
public record FilterSpec(FilterNode root) {          // root 는 AST. 조건 줄도 식도 여기로 모인다
    String sqlAnd(String alias, String prefix);      // " AND s.warehouse_code IN (:l0) AND ..."
    Map<String, Object> params(String prefix);
    boolean isAll();
    String describe();                               // 화면에 보여줄 말
    String toExpression();                           // AST → 사람이 읽는 식
}
```

**`FilterSpec` 은 줄 목록이 아니라 AST 를 든다.** 조건 줄은 `AND` 로 묶인 비교 노드들로
컴파일되고, 식은 파서가 만든 노드가 그대로 들어온다. SQL 을 만드는 코드가 한 벌이라 두 입구가
갈릴 수 없다(아래 「식」 절).

- **비어 있으면 빈 문자열.** `IN ()` 은 문법 오류라 「전부」 를 빈 목록으로 표현할 수 없다.
- **바인딩 이름은 `prefix + 줄번호`.** 한 쿼리가 좌·우 두 조건을 동시에 거는 자리가 있다(품목
  묶기). 이름이 겹치면 뒤에 넣은 값이 앞을 덮어써 **양쪽이 같은 조건으로 걸린다** — 화면은
  멀쩡해 보이는데 한쪽이 통째로 비거나 엉뚱한 줄이 짝으로 잡힌다. 줄 번호로 뽑으면 겹칠 수 없다.
- 컬럼 표현식은 **카탈로그에서만** 온다. 사용자 값은 언제나 바인딩 파라미터로 간다.

## 식 — 줄로 안 되는 조건

조건 줄은 전부 AND 다. 「창고 A 이거나 품질상태 B」 처럼 칸을 넘는 OR, 괄호로 묶는 조건은 줄로
쓸 수 없다. 그런 조건을 위해 **식**을 하나 더 쓸 수 있다.

```
 ▾ 고급 — 줄로 안 되는 조건
 ┌──────────────────────────────────────────────────────┐
 │ (창고 = '위탁창고' 또는 창고 = '예비창고')              │
 │   그리고 품질상태 ≠ '불량'                             │
 │   그리고 유통기한 이후 오늘                             │
 └──────────────────────────────────────────────────────┘
  ✓ 읽었습니다 — 27줄 → 14줄 · 합계 20,417
```

식과 조건 줄은 **AND 로 함께** 걸린다. 한 쪽만 쓸 수도 있다.

### 안전 — 검사하지 않고 다시 만든다

```
   사용자 글 ─▶ [파서] ─▶ AST ─▶ [SQL 생성기] ─▶ SQL + 바인딩 값
                                     ▲
                        여기서 나오는 SQL 은 우리가 적어 둔 틀뿐이다
```

**금지어 목록으로 막지 않는다.** `;` 를 막고 `DROP` 을 막는 방식은 언젠가 뚫린다 — 막을 것을
전부 알고 있어야 성립하는 방어이기 때문이다. 우리는 반대로 한다: **통과한 것으로 무엇을 만들지**
를 우리가 정한다.

이 구조가 보장하는 것은 셋이다.

**하나 — 사용자 문자열이 SQL 에 이어붙는 자리가 없다.** 식별자는 카탈로그에서만 나오고, 값은
전부 바인딩 파라미터로 간다. 파서에 구멍이 있어 이상한 것이 통과해도, 그것은 AST 노드가 되고
AST 노드가 만들 수 있는 SQL 은 아래 문법이 허용하는 모양뿐이다.

**둘 — 위험한 것은 막는 게 아니라 문법에 없다.** 함수 호출·서브쿼리·세미콜론·주석·문자열
이어붙이기가 문법에 아예 없다. 표현할 수단이 없는 것은 막을 필요도 없다.

**셋 — 실패는 저장 시점에 드러난다.** 못 읽는 식은 저장이 거부되고, 어디서 막혔는지를 화면이
가리킨다. 도는 순간까지 미뤄지지 않는다.

### 문법

```
   or         := and ( ("또는" | "OR") and )*
   and        := not ( ("그리고" | "AND") not )*
   not        := ("아님" | "NOT")? primary
   primary    := "(" or ")" | comparison
   comparison := field ("=" | "≠" | ">" | ">=" | "<" | "<=") operand
               | field ("포함" | "CONTAINS") 문자열
               | field ("IN" | "중에") "(" 값 ("," 값)* ")"
               | field ("BETWEEN" | "사이") 값 "AND" 값
               | field ("비었음" | "IS EMPTY")
   field      := 카탈로그 키 또는 그 화면 이름   ← 없으면 읽기 실패
   operand    := 숫자 | '문자열' | 날짜토큰
   날짜토큰    := "오늘" | "오늘+30" | "2026-08-22"
```

**식별자 자리에 올 수 있는 것은 카탈로그 키뿐이다.** 문법에 임의 식별자가 없다. 그래서 테이블
이름·다른 칼럼·함수 이름을 적을 방법이 없다.

한글 연산자를 함께 받는 이유는, 이 화면을 쓰는 사람이 개발자가 아니기 때문이다. 「그리고」 로
쓰든 `AND` 로 쓰든 같은 AST 가 된다.

### 폭주 방지

파싱이 성공해도 비싼 것은 만들 수 있다. 셋으로 막는다.

- 글 길이 **2000자**, AST 깊이 **20**, 노드 수 **200** 상한. 넘으면 저장 거부
- 조회에 `statement_timeout` 을 건다 — 화면에서 도는 미리보기가 서버를 물고 늘어지지 않는다
- `CONTAINS` 는 `LIKE '%…%'` 라 인덱스를 못 탄다. 화면이 그 사실을 말한다 (막지는 않는다)

### 조건 줄도 같은 AST 로 간다

**SQL 을 만드는 경로를 하나로 둔다.**

```
   조건 줄 ─┐
            ├─▶ AST ─▶ SQL
   식     ─┘
```

두 입구가 각자 SQL 을 만들면 「줄로 건 것과 식으로 건 것이 다르게 돈다」 가 언젠가 생기고, 그
차이는 숫자로만 드러나 원인을 찾기 어렵다. 이 프로젝트는 판단이 두 군데로 갈려 어긋난 일을 이미
두 번 겪었다(07-DECISIONS 030·032).

경로가 하나면 **「지금 조건을 식으로 보기」 가 공짜로 나온다** — AST 를 글로 되돌리면 된다.
사람이 조건 줄로 시작해 식을 배우는 길이 되고, 「내가 고른 것이 무슨 뜻인지」 를 확인하는 길도
된다.

## 화면

### 대조 정의 상세 — 「견줄 창고」를 「볼 조건」으로

```
 볼 조건                                                    이카운트 쪽
  [창고      ▾] [이것만 ▾]  ☑ 위탁창고(01) 9,426   ☐ 사무실(02) 312
  [품질상태  ▾] [이것만 ▾]  ☑ 정상   ☐ 불량
  [유통기한  ▾] [이후   ▾]  [오늘 ▾]
                                                        [+ 조건 추가]
 ──────────────────────────────────────────────────────────────────
  ▾ 고급 — 줄로 안 되는 조건                          [지금 조건을 식으로 보기]
  ┌────────────────────────────────────────────────────────────────┐
  │ (창고 = '위탁창고' 또는 창고 = '예비창고') 그리고 품질상태 ≠ '불량' │
  └────────────────────────────────────────────────────────────────┘
   ✓ 읽었습니다
 ──────────────────────────────────────────────────────────────────
  이 조건이면  27줄 → 14줄 · 합계 20,417                      [저장]
```

- **「고급」 은 접혀 있다.** 대부분은 줄로 끝나고, 접힌 채로도 무엇이 들어 있는지는 보인다
  (내용이 있으면 접힌 제목에 표시). 안 쓰는 사람에게 안 보이되 숨겨지지는 않는다.
- **「지금 조건을 식으로 보기」** 는 줄로 고른 것을 그대로 식으로 적어 준다. AST 가 하나라
  공짜로 나오는 기능이고, 식을 배우는 길이자 「내가 고른 것이 무슨 뜻인지」 확인하는 길이다.
- 식이 안 읽히면 **저장이 막히고 어디서 막혔는지를 가리킨다.** 도는 순간까지 미루지 않는다.
- 값 위젯이 타입을 따른다 — TEXT 는 **담긴 자료의 실제 값**을 건수·수량과 함께 체크박스로,
  DATE 는 날짜칸, NUMBER 는 숫자칸. 무엇을 골라야 하는지 규모로 알아볼 수 있다.
- **저장 전에 몇 줄이 남는지 보인다.** 이것이 없으면 저장하고 대조를 돌려 봐야 결과를 안다.
- 조건이 없는데 값이 여럿이면 지금의 경고를 유지한다 — 조용히 틀린 답을 내는 것보다 낫다.

### 품목 묶기 — 지금 조건이 안 보인다

지금 이 화면은 원천 이름만 말한다. 뒤에서는 창고 범위가 제대로 걸리는데 **화면에 창고가 한
글자도 없어서**, 보고 있는 수치가 전 창고 합인지 한 창고인지 알 수 없다. 그리고 여기서 대조
정의로 가는 링크가 없어 조건을 고치러 갈 수도 없다.

```
 대조 «이름» 에 적힌 두 곳을 봅니다 — «좌» ↔ «우»
 볼 조건  [창고 위탁창고(01)]  [품질상태 정상]              조건 고치기 →
```

조건이 없으면 「조건 없음 — 전부 더해서 봅니다」 를 경고색으로.

### 대조 결과 상세

그 회차가 쓴 조건을 같은 칩으로 보여준다. 「어제와 오늘 숫자가 왜 다른지」 가 화면에서 끝난다.

## 건드리지 않는 것

- **연동·수집·매핑·후처리 스크립트.** 조건은 담긴 뒤에만 건다.
- **동결 도메인**(sku·order·collector·channel·mapping·incident).

## 검증

Testcontainers 로 실제 PostgreSQL **14** 를 띄운다.

1. 조건이 없으면 지금과 같은 답이 나온다
2. 창고 CSV 가 조건 줄로 옮겨지고, 옮긴 뒤 결과가 옮기기 전과 같다
3. 좌·우에 서로 다른 조건을 걸어도 섞이지 않는다 (바인딩 이름 겹침 회귀)
4. 카탈로그에 없는 `field_key` 는 실행을 거부한다
5. 회차에 조건이 남아, 정의를 바꿔도 지난 회차 상세가 변하지 않는다
6. **합계·미매칭·뜯어보기·품목 묶기 네 쿼리가 같은 숫자를 낸다**
7. 값이 0개인 `IN` 은 `IN ()` 을 만들지 않는다
8. 상대 날짜(`TODAY+30`)가 **회차 기준 시각**으로 풀린다 — 하루 뒤에 같은 정의로 돌리면 걸리는
   범위도 하루 밀린다
9. 연산자가 요구하는 값 개수를 어기면 저장이 거부된다 (`BETWEEN` 에 값 1개 등)
10. **인젝션 시도가 전부 읽기 실패로 떨어진다** — 세미콜론, 주석(`--`, `/* */`), 서브쿼리,
    함수 호출, `UNION`, 카탈로그에 없는 식별자, 따옴표 탈출. 시험에 payload 목록을 박아 둔다
11. 길이·깊이·노드 수 상한을 넘는 식은 저장이 거부된다
12. **조건 줄과 같은 뜻의 식이 같은 SQL·같은 결과를 낸다** — 두 입구가 한 AST 로 모이는지

시험 자료는 합성으로 만든다.

## 나중에

- **식을 조건 줄로 되돌리기.** 지금은 줄 → 식 한 방향만 된다. 반대는 AST 가 줄로 표현 가능한
  모양일 때만 되는데, 그 판정과 「안 되는 식을 열었다가 못 돌아가는」 경우의 화면이 만만치
  않다. 실제로 식을 쓰다가 줄로 내려오고 싶다는 말이 나오면 그때 만든다.
- **조건을 다른 대조에 복사하기.** 대조가 여럿이 되면 같은 조건을 다시 짜게 된다.
- **다른 표준 모델로 넓히기.** 지금 카탈로그는 재고 스냅샷 전용이다. 대조가 다른 표를 보게
  되면 카탈로그를 표별로 나눈다 — `FilterSpec` 은 그대로 쓴다.
